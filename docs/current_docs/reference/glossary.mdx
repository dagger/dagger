# Glossary

Terms used in the Dagger documentation, each with a link to the page that covers it.

## Artifact

A value that a workspace exposes at a [DAG address](#dag-address): the result of a zero-argument function on an installed module, such as a `Service`, `Container`, `Directory`, or `File`. `dagger list` lists the artifacts in a workspace by type. See [Module wiring](../config/module-wiring.mdx).

## Cache

Dagger caches work at two levels. The function cache stores a function's result, keyed by its inputs, and a hit skips the function entirely. The layer cache stores the result of each operation inside a function, such as a container command, so a function that runs again reuses its unchanged steps. See [engine.json](./config-files/engine-json.mdx) for how the engine prunes it.

## Cache volume

A directory whose contents persist across [sessions](#session), such as a package manager's download cache. A function mounts it into a container. See [`CacheVolume`](./api/cache-volume.mdx).

## Changeset

A set of proposed file changes. A [Generator](#generator) returns one, and so can any function that edits files, such as a formatter's `fix`. Dagger shows the changed paths for review and writes them only when the changeset is applied. See [Generating code](../using/generating.mdx).

## Check

A function that validates the project, such as a test suite, a linter, or a scan. A module marks it with `@check` or its SDK's equivalent. `dagger check` runs every Check in the workspace and exits non-zero if any fails. Each Generator also provides a Check that fails when the files it generates are stale. See [Checking your code](../using/checking.mdx).

## Client

A program that opens a [session](#session) with the [engine](#engine) and calls the [Dagger API](#dagger-api). The Dagger CLI is a client. Other programs become clients through a [generated client](#generated-client), a [client library](#client-library), or raw GraphQL. See [Client libraries](./client-libraries/index.mdx).

In the context of [services](#service), a client is any container or program that connects to a service.

## Client library

A package, published for each language, that calls the [core API](#core-api) from a program, such as `dagger.io/dagger` for Go or `@dagger.io/dagger` for TypeScript. See [Client libraries](./client-libraries/index.mdx#standalone-client-libraries).

## Cloud Checks

A Dagger Cloud feature that runs a workspace's Checks on [Cloud Engines](#cloud-engine) after each push or pull request to a GitHub repository. `dagger cloud checks on` enables it. See [Set up Cloud Checks](../getting-started/cloud-checks.mdx).

## Cloud Engine

An [engine](#engine) that Dagger Cloud runs. [Cloud Checks](#cloud-checks) run on Cloud Engines.

## Collection

A set of objects with unique keys that a module returns for the units of a project it discovers at run time, such as Go packages or test files. Each collection adds a flag to `dagger check` and `dagger generate`, such as `--go-package`, that selects items by key. See [Collections](../using/calling-functions.mdx#collections) and [Select collection items](../using/checking.mdx#select-collection-items).

## Constructor

The function that creates a module's main [object](#object). Its arguments are the module's [settings](#setting). See [Design your module for wiring](../config/module-wiring.mdx#design-your-module-for-wiring).

## Core API

The types and functions the [engine](#engine) provides without any module installed, such as `Container`, `Directory`, `Secret`, and `Service`. Modules extend it with their own types. See the [API reference](./api/index.mdx).

## DAG address

An address with the `dag://` scheme that names something in a workspace by its path. The first segment is a module's [install name](#install-name), and the rest names functions, as in `dag://go/packages/tests/test`. Query parameters select [collection](#collection) items. The [workspace main](#workspace-main) module's functions omit the module segment, as in `dag://serve`. Also called a DAG link.

`dagger check` and `dagger generate` take DAG addresses to select Checks and Generators. A [setting](#setting) whose value is a DAG address [wires](#module-wiring) in another module's [artifact](#artifact). See [Filter checks](../using/checking.mdx#filter-checks).

## Dagger API

The GraphQL API that the [engine](#engine) serves. The CLI, modules, and [clients](#client) all run on it. It is made of the [core API](#core-api) plus the types of the modules a workspace installs. See the [API reference](./api/index.mdx).

## Dagger Cloud

Dagger's hosted service. It stores [traces](#trace) and runs [Cloud Checks](#cloud-checks) on [Cloud Engines](#cloud-engine). `dagger cloud signup` creates an account. See [Set up Cloud Checks](../getting-started/cloud-checks.mdx).

## `dagger-module.toml`

The manifest of a [module](#module). It holds the module role of the Dagger 0.x [`dagger.json`](#daggerjson). See [Migrate from dagger.json](../config/migrate-dagger-json.mdx).

## `dagger.toml`

The [workspace](#workspace) configuration file. It records the installed modules, their [settings](#setting), [SDK scopes](#sdk-scope), and [includes](#include). Dagger reads the nearest `dagger.toml` above the current directory, up to the [workspace root](#workspace-root). See [dagger.toml](./config-files/dagger-toml.mdx).

## Dang

Dagger's native language for writing modules. A Dang module runs as written, with no code generation or build step. See [Dang](./sdks/dang.mdx).

## Engine

The Dagger Engine serves the [Dagger API](#dagger-api). It runs functions and containers, starts [services](#service), and stores the [cache](#cache). The CLI starts an engine in a container on the local machine, and Dagger Cloud runs [Cloud Engines](#cloud-engine). See [engine.json](./config-files/engine-json.mdx).

## Function

An operation that a module exposes on one of its [objects](#object). It takes typed arguments and returns a value, often another object whose functions can be called next. Checks, Generators, and services are functions with a role in the workspace. See [Calling functions](../using/calling-functions.mdx).

## Generated client

A typed binding to one module's API, including the [core API](#core-api) and every module it depends on. An [SDK](#sdk) generates it into an [SDK scope](#sdk-scope), and `dagger generate` regenerates it. See [Generated clients](./client-libraries/index.mdx#generated-clients).

## Generator

A function that produces source changes, such as code generation, formatting, or lockfile updates, and returns them as a [changeset](#changeset). A module marks it with `@generate` or its SDK's equivalent. `dagger generate` runs every Generator in the workspace. See [Generating code](../using/generating.mdx).

## Include

An `[[include]]` entry in `dagger.toml` that inherits another config file. The included config is merged underneath the workspace's own, so the workspace wins every conflict. See [Includes](../config/includes.mdx).

## Install name

The key a module is installed under in `dagger.toml`, as in `[modules.<name>]`. Commands, flags, and [DAG addresses](#dag-address) refer to the module by this name, as in `dagger check --go` and `dag://go/packages`.

## Lockfile

The `dagger.lock` file beside `dagger.toml`. It pins resolved image, Git, and vanity URL lookups so that later runs reuse them. `dagger lock update` refreshes the pins. See [`dagger.lock`](./config-files/dagger-toml.mdx#daggerlock).

## Module

A package of code that the [engine](#engine) loads to extend the [Dagger API](#dagger-api). It defines [objects](#object) and [functions](#function), including Checks, Generators, and services. A module is written with an [SDK](#sdk), described by [`dagger-module.toml`](#dagger-moduletoml), and used by installing it in a workspace. See [SDKs](./sdks/index.mdx).

The docs name a Dagger module by its install name in code font, such as the `go` module. "Go module" without code font is a Go project defined by a `go.mod` file. `Module` in code font is the [API type](./api/module.mdx).

## Module source

The address a module is installed from: a local path such as `./ci/myapp`, or a Git ref such as `github.com/org/mod@v1.0`. It is the `source` of a module entry in `dagger.toml`. See [`[modules.<name>]`](./config-files/dagger-toml.mdx#modulesname).

## Module wiring

Connecting installed modules through [settings](#setting). A setting whose value is a [DAG address](#dag-address) passes the [artifact](#artifact) at that address to the module's [constructor](#constructor). See [Module wiring](../config/module-wiring.mdx).

## Object

A type that a module defines, with fields and [functions](#function). A module's main object is named after the module and created by its [constructor](#constructor).

## Official module

A module that Dagger publishes under `dagger.io/`, such as `dagger.io/go` or `dagger.io/js/eslint`. See [Modules](./modules/index.mdx).

## SDK

The toolkit for writing modules in one language. Each SDK is a module itself, such as `dagger.io/sdk/go`. An SDK installed in a workspace creates modules with `dagger module init` and generates their code. See [SDKs](./sdks/index.mdx).

## SDK scope

A directory where an [SDK](#sdk) generates code: a module, [generated clients](#generated-client), or both. `dagger.toml` records each scope under `[sdks.<name>.scopes]`. See [`[sdks.<name>]`](./config-files/dagger-toml.mdx#sdksname).

## Secret

A credential that a function receives as a `Secret`, read from a provider URI such as `env:DEPLOY_TOKEN`, `file:./token.txt`, or `vault://secret/foo/bar.token`. Dagger keeps secret values out of logs, container filesystems, and the cache. See [Secrets](../config/secrets.mdx).

## Service

A long-running process, such as a database or web server, running in a container. A module function that returns a `Service` and takes no required arguments is a service of the workspace, and `dagger start` starts it and tunnels its ports to the local machine. See [Running services](../using/services.mdx).

## Session

A connection between a [client](#client) and the [engine](#engine). Each `dagger` command that calls the engine runs in a session, and `dagger api with-session` starts one for another program. See [Client libraries](./client-libraries/index.mdx#standalone-client-libraries).

## Setting

A value that a workspace sets for an installed module, stored under `[modules.<name>.settings]` in `dagger.toml`. Each setting is an argument to the module's [constructor](#constructor). `dagger module settings` lists and changes them. See [Configuring your Workspace](../config/index.mdx).

## Trace

The record of a Dagger run: each function call and operation, with its logs and duration. The CLI sends traces to [Dagger Cloud](#dagger-cloud).

## User configuration

The file `~/.config/dagger/config.toml`, or the file named by `$DAGGER_CONFIG`. It holds personal module settings for a workspace, keyed by the workspace's Git remote, and merges them on top of `dagger.toml`. See [User configuration](../config/user.mdx).

## Workspace

The Git repository that Dagger runs in, together with its configuration. Its installed modules provide the Checks, Generators, services, and functions that `dagger` commands run. `-W` selects a remote workspace by its Git address. `Workspace` in code font is the [API type](./api/workspace.mdx) that gives a module access to workspace files. See [Configuring your Workspace](../config/index.mdx).

## Workspace main

The installed module marked `main = true` in `dagger.toml`. Its functions are hoisted onto the [workspace root](#workspace-root), so they are called and addressed without the module name. See [Reference the workspace main](../config/module-wiring.mdx#reference-the-workspace-main).

## Workspace root

The root of the workspace's Git repository. A path that starts with `/` in a command or `dagger.toml` is relative to it.

## Dagger 0.x terms

These terms appear in `dagger.json` files from Dagger 0.x. See [Migrate from dagger.json](../config/migrate-dagger-json.mdx).

### `dagger.json`

The Dagger 0.x file that was both a module's manifest and the workspace configuration. [`dagger-module.toml`](#dagger-moduletoml) and [`dagger.toml`](#daggertoml) hold those roles in 1.0. `dagger workspace migrate` and `dagger module migrate` convert it.

### Toolchain

A module installed in a Dagger 0.x `dagger.json` to add its functions and checks to the project. `dagger workspace migrate` installs each toolchain as a module in `dagger.toml` and converts its customizations to [settings](#setting).

### Blueprint

A module installed in a Dagger 0.x module with `dagger init --blueprint`, whose functions that module served as its own.
