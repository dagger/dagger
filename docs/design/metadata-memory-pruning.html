Pruning retained DAGQL cache metadata

Design and implementation plan. Verified against upstream/main@1c6e07b197327c57e9db8584deb36e5166278677 on 3 August 2026. The brief's b1c2c81eeea9e1b751194b7372b9a394cd5c5a7f is an ancestor. The intervening commits do not change the code discussed here.

1. Observed defect

A current-main experiment persisted 11,003 unique Directory.glob calls that returned no matches. They consumed effectively zero physical cache space. Calling /debug/gc did not change the counts because that endpoint invokes Go runtime heap collection and debug.FreeOSMemory; it does not prune the DAGQL cache (cmd/engine/debug.go:53-57). An explicit DAGQL prune-all removed all 11,003 persisted roots, reported only 4 KiB of physical bytes reclaimed, reduced live results from 15,336 to 4,332, and reduced allocated equivalence-class slots from 19,906 to 7,265.

The result follows directly from the current implementation. Cache.Prune starts work only when a disk policy produces a physical-byte target. A scalar or metadata-only result often contributes zero CacheUsageEntry.SizeBytes. Thousands of such results can therefore keep result objects, call frames, dependency edges, terms, equivalence classes, digests, and indexes alive without ever starting automatic pruning.

Proposed correction. Keep a coarse byte estimate for the DAGQL graph. Start a separate pruning pass when that estimate exceeds a finite maximum. First compact stale equivalence classes. If the estimate still exceeds the lower target, remove cold persisted edges through the existing ownership collector until a post-compaction estimate reaches the target or only protected results remain. Do not convert this estimate to physical cache bytes, and do not require disk measurement or a successful disk-stat call.

Required outcome

A growing set of zero-disk or tiny-disk persisted results must cross a configured threshold by itself. The pass must remove persisted ownership from cold roots, collect newly unowned dependency closures, run normal release hooks, and reduce the measured graph structures. Active sessions and engine-lifetime roots must keep their ownership.

Non-goals

  • Do not estimate exact retained heap for each root. Shared dependency closures make exact attribution non-additive.
  • Do not add a process-wide heap trigger, GOMEMLIMIT, Module SchemaBuilder eviction, content-hash redesign, recipe expansion fixes, paging, or a generic snapshot collector.
  • Do not inspect arbitrary object graphs. Direct byte sizing is limited to known call-frame strings, retained persistence envelopes, and payloads that implement a narrow sizing interface.
  • Do not rebuild every cache map in the first implementation. Add only the equivalence-class compaction required to make the proposed estimate fall after churn.
  • Do not redesign the public GraphQL cache API, security model, multi-user policy, or broad cache metrics.

2. Current code

Disk pruning

  1. dagql/cache_prune.go:58-163 loops over disk policies. For each policy it snapshots active session result IDs, calls measureAllResultSizes, builds snapshotPruneState, and calls pruneTargetBytes.
  2. snapshotPruneState at lines 165-258 sums physical CacheUsageEntry.SizeBytes. Metadata-only and scalar entries commonly sum to zero.
  3. pruneTargetBytes at lines 579-617 returns no target unless MaxUsedSpace, MinFreeSpace, TargetSpace, or ReservedSpace requires one. An explicit all/filter policy without thresholds is the exception.
  4. Only after it gets a positive target does the code compute the active dependency closure, candidates, and a prune plan. TTL expiry changes lookup and candidate order, but it does not start pruning.
  5. collectPruneCandidates at lines 289-359 considers persisted roots, excludes the active closure and unpruneable results, and orders candidates by expiry and age. buildPrunePlan at lines 361-450 simulates shared incoming ownership and physical usage identities.
  6. The loop removes persisted edges at line 97. It invokes equivalence-class compaction and snapshot garbage collection only after at least one persisted edge was removed, at lines 146-160.

A persisted edge is the ownership edge that keeps a result alive after its producing session ends. Removing that edge is only an eviction decision. collectUnownedResultsLocked decides which results actually became unreachable.

3. Measured evidence

The following workload measurements came from the two investigations supplied to this council. This draft did not rerun those profiles.

  • A minimal persisted scalar added about 3.12 KiB of HeapAlloc and 28 objects. A unique no-match Directory.glob added about 4.78 KiB and 43.9 objects. An eight-argument call added about 5.48 KiB and 60.9 objects.
  • Creating 200,000 live results over a 2,000-result unpruneable floor added 1,047-1,058 MiB, or 5.238-5.292 KiB per result. Releasing the session without class compaction left 198.7 MiB, or about 994 bytes per peak result. Current class compaction reduced that floor to 56.6 MiB. Later compacted floors were 72.0, 73.6, 76.4 MiB, about 5-7% of peak.
  • Current forced class compaction took about 23 ms over roughly 400,000 slots. Current full pruning of 200,000 roots took about 5.7 seconds. These observations calibrate the scale tests; they are not universal latency guarantees.
  • A 400,000-root cut produced roughly 158 MiB of logs because the current path logs and clones frames per root.
  • A separate module workload fell from 378 MiB to 58 MiB after forced full pruning. The modeled DAGQL metadata in that workload was reportedly about 35 MiB. The extra release came from pools such as module servers, so this does not establish a fixed estimate-to-RSS ratio.
  • A controlled v0.20.3 versus v0.21.7 graceful-restart experiment reproduced about 2.2 times the heap and RSS from the loaded in-memory DAGQL graph. Release-specific dependency and recipe expansion defects exist, but this design does not change them.

Focused current-main tests passed: go test ./dagql -run 'TestCachePrune|TestCacheMakeResultUnpruneable|TestCacheUsageEntriesAll' -count=1, go test ./dagql -run 'TestCompactEqClassesSkipsWhenBelowThreshold|TestCachePruneCompactsEqClassesAndPreservesLookup' -count=1, and go test ./engine/server -run 'Test(LocalCacheDiskPressureGCNeeded|GetDagqlGCPolicy|ResolveEngineLocalCachePrunePolicies)' -count=1. The compaction tests confirm both the current two-times guard and compaction after a persisted-edge removal.

4. Proposed byte estimate

Add Cache.EstimatedMetadataBytes(). It returns estimated bytes for cache-owned DAGQL graph structures. It does not return RSS, HeapAlloc, physical cache bytes, or exact retained heap.

estimatedBytes =
    3,072 * len(resultsByID)
  +   512 * len(egraphTerms)
  + 1,024 * max(0, len(egraphParents) - 1)
  + logicalVariableBytes
TermSource and unitReason
resultsByID3,072 estimated bytes per live resultCovers fixed result state, ownership, digests, and index overhead at coarse resolution.
egraphTerms512 estimated bytes per live termCharges recipe terms independently of result count.
egraphParents - 11,024 estimated bytes per allocated class slotIncludes stale class records until actual compaction releases them.
logicalVariableBytesLogical string and byte-slice lengthsPrevents one supported multi-megabyte argument or result from looking like one fixed-size entry.

The three cardinalities already exist. Reading them is O(1) under egraphMu.RLock. The fixed weights are intentionally coarse. They fit the observed 3.12-5.48 KiB live-result samples and the roughly 994-byte stale-class floor without adding counters for every edge, map membership, or digest.

Call-frame bytes

Add a logical byte sizer in dagql/result_call_frame.go. It counts every string-bearing field in a ResultCall graph, including type, module, field, argument, literal, effect, view, and digest strings. ResultCallLiteral keeps both StringValue and DigestedStringValue, so the sizer counts both.

The walk visits each distinct *ResultCall pointer once within one installed root frame. It does not follow the runtime ResultCallRef.shared pointer. If two root frames point to the same child frame, each root receives the child charge. This conservative cross-root duplication avoids global reference counting. The visited set terminates even on malformed cycles. The walk never serializes a call frame.

Payload and imported-envelope bytes

Add this optional interface:

type CacheMetadataSizer interface {
    CacheMetadataSizeBytes() int64
}

dagql.String returns its length. Scalar[T] delegates when its wrapped value implements the interface. core.JSON returns its byte length. core.JSONValue returns len(Data). The interface contract is pure, O(1), allocation-free, and limited to retained logical string or byte lengths; it must not call back into the cache. Other values receive only the fixed result charge.

An imported result can retain raw bytes instead of a decoded value. A recursive envelope sizer sums len(ObjectJSON) and len(ScalarJSON) for the root envelope and every nested Items envelope. It does not serialize the value. The raw-envelope charge stays in the total until materialization. Materialization replaces that charge with the decoded value's CacheMetadataSizer result. It never charges both representations at once.

Registered-result charging protocol

Add metadataMu, metadataOwner *Cache, metadataFrameBytes, and metadataPayloadBytes to sharedResult. Add one atomic.Int64 named logicalVariableBytes to Cache. The per-result fields make cache ownership explicit.

  1. storeResultCall computes the new call-frame size before locking; installed call frames remain immutable. Under metadataMu and then resultCallMu, it swaps the frame and its local byte charge. If metadataOwner is non-nil, it applies the old-to-new delta to that cache's atomic total. Detached results update only their local charge.
  2. Replace the remaining production struct literals that set resultCall directly with storeResultCall. This guarantees a local frame charge before first publication.
  3. Add publishResultLocked. The caller must hold egraphMu. The helper takes metadataMu, computes the initial payload charge from the retained decoded payload or raw envelope under payloadMu, sets metadataOwner, adds both local charges, and inserts the result into resultsByID. Re-publishing the same result to the same ID is an idempotent validation. A conflicting cache, ID, or result pointer is an error.
  4. Use publishResultLocked from normal e-graph indexing and version-17 import. Import stores its frame and retained envelope before publication. The temporary sharedResult used only by cache_persistence_worker.go is never published, so it never changes the cache total.
  5. After publication, only a cache-aware payload replacement helper may exchange a retained envelope for a decoded payload. It takes metadataMu and then payloadMu, swaps the state and local charge together, and applies one delta to the owner. Refactor both eager and lazy import decode paths through this helper. Other payload fields that do not retain sized bytes continue to use payloadMu alone.
  6. Add unpublishResultMetadataLocked. The caller holds egraphMu. The helper takes metadataMu, verifies the owner, clears it, and subtracts both local charges exactly once before removeResultFromEgraphLocked deletes the map entry.
  7. A full e-graph reset or failed partial import calls the same unpublish helper for every mapped result before discarding maps. It then asserts that the atomic total is zero. It must not reset the total while any result still names the cache as owner.

The combined lock order is egraphMu → sessionMu when a session check is needed, then metadataMu → resultCallMu/payloadMu. Paths without a session check go directly from egraphMu to metadataMu. Detached frame stores start at metadataMu. No result lock may acquire egraphMu or sessionMu. metadataMu decides races: a replacement that wins before unpublication contributes to the total and to the final subtraction; a replacement that wins afterward remains local and uncharged.

EstimatedMetadataBytes reads the three graph lengths under egraphMu.RLock, loads the atomic variable-byte total, and uses saturating arithmetic for the final sum. The variable total itself uses exact checked deltas. A concurrent replacement can make one sample contain a bounded before/after mix, but publication and removal cannot leak a permanent charge. The five-second poll reads it again.

Accuracy and alternatives

Known string and byte-backed values are exact in logical bytes. Fixed object and slot costs remain estimates. Unmodeled memory includes map bucket slack, allocator fragmentation, arbitrary payloads without CacheMetadataSizer, Module schema state, and unrelated engine allocations. On metadata-dominated calibration fixtures, the proposed engineering check is a post-GC estimate delta between 0.5 and 2 times the cache-owned HeapAlloc delta. Module-heavy process heap may be 3-10 times the estimate because pruning roots can indirectly release excluded pools.

  • A persisted-root count misses transitive dependencies, terms, stale classes, and large arguments.
  • A live-result count misses term and class growth.
  • Exact retained-heap attribution would require expensive shared-closure and arbitrary-object analysis on a frequent control path.
  • A Go heap trigger cannot distinguish reclaimable cache state from active sessions or unrelated allocations.

5. Trigger and pass execution

Configuration and trigger times

type GCMetadataConfig struct {
    MaxBytes    *DiskSpace `json:"maxBytes,omitempty"`
    TargetBytes *DiskSpace `json:"targetBytes,omitempty"`
}

// in GCConfig
Metadata *GCMetadataConfig `json:"metadata,omitempty"`

Reuse DiskSpace only for absolute-byte parsing. Reject percentages because there is no metadata-capacity denominator. Require 0 < targetBytes < maxBytes. Omitted values use a finite production pair. Section 9 leaves the choice between 256/192 MiB and 512/384 MiB to Erik after canary measurements. gc.enabled: false disables both disk and graph GC. An operator can set a very large maximum to make graph pruning effectively dormant without disabling disk GC.

Generalize the five-second disk monitor into a GC monitor. Each tick reads the O(1) graph estimate before doing any graph traversal. It starts PruneMetadata only when the estimate is greater than maxBytes. Once started, the pass aims for targetBytes. Concurrent insertions and the poll interval can overshoot the maximum; this is not an allocator limit.

The existing one-second startup GC, session-completion request, and graceful-stop GC perform the same comparison. The existing server GC lock serializes disk and graph passes.

gcLocked must compute and act on the graph estimate even when disk.GetDiskStat fails. It logs that error and skips or defers only disk policies that need new CurrentFreeSpace. The five-second monitor also checks the graph estimate independently of the disk-stat result. Remove the current no-worker-policy early return when graph GC is enabled.

If a pass exhausts candidates above target because protected roots retain the graph, save the blocked byte count and the estimate sampled when suppression begins. Let retryGrowth be the larger of 5% of that saved estimate and 16 MiB. Suppress ticker retries until the current estimate is at least the saved estimate plus retryGrowth, or until a session closes. Startup, explicit calls, and session completion bypass suppression.

Execution order

  1. Read the estimate. Return with no allocation when it does not exceed maxBytes.
  2. When it exceeds maxBytes, take one egraphMu write hold and run a forced equivalence-class liveness check before selecting a root. Release the lock, then remeasure. Stop if the result is at or below targetBytes; otherwise continue toward the target even if compaction moved it below the maximum.
  3. Take a new egraphMu hold to snapshot and mark protected closures. While holding it, take sessionMu only long enough to read the active session roots, then release sessionMu. Mark the dependency closure of those roots and every unpruneable root, then release egraphMu. A closure means the root plus every result reachable through dependency edges. Use one generation field on sharedResult and an 8-byte result-ID queue. Drop the queue reference after marking. Peak-memory tests still count its backing array because no forced GC runs between phases.
  4. Take a separate egraphMu hold and scan persistedEdgesByResult once. Exclude every result marked in the protected generation. Store each remaining candidate in a 32-byte record containing result ID, last-use time, creation time, an expired flag, and whether snapshotOwnerLinks is non-empty. Read the snapshot flag without cloning the link slice. Release egraphMu after building the vector.
  5. Sort the vector with no cache lock held. Sort in this order: expired before unexpired; older last-use hour bucket first; no snapshot owners before snapshot owners inside one hour bucket; then exact last use, creation time, and result ID. There is no metadata KeepDuration. Snapshot-owning roots remain eligible, but the cheap existing flag delays destruction of large snapshot and recomputation state. This pass does not call measureAllResultSizes.
  6. Before each cut, take payloadMu, reread lastUsedAtUnixNano, and release it. Skip a result touched after the pass began. Then call removePersistedEdgeIfMetadataEligible. The helper takes a short egraphMu → sessionMu hold, verifies that the persisted edge still exists, that the result is not directly unpruneable, and that no session directly owns it, and runs locked edge removal and cascading collection. It releases both locks before invoking any collected OnRelease callbacks.
  7. Continue after a cut that immediately changes the estimate by zero. Several persisted roots can own one shared closure, so the last ownership cut can release most of the graph.
  8. After modeled non-class removals reach 16 MiB, take a separate egraphMu write hold, force compaction, and release the lock before rereading the estimate. Repeat with a new lock hold at geometric thresholds of 32 MiB, 64 MiB, and so on. Compute these deltas from successive O(1) samples with the class term excluded; do not assign a retained closure cost to a root. Perform end compaction under one final separate write hold. Stop when the post-compaction estimate is at or below target, candidates are exhausted, or the context is cancelled.
  9. Perform one additional candidate scan only when the final sample proves that concurrent additions or stale candidate state left removable results above target. Otherwise report the remaining protected bytes and activate retry suppression.

The one-million-result benchmark applies the 500 ms single-write-hold gate separately to initial compaction, protected-closure marking, candidate-vector construction, every cut, and every later compaction. If closure marking or candidate construction exceeds that gate, implementation must stop before shipping and receive a reviewed bounded or chunked scan design with revalidation rules. This document does not pre-authorize an unspecified chunking change.

For a small example, suppose 10,000 persisted scalar roots report zero physical bytes but contribute more than 30 MiB through the result, term, class, and variable-byte terms. A 24 MiB maximum and 18 MiB target starts this pass without a disk target. The pass compacts stale class slots, removes the oldest persisted edges, and lets collectUnownedResultsLocked release dependencies. It stops only after the estimate is at most 18 MiB or protected roots prevent further removal. Reported physical bytes can remain zero.

Concurrent ownership changes

The pass-start closure is a planning snapshot. It is not an atomic promise for the entire pass. A session or unpruneable root added during the pass can cause a dependency's persisted edge to be removed after planning. The direct session and unpruneable checks occur at the cut. Existing incoming ownership prevents a result or dependency already acquired by that session or root from being collected. A post-start touch also causes a skip when the freshness recheck observes it. The design does not claim an atomic revalidation of the full dependency closure.

The snapshot-owner ordering is a value tradeoff, not a safety rule. If older snapshotless roots cannot reach target, the pass can remove a snapshot-owning root and release substantial disk or recomputation state for a small estimated-byte reduction. The pass accepts that consequence so zero-disk results cannot grow without a bound. It avoids physical measurement by using only the existing owner-link presence bit.

6. Required equivalence-class compaction

Change compactEqClassesLocked() to compactEqClassesLocked(force bool). Disk pruning passes false and keeps the current two-times rule. A graph-estimate pass passes true. Forced mode performs the liveness walk and rebuilds whenever oldSlots > liveSlots, even below two-times sparsity.

Keep maybeResetEgraphLocked's existing empty-graph reset. Forced compaction applies only when live terms remain.

This change is required because allocated class slots are part of the estimate and removeResultFromEgraphLocked does not delete them. A separate removed-result counter is unnecessary and unsafe: the current sparsity guard can decline a rebuild, leaving unclear debt. With allocated length as the charge, a declined or no-op compaction changes no counter. A successful compaction lowers len(egraphParents) directly.

The current compactor holds a live-root hash map, a sorted root slice, a remap map, and replacement indexes together at dagql/cache_egraph.go:1777-1914. Replace the live-root and remap maps with dense mark and remap arrays indexed by class ID. Scan IDs in ascending order instead of sorting roots. Stage replacement indexes so temporary structures do not all peak together. Keep the final remap commit atomic under egraphMu. Do not invoke runtime.GC inside the pass.

Measure peak HeapInuse and RSS during compaction, not only after a forced GC. The max-to-target difference is not free memory before compaction, especially while loading an old large graph. At one million results, the closure queue backing array, candidate vector, and live compaction scratch must fit the selected gap: 64 MiB for the 256/192 arm or 128 MiB for the 512/384 arm. If they do not, reduce scratch or widen the gap before selecting defaults.

Do not rebuild unrelated top-level maps initially. The supplied churn run dropped from 198.7 MiB to 56.6 MiB with current class compaction, and later floors remained around 5-7% of peak. Bounding peak live cardinality also bounds that bucket floor. Add wider map rebuilding only as a separately reviewed follow-up if ten churn/compaction cycles exceed the retained-floor acceptance test in section 8.

7. Unchanged disk path, persistence, and reporting

Disk policies

Keep Cache.Prune, CachePrunePolicy, physical measurement, policy ordering, simulation, and physical-byte reports unchanged. Policy N+1 must continue to snapshot ownership after policy N. Do not reuse one snapshot across policies.

When both controllers need work, the server runs the existing disk policies first. It then rereads the graph estimate and starts PruneMetadata only if still required. A disk cut can make the second pass unnecessary. No code converts reclaimed physical bytes into estimated graph bytes or converts one target to the other.

Persistence and restart

Keep cachePersistenceSchemaVersion at 17. The record format does not change, and no estimate counter is persisted. Version-17 import rebuilds local call charges and raw envelope charges, then publishes every result through the same registered-result helper. Eager or later lazy decoding replaces the retained-envelope charge with the decoded charge.

The existing startup sequence imports the entire legacy graph before the one-second GC runs. A legacy graph above the new maximum is therefore resident during import and for that delay. Preserve that transient and benchmark it. Do not bump the schema and do not add a pre-import reset: the current mismatch path deletes worker snapshots and content as well as the SQLite mirror.

Graceful shutdown evaluates the graph estimate and prunes before the persistence worker snapshots the graph. Unclean persistence remains subject to the existing rejection rules.

Focused correctness tests

  • Estimate: construct known result, term, class, frame, and payload counts and assert the formula. Random concurrent publication, import, frame replacement, payload replacement, removal, reset, and failed-import sequences must equal a full test-only recomputation.
  • Registered ownership: assert idempotent publication, exactly-once unpublication, zero after reset, and no charge from detached results or the persistence worker's temporary result. Race a registered frame replacement and lazy payload swap against removal.
  • Large variable values: persist 1-10 MiB plain and digested call arguments, String, wrapped scalar, JSON, and JSONValue. Verify logical lengths without serialization and automatic removal with zero physical use.
  • Version-17 import: restart with a multi-megabyte cold JSONValue object and a nested list containing object and scalar envelopes. Verify raw ObjectJSON/ScalarJSON charges before materialization, one replacement delta afterward, no snapshot/content deletion, and eventual startup trim.
  • Zero and tiny disk: create thousands of persisted scalar and no-match glob roots. Verify that disk pruning has no target, the graph estimate crosses a small test maximum, and the new pass reaches its target with near-zero physical reclaim.
  • Compaction first: build a graph with dead class slots below the current two-times ratio. Verify forced compaction occurs before any persisted edge is removed. If compaction reaches target, verify zero evictions. Verify lookup remains correct.
  • Ownership races: exclude pass-start active and unpruneable closures. Verify direct session/unpruneable membership and observed post-start touches skip a cut. Verify a dependency acquired during the pass remains alive through incoming ownership even if its persisted edge is removed.
  • Ranking: verify expired roots first, then age bucket, snapshotless preference, exact age, creation time, and ID. Verify snapshot-owning roots remain eligible and no KeepDuration blocks the target.
  • Independent disk state: keep existing disk-only tests unchanged. Verify a graph-only pass never calls physical sizing. Inject disk.GetDiskStat failure in engine/server/gc_test.go and verify both the monitor and gcLocked still run an over-budget graph pass.
  • Combined run: trigger both controllers. Verify disk policy N+1 still sees post-policy-N ownership, the graph estimate is reread after disk pruning, no root is removed twice, and reports retain separate units.
  • Output bound: prune 400,000 roots. Verify at most 20 total details, O(number of compactions) summaries, no unsampled frame clone or digest derivation, and snapshot GC after any root removal.

Scale benchmarks and proposed engineering gates

  • At one million live results, a below-maximum poll must be O(1) and allocate zero bytes.
  • An over-maximum pass performs one candidate scan and at most one evidence-triggered rescan. It performs no more than 2 + ceil(log2(max(1, initialExcess / 16 MiB))) compactions.
  • The closure queue uses 8 bytes per visited result. Its reference is dropped before the 32-byte-per-eligible-root candidate vector, but the peak calculation includes both backing stores plus compaction scratch. The total must fit the chosen max-to-target gap.
  • On the recorded benchmark host, no single write-lock hold may exceed 500 ms and the complete one-million-result pass must finish within 60 seconds. Record the host, result count, slots, roots per second, scans, compactions, and peak scratch.
  • Across ten 200,000-result churn and class-compaction cycles, the retained floor must remain below 15% of the configured maximum and grow by less than 2% of that maximum per cycle. Failing this gate triggers a separate design review for wider map rebuilding.
  • Measure a large version-17 import from process start through the one-second trim. Record peak HeapInuse, RSS, import time, trim time, and final estimate. The final estimate must reach target unless the report identifies protected bytes.
  • Re-run the three representative metadata workloads after a forced Go GC. The estimate delta should remain between 0.5 and 2 times the cache-owned HeapAlloc delta. Re-run the 11,003-glob case and require automatic reduction of result and class counts with near-zero physical reclaim.

9. Migration and Erik's decision

There is no persistence-format hard cut or wholesale cache wipe. Existing version-17 state imports. The new process derives its estimate from the loaded graph and retained envelopes. It can temporarily load an oversized legacy graph before the startup pass. This is nevertheless an intentional retention-policy change: on first startup after upgrade, a version-17 graph above the selected maximum can lose cold persisted roots until it reaches the target. Later use recomputes those results. The large-import benchmark makes both the transient and the first-startup eviction consequence explicit.

Unresolved: current evidence does not choose a finite production default between 256 MiB maximum / 192 MiB target and 512 MiB maximum / 384 MiB target. Run canary arms with both pairs. Collect the per-engine estimate distribution, RSS-to-estimate multiplier, time above maximum, pass frequency and duty, roots removed, protected bytes, compaction and total-pass pauses, peak scratch, cache hits, and recomputation latency. Erik must choose the production pair from the observed memory-headroom and recomputation tradeoff. This document sets no numerical launch SLO. Shipping with no finite default would preserve the observed zero-disk retention defect.
