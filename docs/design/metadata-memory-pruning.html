Metadata-memory-aware DAGQL cache pruning

Council revision 1 design and implementation plan. Code baseline: upstream/main@1c6e07b197327c57e9db8584deb36e5166278677, 3 August 2026. The brief's b1c2c81 is an ancestor; the intervening version commits do not change the scoped cache, persistence, GC, configuration, or snapshot code.

Decision. Add a finite, independent budget in estimated DAGQL metadata bytes. Maintain its estimate incrementally, trigger it independently of physical disk usage, and evict persisted roots in bounded batches until the post-compaction estimate reaches a target. Disk and metadata pruning share protection, ranking, edge removal, cascading collection, and lifecycle hooks, but never mix byte units or require disk measurement for a metadata-only pass.

1. Problem and boundaries

Persisted DAGQL results can retain result objects, calls, dependency edges, e-graph terms and equivalence classes, digests, and indexes while owning no measurable snapshot bytes. Current automatic pruning asks only whether physical cache use exceeds a disk threshold. A cache made mostly of scalar or metadata-only results therefore has no reclaim target and can grow until process restart or an explicit prune-all. TTL affects lookup and candidate preference only after pruning has started; it is not a trigger.

The required outcome is: a sustained population of zero-disk or tiny-disk persisted roots must itself cross a finite pressure threshold, lose cold persisted edges, cascade through now-unowned dependencies, compact the metadata structures that retained those results, and stop below a lower target without harming active or permanent roots.

Non-goals: exact retained-heap attribution; a general Go heap controller or GOMEMLIMIT; Module SchemaBuilder eviction; content-hash or recipe redesign; release-specific dependency/recipe fixes; paging metadata to disk; generic snapshot GC changes; arbitrary object/payload introspection beyond known byte-backed scalars; security or multi-user policy; and broad metrics or public GraphQL cache APIs. Snapshot/e-graph work is included only where deleting cache ownership would otherwise fail to lower the new estimate materially.

3. Proposed system

3.1 One independent estimated-metadata-byte budget

Add Cache.EstimatedMetadataBytes(). Its unit is an explicitly approximate byte estimate for cache-owned DAGQL graph metadata, not RSS, HeapAlloc, physical cache bytes, or exact retained closure size:

estimated =
    3,072 * len(resultsByID)
  +   512 * len(egraphTerms)
  + 1,024 * max(0, len(egraphParents) - 1)
  + logicalVariableBytes

The three cardinalities already exist and are O(1) under egraphMu; there are no per-edge, per-membership, digest, or map-capacity counters. The starting weights fit the supplied calibration: live entries cost about 3.1–5.5 KiB, while the 200,000-result churn retained about 994 B per peak result after result release but before class compaction. The allocated class-slot term deliberately includes records not yet proven dead and drops only when compactEqClassesLocked commits a shorter egraphParents. This is the cheap retained charge that makes churn trigger compaction without a fragile deletion-debt counter.

logicalVariableBytes is one maintained aggregate for variable content that fixed weights cannot bound:

  • Result calls: a DAG-aware walk counts the byte lengths of all string-bearing ResultCall, type, module, argument, literal, effect, view, and digest fields, including both StringValue and DigestedStringValue. It visits each distinct *ResultCall once per installed root frame and never follows the runtime ResultCallRef.shared pointer. Shared subframes reached from two owning root frames are conservatively charged twice; within one frame DAG they are charged once. It does not serialize a frame.
  • Result payloads: a narrow CacheMetadataSizer reports logical bytes without serialization. dagql.String reports len, Scalar[T] delegates to its wrapped value, and core.JSON/JSONValue report byte lengths. An imported lazy scalar charges the retained ScalarJSON bytes; materialization atomically replaces that charge with the decoded value's charge.

dagql/cache_metadata.go holds only an atomic.Int64 aggregate for variable bytes and saturating arithmetic for the formula. storeResultCall computes the new DAG-aware size before taking resultCallMu, swaps the frame and cached per-result size under that mutex, then atomically applies the delta. Result publication installs payload size when the result enters resultsByID; lazy import/materialization updates it under payloadMu; removeResultFromEgraphLocked subtracts both cached variable charges before unlinking the result. A pressure read takes egraphMu.RLock for the three lengths and loads the atomic variable total. Concurrent replacement can give one read a bounded before/after skew but cannot lose a delta; the five-second monitor rechecks.

On metadata-dominated calibration workloads, after a forced Go GC, estimate deltas must remain between 0.5× and 2× observed cache-owned HeapAlloc deltas. Large supported call arguments and byte-backed scalar results are exact in logical bytes. Unmodeled terms include fixed slot/index variation, Go map bucket slack, arbitrary object payloads without the opt-in interface, allocator fragmentation, Module schema state, and unrelated engine memory. Module-heavy real heap can be roughly 3–10× the estimate because excluded module servers and pools are released indirectly when roots disappear; the supplied 378 MiB workload reportedly had only about 35 MiB of modeled graph metadata.

This representation is preferable to:

  • Persisted-root count: misses a root's dependency closure and a shared result's expanding e-graph.
  • Live-result count alone: misses term/class growth, stale allocated class slots, and multi-megabyte supported strings.
  • Exact retained-heap attribution: shared closures are non-additive, arbitrary values are opaque, and whole-heap profiling is too expensive and noisy for a five-second control loop.
  • Runtime heap pressure: cannot distinguish cache-owned reclaimable metadata from active sessions or unrelated engine allocations.

3.2 Configuration and trigger

Extend engine/config.GCConfig with one section:

"gc": {
  "metadata": { "maxBytes": "256MB", "targetBytes": "192MB" }
}
type GCMetadataConfig struct {
    MaxBytes    *DiskSpace `json:"maxBytes,omitempty"`
    TargetBytes *DiskSpace `json:"targetBytes,omitempty"`
}

// in GCConfig
Metadata *GCMetadataConfig `json:"metadata,omitempty"`

Use the existing DiskSpace absolute-byte parser but reject percentages for these fields: a percentage needs a nonexistent metadata capacity denominator. Pointer fields distinguish omission from an explicit invalid zero. Omitted fields default to 256 MiB maximum and 192 MiB target; require 0 < targetBytes < maxBytes. Existing gc.enabled: false disables both disk and metadata GC. There is no second disable switch: the default must be finite or metadata-only roots can again live indefinitely. Operators who deliberately want an effective metadata off-switch can configure a very large maximum without disabling disk GC.

Generalize the server's five-second disk monitor into a GC-pressure monitor. It independently reads disk free space and the O(1) metadata estimate. A metadata pass starts when the estimate exceeds maxBytes; the desired post-pass value is targetBytes. The existing one-second startup GC, session-completion GC, explicit GC serialization, and graceful-stop GC evaluate the same condition. This is an operational budget, not an allocator limit: concurrent mutations and the polling interval allow bounded overshoot.

Metadata pressure must not inherit disk availability as a prerequisite. gcLocked evaluates and runs metadata compaction/pruning even when disk.GetDiskStat fails; it logs the disk error and omits or defers only disk policies that require refreshed CurrentFreeSpace. The monitor likewise checks metadata before/independently of the disk-stat call, so a disk-stat error cannot suppress an over-budget metadata signal.

If a pass cannot reach target because all remaining roots are active, unpruneable, or share protected ownership, record the blocked amount and suppress ticker retries until either the estimate grows by the larger of 5% or 16 MiB, or a session closes. Startup, explicit prune, and session completion bypass suppression. This prevents an unfreeable graph from causing a full traversal every five seconds.

3.3 Candidate selection and collection

  1. Evaluate disk and metadata pressure before physical measurement or graph traversal. A metadata-only run never calls measureAllResultSizes.
  2. On every metadata-triggered pass, unconditionally run the forced class-liveness check, then remeasure before selecting a root. If that lowers the estimate below maxBytes, stop. The condition cannot be “capacity caused pressure”: dead class records still look like allocated structural records until the O(N) liveness walk.
  3. At pass start, mark dependency closures from current session roots and current unpruneable roots. Persisted roots in either marked closure are excluded from this plan.
  4. Scan persistedEdgesByResult once into a compact []metadataPruneCandidate containing only result ID, last-use time, creation time, and expiry/snapshot flags: 32 bytes per eligible persisted root. Sort once by expired TTL first; oldest-use hour bucket; roots without snapshotOwnerLinks before snapshot-owning roots in that bucket; then exact last use, creation, and stable result ID. The snapshot bit is existing evidence of higher disk/recomputation value and steers pure metadata pressure toward on-mandate roots without making snapshots unpruneable. There is no KeepDuration barrier and no physical size measurement.
  5. Before each cut, read lastUsedAtUnixNano under payloadMu and skip results touched after passStartedAt. Then removePersistedEdgeIfMetadataEligible acquires the existing egraphMu→sessionMu order and atomically rechecks that the edge exists, is not directly unpruneable, and has no direct session membership before calling the normal locked edge-removal/cascade path. Existing incoming ownership and collectUnownedResultsLocked perform exact collection and result/snapshot release. Continue through zero-immediate-delta cuts: several shared roots may have to lose ownership before their common closure is freed.
  6. Read the O(1) estimate after cuts. Force class compaction when modeled non-class cost removed since the prior check crosses geometrically increasing thresholds (16 MiB, then 32 MiB, 64 MiB, and so on), and once at pass end. Stop only after post-compaction estimate is at/below target, candidates are exhausted, or the context is cancelled. Re-scan once only if the final check demonstrates shortfall from concurrent additions/drift; otherwise report protected/no-progress pressure.

The closure walk uses a generation mark on sharedResult plus an 8-byte result-ID queue, not a map or cloned pruneSnapshotResult. Release that queue before allocating the 32-byte/root candidate vector. The pass performs one candidate scan/sort and at most one demonstrated-drift retry, not a full rescan per fixed batch. It never clones call frames, descriptions, dependency maps, or physical-usage entries.

The pass-start closure is a planning snapshot, not an atomic promise. A session or unpruneable root acquired mid-pass can cause a dependency's persisted edge to be demoted after planning. Direct membership and freshness are rechecked at cut linearization, while incoming ownership guarantees that a newly protected result/dependency is not collected. Session close forces a later retry after protection shrinks.

Disk policies retain their current Cache.Prune entry point, per-policy physical measurement/simulation, order, and reports. The server applies a triggered disk pass first, then rereads metadata pressure and invokes the metadata controller on remaining roots. The two paths share active/unpruneable eligibility helpers, edge removal, cascading collection, and snapshot lifecycle, but not target calculation or planner state. This deliberately avoids changing later disk-policy snapshots inside a metadata feature. A disk cut can incidentally satisfy the metadata controller, but reclaimed physical bytes are never added to estimated metadata bytes and neither target is converted into the other's unit.

3.4 Compaction is part of success, not a side project

Change compactEqClassesLocked() to compactEqClassesLocked(force bool). Disk-only pruning keeps the existing 2× sparsity heuristic. Metadata pressure always performs the liveness walk and rebuilds whenever oldSlots > liveSlots, bypassing 2×. If the heuristic declines or the forced walk finds no dead slots, structural lengths do not change; there is no separate debt to clear. The committed shorter egraphParents is the accounting change.

Current compactEqClassesLocked holds a live-root hash map, sorted root slice, remap map, and replacement indexes together (dagql/cache_egraph.go:1777-1914). Replace live-root/remap hashes with dense mark/remap arrays indexed by class ID where benchmarks show a lower peak, and stage temporary structures without calling runtime.GC; the equivalence-class remap remains atomic under egraphMu. Compaction is O(N), so start/end plus geometric removed-cost checks bound a pass to O(log initial excess) compactions.

Do not add broad top-level map rebuilding in this feature. The supplied 200,000-result profile fell from about 198.7 MiB after release to 56.6 MiB after current class compaction; later floors of 72–76 MiB were only about 5–7% of the roughly 1.05 GiB peak and become bounded when peak live cardinality is budgeted. Stage wider rebuilding only if a ten-cycle retained-floor benchmark after class compaction exceeds 15% of the configured maximum or grows by more than 2% of that maximum per cycle.

At one million results, require no individual write-lock hold above 500 ms and total live auxiliary HeapInuse/RSS across the retained candidate vector plus compaction scratch at or below the selected max→target gap (provisionally 64 MiB). The gap is not guaranteed free memory when compaction starts, especially on first legacy import; it is only a steady-state design bound. If the benchmark exceeds either limit, reduce scratch or widen the configured gap before choosing defaults.

3.5 Lifecycle interactions

ConcernRequired behavior
Active sessionsExclude the pass-start closure; recheck direct membership and last-use freshness at cut. A closure acquired mid-pass can still lose persistence, but incoming session ownership prevents collection. Session close forces a retry after protection shrinks.
Persisted roots and shared closuresOnly persisted edges are eviction decisions. Exact incoming ownership decides what becomes unreachable. No root receives an additive share of a common closure; actual estimate is checked at geometric compaction points and pass end.
Unpruneable rootsExclude pass-start closures and directly recheck the candidate edge's flag. A dependency newly protected mid-pass can lose persistence but cannot be collected because incoming ownership remains. If protected state alone exceeds target, report blocked pressure.
TTL and ageExpired entries remain usable only according to existing lookup semantics and rank first under pressure. TTL does not add a timer or trigger below budget. Age is a value proxy, not a hard retention promise.
Snapshots and leasesNormal result collection runs OnRelease and removes leases. Existing snapshot GC still runs only after at least one persisted edge was removed; capacity-only compaction does not invoke it.
Disk pruningIndependent pressure and target, shared eligibility/removal lifecycle. Metadata-only passes skip physical measurement; disk reports keep physical-byte semantics.
Graceful persistence and restartGraceful stop evaluates metadata pressure before the persistence worker snapshots the remaining graph. 5. Tests, benchmarks, and acceptance

  • Coarse estimator: direct fixtures assert the formula from len(resultsByID), len(egraphTerms), allocated class slots, and logical variable bytes. Random publication/import/replacement/removal sequences keep the sole variable-byte counter equal to a full test recomputation; dependency/digest membership changes require no hooks.
  • Large variable content: one persisted 1–10 MiB plain/digested call argument and persisted String, wrapped module scalar, JSON, and JSONValue results charge logical byte lengths without serialization, cross a small budget without disk use, and are reclaimed. Shared subframe DAGs terminate and follow the stated dedup rule.
  • Zero/tiny disk: thousands of persistable scalar and no-match glob roots produce no disk target but cross a small test metadata maximum; the five-second/startup/session trigger automatically cuts persisted roots and reaches target. Physical reclaim may remain zero.
  • E-graph growth: many equivalent recipes taught to one result grow term and allocated-class components. A pass over a below-2× sparse graph force-compacts before cutting any persisted edge and lowers the class component/benchmark heap; a compact-first success performs zero evictions.
  • Ownership/races: pass-start active and unpruneable closures are excluded; direct session/unpruneable membership and post-start touches skip at cut. A closure acquired concurrently may lose persistence but remains collection-proof through incoming ownership. Shared zero-delta cuts, lease release, and cascading collection retain current behavior.
  • Ranking: expired before unexpired; then deterministic age bucket, snapshotless preference, exact LRU/creation/ID. Snapshot-owning roots remain eligible when needed. No metadata KeepDuration blocks target. Active/unpruneable candidates never appear.
  • Combined pressure: disk-only tests are unchanged; metadata-only never invokes physical size measurement; simultaneous pressure never removes one root twice and reports both units independently.
  • Disk-stat failure: inject disk.GetDiskStat failure in engine/server/gc_test.go; an over-budget metadata pass still compacts/prunes, while only disk policy execution is skipped/deferred. The pressure monitor still schedules metadata GC.
  • Persistence: a large version-17 restart reconstructs the same estimate without resetting worker snapshots/content. Measure peak import HeapInuse/RSS through the one-second startup trim and require eventual target; graceful shutdown persists only the post-GC graph.
  • Scale/complexity: at one million live results, a below-pressure poll is O(1)/zero allocation. A pressured pass performs one candidate scan and at most one drift retry; compactions are bounded by 2 + ceil(log2(max(1, initialExcess/16MiB))). Closure scratch is 8 bytes/result and released before the 32-byte/eligible-root candidate vector; candidate plus compaction peak HeapInuse/RSS fits the selected max→target gap. No write-lock hold exceeds 500 ms and the entire one-million-result pass completes within 60 s on the benchmark host. Record host and roots/sec. The supplied ~23 ms 400K-slot compaction and ~5.7 s 200K full prune are calibration observations, not guarantees.
  • Retained floor: ten churn/class-compaction cycles stay below 15% of configured max and grow less than 2% of max per cycle; otherwise broad map rebuilding becomes a separately justified follow-up.
  • Mass-prune output: a 400,000-root metadata cut emits O(compactions) bounded summaries, at most 20 total details including skips, and a bounded report. Assert unsampled roots do not clone frames/derive digests and snapshot GC still runs after cuts.
  • Calibration: on the three supplied representative workloads, controlled post-GC estimate deltas stay in the 0.5×–2× HeapAlloc band. Re-run the 11,003-glob case and require automatic post-compaction estimate ≤ target, materially lower result/e-graph counts, and near-zero physical reclaim.

Place focused cases beside existing coverage in dagql/cache_test.go/cache_prune_test.go, dagql/cache_persistence_import_test.go, dagql/cache_persistence_worker_test.go, engine/server/gc_test.go, engine/config/load_test.go, and core/integration/localcache_test.go. Do not gate this feature on broad engine benchmarks or unrelated module-memory fixes.

6. Migration and one unresolved decision

There is no persistence-format migration or hard cut. Existing version-17 graceful state imports normally, logical variable bytes are reconstructed from it, and the existing one-second startup GC then compacts/evicts. An oversized legacy graph is therefore fully resident during import and for that startup delay; the large-import benchmark measures this migration transient. That exposure is preferable to bumping the schema, because the current mismatch path deletes the entire worker snapshot/content cache as well as DAGQL metadata. Unclean snapshots are already rejected by existing logic. No estimator aggregate is persisted.

Genuine unresolved decision: the mechanism requires a finite default, but current evidence does not choose 256/192 MiB over 512/384 MiB. Use 256/192 as the provisional implementation default. A canary compares both and ships the smallest pair for which at least 99% of steady-state engines remain below maximum without pruning, metadata-GC duty stays below 1%, p95 post-prune recomputation latency regresses less than 5%, and measured compaction scratch fits the max→target gap; otherwise choose 512/384 and retain the same controller. Also record RSS/estimate distribution, because module-heavy real heap may be 3–10× the estimate. The budget affects the supplied 378→58 MiB module case only indirectly—the modeled metadata there was reportedly about 35 MiB—and no 0.5–2× RSS claim applies. Shipping disabled-by-default is rejected because it preserves the defect.
