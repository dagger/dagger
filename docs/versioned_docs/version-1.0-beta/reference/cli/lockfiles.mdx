Dagger automatically records the exact results of supported symbolic lookups in `dagger.lock`. Later runs reuse those recorded results, making container image and Git lookups reproducible.

Locking is enabled by default. Missing entries are resolved normally and written to the lockfile; existing entries are reused.

## Lockfile format

New lockfiles use format version 2. Each non-empty file starts with a version header followed by one JSON tuple per lookup:

```json
[["version","2"]]
["","oci-latest",["docker.io/library/alpine"],"3.22.1"]
["","oci-sha",["docker.io/library/alpine:3.22.1"],"sha256:..."]
```

Each entry contains, in order:

1. namespace
2. operation
3. required positional inputs, encoded as an array
4. resolved string value
5. optional named inputs, encoded as key-value pairs when present

For example, non-default transport options are appended after the value:

```json
["","oci-latest",["registry.example/acme/image"],"2.0.0",[["protocol","http"]]]
```

The options array is omitted when every option has its default value. Option
pairs are sorted by name so equivalent lookups have one canonical identity.

Entries are ordered deterministically by namespace, operation, and inputs.

### Version compatibility

Dagger only reads and writes version 2 lockfiles. Version 1 lockfiles are
rejected and must be regenerated. Version 2 does not store policies: every
recorded result is pinned until explicitly updated.

Clients using an API view from before pinned-by-default locking ignore the
lockfile entirely. They neither read nor write it, even when run by a newer
engine. This prevents an older module from silently acquiring new locking
semantics.

Unsupported lockfile versions are rejected instead of being interpreted with
potentially incompatible semantics.

## Updating lockfiles

Use `dagger update` to refresh entries already recorded in `dagger.lock`:

```bash
dagger update
```

The update uses the current environment ambient authentication. Run it somewhere that can authenticate to any private registries or repositories referenced by the lockfile.

Ordinary commands discover and record missing entries automatically. There is no separate lock mode to select.

## Lock-aware operations

These operations currently record and resolve lock entries:

| Operation | Required inputs | Optional inputs | Result |
| --- | --- | --- | --- |
| `oci-latest` | image name without a tag | `protocol`, `insecureSkipTLSVerify` | selected stable semantic-version tag, or `latest` |
| `oci-sha` | tagged image reference | `protocol`, `insecureSkipTLSVerify` | OCI digest |
| `git-latest` | remote URL | `tagPrefix` | selected stable semantic-version tag ref, or canonical remote HEAD branch ref |
| `git-sha` | remote URL, Git ref | none | commit SHA |

The latest operations select a mutable name but do not combine it with its
content pin. A bare image therefore records both `oci-latest` and `oci-sha`;
an unversioned Git dependency records both `git-latest` and `git-sha`.
Explicit image tags and Git refs only require their corresponding SHA
operation.

`tagPrefix` restricts Git release selection to monorepo tags under that path.
Registry transport options are
part of OCI lookup identity, but platform is not: `oci-sha` stores the digest
of the platform-independent root manifest or index.

`git.commit` is already pinned by its input and does not create a lock entry.
