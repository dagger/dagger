1. Decision and scope

A process inside a container can be the main client of a fresh session. The engine already creates a new peer daggerSession when a direct client sends a fresh ClientMetadata.SessionID. The missing product capability is a safe route from an opted-in exec or service to that top-level path. The existing nested route cannot negotiate a fresh session.

Recommend a DaggerNesting enum on execs and services which opt into Dagger access.

NESTED_CLIENT selects the current parent-session route.

INDEPENDENT_SESSIONS selects a fresh-session route on the same process listener.

One process receives one selected mode.

The capability creates ordinary peer sessions only in the first phase.

The first client in each peer is its main client.

Closing the peer uses the existing whole-session cleanup path.

Ordinary sessions and current same-session nesting remain unchanged.

Module function runtimes continue to join their caller's session.

Do not expose the raw engine socket or TCP listener as the product API. A raw engine transport can create a peer today, but it can also reach engine-wide detachable-session control routes. Those routes are handled before normal session lookup. The independent listener mode accepts only fresh ordinary sessions created through that listener.

This model is materially smaller than client-specific cache ownership when a process boundary is sufficient.

It does not release objects created by another client that remains in the long-lived parent session.

It does not solve per-module-call or per-callback lifetime inside one long-lived peer.

It therefore replaces the first-track proposal only where a whole peer session is the right lifetime boundary.

It defers, rather than disproves, client-specific ownership for finer same-session release.

2. Problem, target use case, constraints, and non-goals

Target use case

A long-running Dagger session may create many exec and service processes over weeks or months.

Those processes may call Dagger and may start further services or nested execs.

An explicitly selected process should be able to place its Dagger API work in a separate session.

Closing that peer should release its session state without closing the parent session.

Current problem

dagql.Cache.trackSessionResult records one root edge for each result first observed by a session.

dagql.Cache.ReleaseSession removes those edges only when the whole session ends.

A nested client currently uses its parent's SessionID.

Its objects therefore remain rooted by the long-running parent session.

The same session also keeps initialized nested daggerClient objects and their telemetry providers.

Required constraints

  • Keep existing session-level cache ownership.
  • Keep default same-session nesting.
  • Make independent-session selection explicit.
  • Do not force module function calls across a session boundary.
  • Do not depend on engine restart recovery.
  • Do not create a workflow database, distributed scheduler, or engine-HA design.
  • Do not pass Dagger object IDs across an independent-session boundary.
  • Do not give a nested process engine-wide session-management authority.

Non-goals

  • This design does not make persisted DagQL entries disappear synchronously.
  • It does not delete BuildKit cache records or cache-volume data at session close.
  • It does not persist live sessions or service processes across engine restart.
  • It does not add attachment or recovery to ordinary peer sessions.
  • It does not change application storage semantics.
  • It does not release the parent session's own roots while that session remains open.

3. Terms and invariants

TermDefinition in this document
Ordinary sessionA current attached-lifetime session. Its main client's last connection schedules whole-session teardown. It is not a P0 detachable session.
Parent sessionThe daggerSession that owns the exec or service process which receives a Dagger connection capability.
Nested-client listener modeThe current loopback route advertised through DAGGER_SESSION_PORT and DAGGER_SESSION_TOKEN. Its handler always substitutes the parent SessionID.
Independent-session listener modeThe same process-local listener shape with a different handler selected when the exec or service is created. It accepts fresh ordinary sessions and does not set a parent caller. It adds no listener-admission token.
Peer sessionA fresh top-level daggerSession in the same engine. It has a new SessionID. It is not stored as a child of the parent session.
Main clientThe first daggerClient created in a session. getOrInitClient fixes mainClientCallerID and creatorClientID from that client.

A peer session shares the engine's DagQL cache, BuildKit worker, content store, snapshotter, lease manager, network provider, and engine state root.

It owns a separate daggerSession, core.Services, resolver, registry auth source, client map, telemetry providers, session resources, container references, and cache roots.

Process containment does not create an engine parent-child session relationship.

Direct top-level connection

host or container SDK
        │
        ├── starts "dagger session"
        │
        └── engine/client.Connect
                ├── startEngine
                ├── create fresh SessionID, ClientID, and token
                ├── GET /sessionAttachables
                ├── start client attachable providers
                ├── subscribe to telemetry
                └── POST /init and /query
                         │
                         ▼
               engine/server.getOrInitClient
                         │
                         └── missing SessionID creates peer daggerSession
                                  └── first client is main client

engine/client/client.go: connect takes this path when DAGGER_SESSION_PORT is absent.

engine/client.Client.startSession upgrades engine.SessionAttachablesEndpoint and serves the normal main-client attachables.

internal/cmd/dagger/session.go: EngineSession exposes a local SDK listener only after withEngine has completed the engine connection.

Current nested connection

parent query
   │
   ├── core/container_exec.go or core/service.go
   │       creates nested ClientMetadata
   │       SessionID = parent SessionID
   │
   └── engine/engineutil.setupNestedClient
           ├── opens loopback listener in process network namespace
           ├── injects DAGGER_SESSION_PORT and DAGGER_SESSION_TOKEN
           └── every request calls ServeHTTPToNestedClient
                        │
                        ├── overwrites request identity with fixed metadata
                        ├── sets CallerClientID
                        ├── may set ModuleContext and FunctionCall
                        ├── clears detachable and observer roles
                        └── calls serveHTTPToClient
                                  │
                                  └── getOrInitClient(parent SessionID)

engine/server/session.go: ServeHTTPToNestedClient does not trust a request-supplied session identity.

setupNestedClient also injects DAGGER_ENGINE_NUM_CPU and copies the process's SSH-agent path and optional Dagger version into the fixed nested metadata.

nestedClientMetadataForRequest copies only request-shaping fields such as client version and workspace selection.

It keeps the executor-provided SessionID.

It clears DetachableSession, AttachSession, and AttachmentID.

It rejects every path recognized by isSessionControlPath.

The nested endpoint reaches the engine, but it reaches only the current session. A request may open /sessionAttachables through that listener. It still registers a client inside the fixed parent session. No request header can turn it into a fresh root session.

SDK precedence

sdk/go/engineconn.Get chooses an explicit connection first and DAGGER_SESSION_PORT second.

It chooses a local or downloaded CLI only after the nested environment check.

dagger.WithRunnerHost therefore does not override a nested route.

Python, TypeScript, Java, PHP, Rust, Elixir, and generated runtime clients use the same practical precedence.

A nested service cannot request a peer through current SDK configuration while the join environment is present.

Existing proof that a peer is possible inside a container

Normal local provisioning ultimately reaches the engine's Unix listeners, including /run/dagger/engine.sock and the BuildKit socket.

The containerized engine driver can expose its engine API over TCP, and the integration dev engine listens on port 1234.

A normal user service receives neither raw endpoint.

It receives only the loopback join listener created in its network namespace.

core/integration/engine_test.go: engineClientContainer gives a container a direct dev-engine service endpoint through _EXPERIMENTAL_DAGGER_RUNNER_HOST.

The CLI in that container creates top-level sessions.

Tests using this helper prove that a client inside a container can become main in a separate session.

This is a technical proof.

It is not a safe production endpoint for a nested process.

Why the raw engine route is too strong

engine/server/session.go: serveHTTPToClient handles session-control paths before getOrInitClient.

engine/server/session_control.go does not authenticate those paths to one existing session.

A process that can reach the raw transport can list, inspect, attach to, or terminate detachable sessions visible to that engine.

It can also create arbitrary top-level sessions.

Mutual TLS may protect a remote engine transport from outsiders.

It does not scope one authenticated transport holder to one process.

6. Recommended peer-session model

One existing listener with one selected mode

Keep the current per-process loopback listener created by engine/engineutil.setupNestedClient.

Generalize its internal configuration from “nested client present” to a DaggerNesting mode.

NESTED_CLIENT keeps the current ServeHTTPToNestedClient handler.

INDEPENDENT_SESSIONS installs a fresh-session handler on that same listener.

Each opted-in process has exactly one Dagger listener and one port.

The selected handler is fixed when the exec or service is created.

A request cannot switch modes.

Fresh peer requirement

engine/client.connect already generates a fresh SessionID and ClientID before it checks DAGGER_SESSION_PORT.

The current nested handler ignores that requested session identity and substitutes the executor-provided parent metadata.

The independent handler instead parses the normal client metadata.

A first request must name a SessionID that does not exist.

The server creates a normal ordinary daggerSession and records that the process listener claimed it.

Later requests may continue only a session and main-client tuple claimed by the same listener.

One independent listener may claim several peer sessions.

It may never join a parent, unrelated peer, or detachable session.

Main-client initialization

The independent handler does not set CallerClientID.

It does not supply ModuleContext, FunctionCall, or a host-service proxy.

getOrInitClient therefore treats the first client as main.

The main client must run normal startSession and serve its own attachables.

This requires a small client-side distinction even though endpoint selection is fixed by the exec's DaggerNesting value.

The current nested environment path skips startSession.

Language SDKs also connect directly to the inherited port instead of starting a local CLI.

INDEPENDENT_SESSIONS must route them through the normal CLI-backed main-client path without asking application code to choose another mode.

Its normal main-client providers originate in that process.

Ordinary lifetime and listener cleanup

Phase one accepts ordinary sessions only.

It rejects detachable, observer, attachment, and global session-control requests in the handler.

The main attachable connection keeps each peer alive.

Last main-client disconnect schedules the existing reapDaggerSession.

Process cleanup first marks the listener closing, rejects new claims, closes accepted connections, and terminates any claimed peers which ordinary disconnect has not reaped.

The listener path and ordinary disconnect path converge through existing session lifecycle state.

Claim tracking is needed for scoped reconnect and failure cleanup.

It is not a second public session-management API.

Process-local scope

A process with INDEPENDENT_SESSIONS may open one or several ordinary peer sessions.

Dagger does not classify the application's reason for opening them.

Each peer follows its own main-client connection lifetime.

Any child exec or service receives its own explicit DaggerNesting value when it is created.

7. Exact API, protocol, metadata, CLI, and SDK shape

Core GraphQL options

enum DaggerNesting {
  NESTED_CLIENT
  INDEPENDENT_SESSIONS
}

# Current parent-session behavior under the new API.
container.withExec(
  args: [...],
  daggerNesting: NESTED_CLIENT
)

# New independent-session behavior
container.withExec(
  args: [...],
  daggerNesting: INDEPENDENT_SESSIONS
)

container.asService(
  daggerNesting: INDEPENDENT_SESSIONS
)

# Deprecated compatibility path. Behavior is unchanged.
container.withExec(
  args: [...],
  experimentalPrivilegedNesting: true
)

Omitting both fields gives the process no Dagger connection capability.

NESTED_CLIENT selects the existing parent-session behavior.

INDEPENDENT_SESSIONS selects the new fresh-session behavior.

experimentalPrivilegedNesting remains supported with its exact current behavior and is deprecated in favor of daggerNesting: NESTED_CLIENT.

Setting the deprecated flag to true together with any daggerNesting value is an input error.

Application code does not make another selection when it connects.

Schema view

DaggerNesting and every new public daggerNesting argument are v1 API.

Install the complete enum with AfterVersion("v1.0.0-0").

Apply View(AfterVersion("v1.0.0-0")) to every new argument.

Do not gate the existing withExec, asService, terminal, or related fields themselves.

Pre-v1 views keep their current schema and continue to expose experimentalPrivilegedNesting.

V1 views expose the enum and new arguments and mark the legacy argument deprecated with “Use daggerNesting: NESTED_CLIENT.”

Where deprecation metadata is view-specific, define the unchanged legacy argument with BeforeVersion("v1.0.0-0") and the deprecated form with AfterVersion("v1.0.0-0").

Injected environment

# New nested-client API:
DAGGER_SESSION_PORT
DAGGER_SESSION_TOKEN
DAGGER_NESTING=NESTED_CLIENT

# New independent-session API:
DAGGER_SESSION_PORT
DAGGER_NESTING=INDEPENDENT_SESSIONS
# No inherited DAGGER_SESSION_TOKEN.

# Deprecated experimentalPrivilegedNesting compatibility path:
DAGGER_SESSION_PORT
DAGGER_SESSION_TOKEN
# DAGGER_NESTING is absent.

Nested-client mode keeps the existing port and token contract.

Independent-session mode injects only the listener port and mode marker.

The new enum is injected as DAGGER_NESTING.

The deprecated flag keeps the current environment byte-for-byte, so a missing marker continues to mean nested-client behavior.

The marker tells SDK provisioning and engine/client how to use the inherited endpoint.

It is not an application-selected connection option.

Independent mode does not authenticate admission with an inherited listener token.

The design does not treat another process in the same network namespace as a separate security principal.

SDK and CLI routing

No public SDK session-mode option is required.

No user-facing or hidden dagger session --session-mode flag is required.

When the marker is absent or NESTED_CLIENT, every SDK connects directly to the parent-session listener.

When the marker is INDEPENDENT_SESSIONS, an SDK must not use its direct environment-session shortcut.

It starts the normal local dagger session helper.

The helper inherits the port and DAGGER_NESTING value.

It generates its own fresh SessionID, ClientID, and ClientSecretToken exactly like an external main client.

engine/client.connect uses the inherited listener instead of calling startEngine, but otherwise follows the ordinary main-client path beginning with startSession.

Each SDK Connect call therefore creates one fresh peer.

Several calls from one process may create several peers through the same listener.

Generated module runtimes keep their current same-session behavior.

This proposal does not change module function execution or any process that does not explicitly select INDEPENDENT_SESSIONS.

internal/cmd/dagger/session.go: EngineSession continues to expose its local SDK listener only after attachables, telemetry subscription, and initialization succeed.

Its connect JSON may add the peer identity for application diagnostics:

{
  "port": 49152,
  "session_token": "...",
  "session_id": "..."
}

This session_token is generated by the normal local helper for its SDK listener.

It is not inherited from the containing process.

Existing SDK JSON decoders must tolerate the optional field.

The SDK does not need to expose it as a connection selector.

Scoped management

An ordinary peer is not attachable under P0.

dagger sessions list currently lists detachable sessions only.

Phase one does not change that command.

The process that opens a peer retains the SDK client handle and terminates the peer by closing that client.

Stopping the containing process also closes its peers.

Process-listener cleanup is the engine backstop.

No new public list, attach, or terminate API is required in phase one.

The process listener must not proxy the engine-wide /v1/sessions routes.

8. Detailed lifecycle and failure sequences

Opening and closing a peer

  1. A session creates an exec or service process with daggerNesting: INDEPENDENT_SESSIONS.
  2. The executor starts one independent-mode listener and injects its port plus DAGGER_NESTING=INDEPENDENT_SESSIONS.
  3. The process starts a normal SDK client.
  4. The SDK sees DAGGER_NESTING=INDEPENDENT_SESSIONS and starts its local dagger session helper instead of directly joining the inherited endpoint.
  5. The helper generates fresh client identities, runs startSession, and connects through the inherited listener.
  6. The engine atomically records the listener claim and creates peer session Q.
  7. The process is Q's main client and supplies Q's attachables.
  8. Queries through that client acquire Q's session roots.
  9. A later SDK Connect call from the same process may create another peer.
  10. Closing the SDK client closes Q's main connection.
  11. Q stops Q-owned services and runs Cache.ReleaseSession(Q).

Failure before a connected client handle exists

The CLI generates Q's SessionID before its first engine request.

The listener records its claim atomically with fresh-session publication.

The CLI does not publish local connect JSON until initialization succeeds.

If attachable upgrade, telemetry subscription, /init, or output fails, client cleanup closes the upgraded connection.

Process-listener cleanup terminates a claimed peer if ordinary disconnect cleanup has not already done so.

Parent termination while a peer remains connected

The parent session calls core.Services.StopSessionServices.

The containing process is canceled.

engine/engineutil marks its listener closing, rejects new sessions, and closes accepted connections.

The peer's main attachable connection loses its transport.

releaseClientConnection schedules peer reap.

Listener cleanup races that reap idempotently for each claimed peer.

Peer services stop before peer cache release.

Peer close while the containing process remains alive

The peer's /shutdown drains workspace locks, stops peer services, and flushes peer telemetry.

The main attachable connection closes.

Session teardown continues in the background.

The containing process remains alive because its lifecycle belongs to the session that created it.

It may exit, remain disconnected, or open another peer.

API state from the closed peer is gone with that session.

Transport loss and reconnect

An ordinary session has a narrow reconnect race before scheduled reap acquires the lifecycle lock.

The independent listener permits reconnection only to a session and main-client tuple already in its own claim set.

Current SDK connect parameters do not provide a durable reconnection contract across CLI process loss.

Phase one treats loss of the peer CLI or main attachable connection as loss of the peer session.

The application opens a new peer and rebuilds API state from its own durable application state.

Do not describe this as detachable reconnect.

Child service must survive main-client disconnect

An ordinary peer always stops its services when its main client closes.

The main process may keep its connection open for the full service lifetime.

If a child service must survive that disconnect, the peer itself needs detachable semantics.

That case requires scoped session-ID retention, termination authority, and attachment recovery.

It is a separate phase.

Phase one requires the main connection to remain open for the required peer lifetime.

Engine shutdown or restart

Server.GracefulStop terminates every live session.

All peer and parent service processes stop.

In-memory listener claims, session roots, and client records disappear.

Persisted cache records follow existing clean-shutdown behavior.

Application storage follows its existing persistence semantics.

No peer or detachable P0 session reconnects after restart.

9. Session-boundary rule

An independent process behaves like any external main client that opens a new ordinary session. Dagger object IDs do not cross that session boundary. The design adds no cross-session handoff or resource translation. The process's filesystem, environment, and network are simply the new client's execution environment. Everything else follows existing ordinary-session behavior.

10. Existing session cleanup is the lifetime boundary

engine/server.removeDaggerSession already defines ordinary session teardown.

It stops that session's work and services, removes its clients and providers, and calls Cache.ReleaseSession after in-flight DagQL work drains.

This releases the peer's active cache roots. It does not promise immediate deletion of persisted DagQL or BuildKit cache data.

It does not affect roots owned by the parent session or another peer.

Closing a peer does not make the parent forget the graph used to create the containing process. The parent continues to retain every result it observed while creating that process. Stopping a service process releases its live service lease. It does not remove the parent's DagQL session roots.

The peer still removes the separate API graph created through the peer.

It does not release unrelated parent-session intermediates.

If the remaining parent growth is material, the application must move more work into peers, periodically replace its parent session, or revisit the first-track design.

The peer boundary also removes the peer's other ordinary session state. It does not bound engine-global persisted data or parent-session state.

11. Concurrency, inspection, limits, races, and performance

Concurrent sessions from one process

The server stores sessions in Server.daggerSessions by SessionID.

One process may run several local dagger session children.

Each child creates a peer with one main attachable connection.

No hard session-count or client-count limit was found in the reviewed code.

Server.ConnectedClients currently returns the number of daggerSessions, despite its name.

engine/clientdb/store_stream.go targets a 2 MiB in-memory tail and applies a 32 MiB blocking hard cap to each of the three telemetry streams by default.

Older rows spill to append-only files, so the cap bounds a stream's live tail rather than its disk history.

removeDaggerSession gives teardown a 60-second safeguard context.

engine/client.Client.shutdownServer uses a 10-second default client timeout, configurable through _EXPERIMENTAL_DAGGER_SHUTDOWN_TIMEOUT.

Per-session fixed cost

  • One daggerSession, resolver, auth source, attachable manager, service manager, analytics object, and lifecycle state.
  • At least one full daggerClient, forked schema, engine utility client, root query, workspace state, and module state.
  • One tracer provider, logger provider, meter provider, exporters, and periodic metric reader.
  • One keepalive client database with span, log, and metric streams.
  • One upgraded attachable connection and ordinary HTTP and telemetry connections.
  • One local CLI process for SDKs that use dagger session.

Peer sessions are appropriate where a full session is the intended lifetime boundary.

They are not appropriate per GraphQL field or module call.

Required production benchmark

  1. Measure 1, 10, 100, and the expected maximum concurrent ordinary peers.
  2. Separate CLI spawn, claim registration, attachable readiness, /init, first query, /shutdown, background session removal, and post-close GC.
  3. Record p50, p95, and p99 latency.
  4. Record engine and client RSS, heap, goroutines, processes, file descriptors, sockets, clientdb bytes, and DagQL root counts.
  5. Repeat with 0, 1,000, and 100,000 peer-owned DagQL results.
  6. Repeat with representative processes and active services.
  7. Force parent termination during every startup and teardown phase.
  8. Wait past the one-hour clientdb retention window and verify disk returns to baseline.

Is there a narrower current API?

Existing leases and handles scope individual subsystems.

None scopes a complete client, service manager, resource table, and cache roots together.

core.Services is already a useful process boundary, but its lifetime remains inside one session.

The existing full daggerSession is the narrowest coherent resource scope found in current code.

13. Critical comparison with client-specific cache ownership

The first-track document is technically serious.

It correctly finds that no client-owned cache reference exists today.

It correctly rejects release at activeCount == 0.

It identifies real module return and service callback handoff gaps.

It also states that its cache change does not solve retained daggerClient objects or telemetry files.

Machinery avoided by a peer

  • No new CacheOwner registry or owner kind.
  • No owner context on every cache hit, miss, waiter, attach, receiver, list child, and ID load.
  • No owner-indexed arbitrary-call roots, provenance, or prune union.
  • No client-epoch resource-binding sequence and conditional unbind.
  • No service cache owner beside the existing service lease.
  • No module function return gate.
  • No moduleTypes result handoff gate.
  • No same-client retired-epoch schema replacement rule.
  • No explicit-owner failure mode in detachable GraphQL contexts.

The peer uses the existing session owner for all of these categories.

It calls the existing ReleaseSession only when the coherent peer ends.

Costs unique to a peer

  • A fresh-session handler on the existing process listener and claim-checked ordinary-session cleanup.
  • Internal SDK and engine-client routing based on the injected listener mode.
  • One full session stack per active peer.
  • The opening process must retain each SDK client handle it intends to close explicitly.

Cases the first track handles better

A module function can return an object to its caller without crossing sessions.

A long-running same-session service can release one callback client's intermediate roots while the service continues.

A short helper need not pay full peer startup cost.

Cases the peer handles better

Closing a peer releases the whole peer session rather than only its cache owner.

It removes the peer's client map, resolver, services, workspace state, session resources, and telemetry providers.

It reuses heavily tested session teardown instead of adding a second liveness graph inside DagQL.

Its principal correctness boundary is transport and session creation.

Recommendation relative to first-track work: implement and soak restricted ordinary peers before client-specific cache ownership for this use case. Treat the first track as deferred. Resume it only if measurement shows unacceptable parent-session growth or if one peer itself needs smaller lifetimes.

C does not make B obsolete.

C solves a coarser subset with less cache machinery.

Principal risks

  • The independent handler may accidentally become a raw engine proxy.
  • A session may publish after listener cleanup enumerates claims.
  • An SDK may treat the independent endpoint as an ordinary nested environment connection and omit main-client attachables.
  • An opted-in process may unexpectedly require parent-session access which its selected mode deliberately withholds.
  • Many peers may exhaust file descriptors, processes, clientdb disk, or telemetry capacity before cache memory becomes a problem.
  • The parent may retain significant roots from constructing the containing process.
  • Persisted cache and BuildKit data may be mistaken for a failed session cleanup.
  • Adding independent mode to generated module runtimes would reintroduce the module return handoff problem.
  • Detachable peer support may expand into a second session-control product before ordinary peers are proven.

19. Appendix: Tailcall example

Tailcall is one motivating application of this Dagger capability.

Its detachable daemon session may live for a month while it creates and retires agent services.

A direct mapping is:

  • the Tailcall daemon uses daggerNesting: NESTED_CLIENT in its long-running parent session;
  • each agent service receives daggerNesting: INDEPENDENT_SESSIONS;
  • the agent becomes main client of its own ordinary peer session;
  • agent-created child processes use NESTED_CLIENT unless they define another autonomous lifetime;
  • archiving an agent stops its containing service, which closes the peer's main connection.

This layout leaves the agent service's construction graph in the daemon's parent session.

Tailcall could instead run the daemon process with INDEPENDENT_SESSIONS, open one peer per agent, and create each agent service inside its peer with NESTED_CLIENT.

That layout keeps the agent service graph in the peer, but the daemon cannot also join its containing parent session and daemon exit closes every peer it opened.

These are Tailcall deployment choices. They are not Dagger modes or client kinds.

If retained parent roots remain material, Tailcall can revisit the first-track ownership design.

Tailcall's durable application data continues to use existing Dagger storage semantics. This design adds no Tailcall-specific protocol.

Conclusion

Yes, independent peer sessions can provide a shorter cache lifetime inside a long-running session with materially less machinery. They are technically possible inside a container when a direct route exists. The current nested route cannot create them. A fresh-session handler selected by DaggerNesting on the existing per-process listener is the simplest safe product design found.

The reduction is real because the design reuses the current session owner, service manager, resource table, client cleanup, and Cache.ReleaseSession.

The reduction is bounded because a full peer is coarser than a client epoch.

Closing a peer releases that peer's cache roots and adjacent session state.

It does not release the parent session's own roots.

It does not solve module or callback churn inside a peer that remains open.

Prototype ordinary peers first.

Measure the remaining parent and within-peer slopes.

Defer the first-track cache-ownership work unless those measurements prove that a peer boundary is too coarse.
