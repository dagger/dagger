1. Purpose and completion rule

P0 must produce one real end-to-end path. A user starts dagger call --detach or dagger api call --detach. The CLI completes local schema discovery and argument conversion, gives the engine one final GraphQL request, receives an engine-issued session ID and query ID, and exits. The query continues without that CLI process. Another CLI can list the session, inspect it, follow the query, print its final result, and terminate the session.

P0 is not complete if only the session registry works. It is also not complete if a test-only query survives but the normal CLI cannot create, inspect, attach to, and terminate it. The engine, client transport, CLI, telemetry replay, saved result, and cleanup must work together.

P0 does not include

P0 does not include dagger up, dagger api query, dagger check, shell, listen, run, develop, interactive stdin, terminal sessions, host output export, user-provided session names, public SDK options, callback rebinding, multiple detached queries in one session, concurrent attachments, force attach, a TTL, engine restart survival, Cloud scale-out, or the long-term DagQL cache ownership change.

Shell and listen are old interfaces and receive no detachable-session support. P0 adds --detach only to the two call commands. Other commands do not receive a global flag that they must reject.

2. Exact P0 contract

AreaP0 behavior
Default sessionsUnchanged. The client chooses the session ID. Client.Close calls /shutdown. Last-main disconnect tears down the session.
Detached session creationThe CLI opts in through client.Params.Detachable. The engine creates the session ID and returns it before the client starts ordinary session traffic.
LifetimeThe engine has one session cancellation root. Disconnect clears the detachable session's current attachment but does not cancel that root. Explicit termination and engine shutdown cancel it.
WorkOne final GraphQL HTTP request is stored and run independently of the request connection. Earlier schema and argument requests remain ordinary attached requests.
ResultThe engine saves the exact GraphQL response status, selected headers, and body. Attach does not rerun the query or reconstruct command arguments.
AttachmentOne current attachment. A later attachment is allowed after the old one closes or its attachable connection is found dead. A stale close cannot clear a newer attachment.
CallbacksP0 does not redirect callbacks to the new client. An operation that needs the absent creator or a concrete source client fails. The session remains live and terminable.
TelemetryThe detached query continues to write to the creator client's existing telemetry database. Attach replays that database through session control routes and then follows new records.
CleanupTerminate runs the existing full teardown once, removes the saved request/result files, and removes the session from list and inspect.
RestartEngine shutdown terminates all sessions. Startup discards result directories from older engine processes. No session is reconstructed.

3. Current code that P0 changes

  • engine/client/client.go creates both IDs, starts attachables, subscribes to telemetry, connects the generated Go client, and always calls /shutdown from Client.Close.
  • engine/server/session.go creates daggerSession inside getOrInitClient. releaseClientConnection schedules reapDaggerSession when the immutable mainClientCallerID reaches zero active requests.
  • serveHTTPToClient calls getOrInitClient before routing normal endpoints. Session management routes must be dispatched before that call. Otherwise session list would create a session merely to list sessions.
  • serveQuery derives work from r.Context(). A closed HTTP connection cancels the query. The reusable part begins after client lookup and includes workspace loading, schema construction, DagQL accounting, telemetry providers, and dagql.NewDefaultHandler(schema).
  • removeDaggerSession already contains the full terminal cleanup: stop services, close the resolver, cancel and drain DagQL work, release containers, shut down telemetry, release the engine cache session, and close shutdownCh.
  • internal/cmd/dagger/functions.go builds the final call through querybuilder.Selection. Selection.Build produces the GraphQL selection after argument values have been marshalled. Selection.Execute adds query Query, sends it, and unpacks the nested response.
  • internal/cmd/dagger/session.go currently owns a hidden bare dagger session command used by SDK launchers.

4. Engine state model

Keep the existing initialized/removed state for safe initialization and teardown. Add detachable lifetime and attachment state instead of replacing that state machine.

type sessionLifetime uint8
const (
    sessionLifetimeAttached sessionLifetime = iota
    sessionLifetimeDetachable
)

type sessionAttachment struct {
    ID         string
    Generation uint64
    ClientID   string
    Ready      bool
    CreatedAt  time.Time
}

type daggerSession struct {
    sessionID string
    lifetime  sessionLifetime

    // Kept in P0 for existing callback behavior. It identifies the creator.
    mainClientCallerID string
    creatorClientID    string

    attachmentMu         sync.Mutex
    currentAttachment    *sessionAttachment
    nextGeneration       uint64
    createdAt            time.Time
    detachedAt           time.Time
    primaryQuery         *detachedQuery

    // Existing lifecycleMu, closingCtx, clients, services, DagQL counters,
    // telemetry, containers, and cleanup fields remain.
}

The P0 attachment is lifecycle control state. It does not redefine every callback call site. mainClientCallerID remains the creator ID until the later role/source-client audit. This makes the limitation explicit: attach can observe and terminate the primary query, but it does not make old client-backed operations portable.

State transitions

POST /v1/sessions
    create + initialize session
    reserve attachment generation 1
                 │
                 ▼
              attached ──graceful close / dead attachables──► detached
                 ▲                                                │
                 └──────────── POST /attachments ─────────────────┘

attached or detached ──DELETE /v1/sessions/{id}──► terminating ──► removed
engine shutdown ──────────────────────────────────► terminating ──► removed

releaseClientConnection keeps its ordinary branch. For a detachable session it schedules detachAttachment, not removeDaggerSession. detachAttachment compares attachment ID and generation, records detachedAt, and deregisters that client's attachables when the departure is graceful. It never calls cancelClosing, StopSessionServices, or Cache.ReleaseSession.

Creation and lost responses

The create request contains a random client-generated request_id. The engine stores request_id → session ID in memory before writing the response. Retrying the same request ID returns the same session descriptor. The index disappears at termination. This handles a connection loss after creation but before the CLI receives the ID without adding persistence.

The create handler generates the session ID, copies it into the parsed ClientMetadata, and explicitly calls the existing initialization path. The route's cleanup sees sessionLifetimeDetachable and leaves the initialized session detached if attachable registration never arrives. P0 does not add a reservation timeout. Such a session remains visible and can be terminated. This is simpler and matches the explicit-cleanup rule.

6. Detached query execution and saved output

Submission boundary

The engine can validate the HTTP envelope and size before acceptance. It cannot promise GraphQL schema validation without beginning GraphQL execution. Therefore 202 Accepted means the complete request bytes and query record are stored and execution has been scheduled. A GraphQL parse, validation, or resolver error becomes the saved GraphQL result. The response does not claim that the GraphQL operation is valid.

Shared execution function

Extract the body of serveQuery after client lookup into a function used by both ordinary and detached paths:

func (srv *Server) executeGraphQL(
    ctx context.Context,
    client *daggerClient,
    w http.ResponseWriter,
    r *http.Request,
) error {
    // Existing DagQL in-flight accounting, workspace/module loading,
    // schema creation, telemetry setup, lease provider, and gqlgen handler.
}

func (srv *Server) serveQuery(w http.ResponseWriter, r *http.Request, client *daggerClient) error {
    return srv.executeGraphQL(sess.withClosingCancel(r.Context()), client, w, r)
}

func (srv *Server) runDetachedQuery(sess *daggerSession, q *detachedQuery) {
    ctx := sessionContextWithStoredTrace(sess.closingCtx, q.traceContext)
    req := q.newHTTPRequest(ctx)
    writer := newResultFileWriter(q)
    err := srv.executeGraphQL(ctx, q.creatorClient, writer, req)
    q.finish(writer.commit(), err)
}

The detached context preserves the submitting trace context and engine metadata but does not preserve request cancellation. It is canceled only by the existing session closing context. The detached path enters the same dagqlInFlight accounting, so existing teardown waits for it.

Files

Use <worker root>/session-results/<engine process ID>/<session ID>/. The directory is mode 0700; files are 0600. IDs are engine-generated and validated before joining paths.

request.json.tmp  → request.json     complete request, max 16 MiB
result.body.tmp   → result.body     exact response body, max 64 MiB
result.json                         status, headers, timestamps, error state

Write temporary files and rename them only after a complete write. Attach never reads a temporary file. Preserve Content-Type and the GraphQL HTTP status. Do not preserve hop-by-hop headers. If the response exceeds 64 MiB, continue draining the handler output, delete the body, and set result_discarded. The exact behavior of gqlgen after a ResponseWriter.Write error must be verified before implementation; the writer should absorb excess bytes and report the limit through its own state instead of relying on gqlgen to return the write error.

P0 has one primary result, so a separate 256 MiB per-session aggregate limit has no effect and should not be implemented yet. Add that limit only when more than one saved result exists.

CLI presentation data

The saved GraphQL body is command-independent. dagger call also needs enough data to print the nested leaf exactly once. The submit request carries a small presentation record:

type QueryPresentation struct {
    Kind       string   `json:"kind"`        // "call" in P0
    ResponsePath []string `json:"response_path"`
    JSON       bool     `json:"json"`
    Void       bool     `json:"void"`
}

Add a read-only ResponsePath() method to the in-repository use of querybuilder only if the dependency can expose it cleanly. The preferred smaller change is to record the aliases while FuncCommand constructs the selection. Attach parses {"data":...}, walks that path, and calls a pure formatting function. P0 supports void, scalar, enum, list, and object-ID output that needs no follow-up query. It rejects Changeset, LLM, terminal, pipe, --output, and any return handler that issues another GraphQL request or writes to the host.

7. Telemetry and result replay

The detached query uses the creator daggerClient and therefore its tracer, logger, meter providers, and client telemetry DB. Detach must not call ShutdownTelemetry. It may force-flush while the client connection is still healthy, but the providers remain session-owned until termination.

The current telemetry routes look up the client named by request metadata. A new attachment has a different client ID, so those routes cannot replay the creator's query history directly. Add session control telemetry routes that resolve the session, select creatorClientID, and call the existing TracesSubscribeHandler, LogsSubscribeHandler, and MetricsSubscribeHandler with that daggerClient. Do not copy telemetry into another database.

dagger session attach starts the normal frontend telemetry consumers against those three routes with no cursor. Existing SSE code replays all rows and follows live rows. When the query is complete, force-flush its providers, close the query-completion channel, let each SSE stream drain, then render the saved result. Ctrl+C closes only the new attachment and exits 130. It does not terminate the session.

Refactor Connect into transport setup followed by session setup. Ordinary mode remains byte-for-byte equivalent in behavior. Attach calls the attachment route first and then starts its own attachables.

Close behavior

func (c *Client) Close() error {
    if c.detachableAttachment != nil {
        // Best effort while transport is still open.
        closeAttachment(c.detachableAttachment)
    } else {
        shutdownServer()
    }
    return c.closeLocalResources()
}

Extract the common local cleanup from current Close. A detachable close never calls /shutdown. Terminate(ctx) calls the session delete route and then performs local cleanup. Control commands need a ControlClient that starts the engine transport but does not create a normal session, attachables, generated Dagger client, or telemetry subscription.

9. CLI implementation

call and api call

Add a persistent --detach flag to each FuncCommand, not to the root command. Set client.Params.Detachable before withEngine. Schema discovery and argument conversion continue through normal requests.

At the leaf, detached mode replaces makeRequest with submitDetachedRequest. Build query Query { ... }, construct the GraphQL JSON body, include presentation data, submit it, print IDs, and return without calling handleResponse. If the CLI created the session but fails before the engine returns a query ID, it sends terminate as cleanup. Once the query ID is returned, normal CLI cleanup closes only the attachment.

Validate unsupported output before submission. Return Cobra usage exit 2 with direct messages such as --detach cannot be used with --output and --detach does not support LLM results in P0.

session command family

Replace the hidden bare command with a visible parent. Move the SDK transport implementation to hidden dagger session serve. This is a hard launcher cut. Update every in-tree launcher and its tests in the same change.

dagger session list [--json]
dagger session inspect SESSION [--json]
dagger session attach SESSION
dagger session terminate SESSION [--json]
dagger session serve [existing hidden SDK flags]

list and inspect use ControlClient. attach opens a detachable engine client, points frontend exporters at session telemetry routes, waits for the primary query, renders the saved result, and closes its attachment. terminate is usable while detached or attached. It does not require becoming the current attachment.

Launcher cut

11. Ordered implementation sequence

  1. Wire types and control routing. Add types, route management requests before getOrInitClient, implement list/inspect snapshots, and test that control commands do not allocate ordinary sessions.
  2. Lifetime split. Add detachable state, create negotiation, generation-checked attach/close, and policy-dependent last-connection handling. Keep removeDaggerSession as the only full cleanup body. Prove ordinary disconnect remains unchanged.
  3. Client connection split. Refactor transport setup, add detachable create/attach, local close versus terminate, and control-only connections. Do this before CLI work so tests use the real client path.
  4. Stored query execution. Extract shared GraphQL execution, store the complete request, start it on session context, save the exact response, expose status/result, and integrate terminal cancellation.
  5. Telemetry replay. Route the creator DB through session endpoints and prove replay before completion and after completion.
  6. Call integration. Add flags, result support checks, final request construction, presentation metadata, ID output, and pre-acknowledgment failure cleanup.
  7. Session CLI and launcher cut. Add list/inspect/attach/terminate, move SDK transport to serve, update all launchers and exact-argv tests.
  8. End-to-end races and cleanup. Run focused engine-dev integration tests. Measure retained DagQL cache metadata while repeating calls in a live detachable session model. Document the measured growth; do not call P0 broadly releasable.

12. Test plan

Follow skills/engine-debugging/SKILL.md. Run focused tests with dagger api call engine-dev test --pkg ... --run=..., save full output under /tmp, and do not use broad repository suites while iterating.

Engine server package tests

  • Ordinary session last-main disconnect calls full teardown. Detachable disconnect does not cancel closingCtx, stop services, release cache ownership, or delete the registry record.
  • Graceful close removes attachables immediately. Abrupt transport loss is detected by the existing health monitor; attach retries until the stale registration is removed.
  • Old attachment close after a new attach is a no-op because ID and generation do not match.
  • Two concurrent attach requests have one winner. Attach racing with terminate either completes before the terminal transition or gets a terminal error.
  • Two terminate requests share one teardown. Service stop, container release, telemetry shutdown, cache release, result deletion, and registry deletion each occur once.
  • Create response loss followed by the same request ID returns the same session. Different input with the same request ID returns conflict.
  • Query body is fully stored before 202. Disconnect before storage gives no execution guarantee. Disconnect after 202 does not cancel execution.
  • GraphQL syntax and schema errors are saved results. Running, succeeded, failed, canceled, and result-discarded states are observable.
  • 16 MiB request and 64 MiB result boundaries, atomic rename, partial file invisibility, result deletion, and stale process-directory cleanup.
  • Terminate during schema load, resolver work, response write, and result commit. The query completes or is canceled once; attach never sees a partial result.
  • Creator telemetry SSE replays from row zero, follows live rows, drains after query completion, and remains readable by a different attachment.

Engine client and CLI tests

  • Ordinary Client.Close still calls shutdown. Detachable close calls attachment close and never shutdown. Terminate calls session delete.
  • Control-only connections do not start attachables, a generated Dagger client, or a new session.
  • call --detach and api call --detach help, human output, JSON output, and direct validation errors.
  • Final query construction matches the querybuilder ordinary request. Presentation paths extract scalar, list, enum, void, and object ID values.
  • Changeset, LLM, terminal, pipe, and --output are rejected before query submission.
  • A failure before query acknowledgment terminates the newly created session. A process exit after acknowledgment leaves it listed.
  • Attach running and completed queries. Verify attach fetches the saved result and never calls query submission.
  • Attach Ctrl+C exits 130 and leaves the session listed. Query failure returns exit 1 after printing the saved GraphQL error. A successful result returns zero.
  • List/inspect table and JSON fields are stable. Unknown session, already attached, terminating, and discarded-result errors map to documented exits.
  • Every SDK launcher invokes exactly session serve and still parses the existing port/token JSON.

Focused end-to-end tests

  1. Run a slow engine-only call with a side effect counter. Wait for IDs, let the first CLI exit, attach while running, observe progress, receive the result, and verify the counter is one.
  2. Run the same call and attach only after completion. Verify exact output and no second execution spans.
  3. Kill the creator transport immediately after the server storage barrier. Verify completion. Kill it immediately before that barrier and verify inspect reports no primary query or a stored query according to which side won.
  4. Run an operation that asks for a host file or registry callback after detach. Verify the query receives a clear client-unavailable error and the session remains listable and terminable.
  5. Use two client implementations with different bytes for the same host path. Verify the second attachment cannot satisfy the first client's source object. This does not require two physical machines.
  6. Terminate a running query. Verify cancellation, result state, service/container/provider cleanup, cache release, result-directory removal, and disappearance from list.
  7. Verify an ordinary slow call still ends when its client disconnects.
  8. Restart the engine process. Verify the old ID is absent and stale result files are removed.
  9. Record /debug/dagql/cache metadata before and after repeated detached operations and after termination. This test measures the known cache retention problem; it does not define its solution.

Deterministic fault injection

Add package-private test hooks backed by channels at these points: session published, create response write, attachment published, attachment cleared, query body committed, query goroutine started, GraphQL handler entered, result body committed, query status completed, terminal transition entered, each resource cleanup, and registry deletion. Use fake clocks only for timestamps. Do not use sleeps to decide race outcomes.

13. P0 acceptance criteria

  1. dagger call --detach and dagger api call --detach return a session ID and query ID only after the engine stores the complete final request.
  2. The initiating CLI can exit gracefully or lose its network connection after acknowledgment without canceling the query or session.
  3. session list and inspect show attached/detached state and primary-query state without creating another session.
  4. session attach works before and after query completion, replays progress, prints the saved result, returns the query outcome, and never reruns the query.
  5. Only one attachment is current. Delayed close from an old attachment cannot clear a new one.
  6. A missing client callback fails the requesting operation and does not terminate the session.
  7. session terminate is race-safe and idempotent while the terminal record exists. It releases all resources through the existing cleanup path and removes saved files.
  8. Ordinary sessions retain their current IDs, startup, /shutdown, disconnect, and cleanup behavior.
  9. Engine restart ends all detachable sessions. No result file is treated as a restorable session.
  10. The hidden SDK transport is available only as dagger session serve, and every in-tree launcher uses it.
  11. Focused package and end-to-end tests pass through the required engine-dev test path.

14. Known limits and implementation validation points

Cache ownership remains unresolved. P0 keeps the current session-wide DagQL ownership model. An indefinitely live session can keep a large result graph from pruning. P0 must measure this growth and is suitable for controlled evaluation only. Broad release requires a separate design that defines which results, services, and object IDs remain owned.
  • Result formatting: confirm every P0-supported FuncCommand result can be rendered from the saved GraphQL body without a follow-up query. Reject any type that cannot.
  • Response writer: verify gqlgen behavior when the result limit is crossed. Use a writer that drains and records overflow rather than depending on error propagation.
  • Telemetry completion: prove provider flush and SSE drain ordering under terminate and normal completion. Do not shut down creator providers on detach.
  • Attachable health delay: the existing monitor normally requires two failed checks and uses bounded RPC checks. Attach must retry with a visible status; it must not steal an attachment.
  • Callback semantics: P0 intentionally leaves role callbacks bound to current code behavior. The later audit must separate creator, current main, and concrete source client. Do not describe P0 attach as making old client-backed values portable.
  • Request acknowledgment: 202 proves storage and scheduling, not GraphQL validity or eventual success.
  • Session creation leak: a client that disappears after creation but before query submission leaves a discoverable session. The CLI terminates it when it can prove no query was acknowledged. Network loss can still leave one; explicit list and terminate are the recovery path.
  • Protocol version: detachable clients require an engine containing these routes and metadata fields. Return a direct incompatible-engine error. Do not add fallback behavior that converts a detachable request into an ordinary session.
Recommended implementation boundary: land P0 behind an experimental CLI flag if release policy requires it, but implement the production lifecycle and cleanup paths directly. Do not build a second prototype registry or a test-only execution path that must later be replaced.
