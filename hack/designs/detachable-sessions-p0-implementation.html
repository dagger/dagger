1. Purpose and completion rule

P0 must produce one real end-to-end path. A user starts dagger call --detach or dagger api call --detach. The client creates the detachable session ID before connecting. The CLI completes local schema discovery and argument conversion, gives the engine one final GraphQL request, receives a query ID, and exits. The query continues without that CLI process. Another CLI can list the session, inspect it, follow the query, print its final result, and terminate the session.

P0 is not complete if only the session registry works. It is also not complete if a test-only query survives but the normal CLI cannot create, inspect, attach to, and terminate it. The engine, client transport, CLI, telemetry replay, saved result, and cleanup must work together.

P0 does not include

P0 does not include dagger up, dagger api query, dagger check, shell, listen, run, develop, interactive stdin, terminal sessions, host output export, user-provided session names, public SDK options, callback rebinding, multiple detached queries in one session, concurrent attachments, force attach, a TTL, engine restart survival, Cloud scale-out, SDK launcher changes, or the long-term DagQL cache ownership change.

Shell is legacy and may be removed. Listen is also outside this work. Neither receives detachable-session support. P0 adds --detach only to the two call commands. Other commands do not receive a global flag that they must reject.

2. Exact P0 contract

AreaP0 behavior
Default sessionsUnchanged. The client chooses the session ID. Client.Close calls /shutdown. Last-main disconnect tears down the session.
Detached session creationThe CLI opts in through client.Params.Detachable. The client generates a detachable session ID before connecting. The first attachables request creates the engine session through the existing initialization path and declares its detachable lifetime.
LifetimeThe engine has one session cancellation root. Disconnect clears the detachable session's current attachment but does not cancel that root. Explicit termination and engine shutdown cancel it.
WorkOne final GraphQL HTTP request is stored and run independently of the request connection. Earlier schema and argument requests remain ordinary attached requests.
ResultThe engine saves the exact GraphQL response status, selected headers, and body. Attach does not rerun the query or reconstruct command arguments.
AttachmentOne current attachment. A later attachment is allowed after the old one closes or its attachable connection is found dead. A stale close cannot clear a newer attachment.
CallbacksP0 does not redirect callbacks to the new client. An operation that needs the absent creator or a concrete source client fails. The session remains live and terminable.
TelemetryThe detached query continues to write to the creator client's existing telemetry database. Attach replays that database through session control routes and then follows new records.
CleanupTerminate runs the existing full teardown once, removes the saved request/result files, and removes the session from list and inspect. Deleting a well-formed but absent detachable session ID also succeeds, which makes termination idempotent without retaining completed-session records.
RestartEngine shutdown terminates all sessions. Startup discards result directories from older engine processes. No session is reconstructed.

3. Current code that P0 changes

  • engine/client/client.go creates both IDs, starts attachables, subscribes to telemetry, connects the generated Go client, and always calls /shutdown from Client.Close.
  • engine/server/session.go creates daggerSession inside getOrInitClient. releaseClientConnection schedules reapDaggerSession when the immutable mainClientCallerID reaches zero active requests.
  • serveHTTPToClient calls getOrInitClient before routing normal endpoints. Session management routes must be dispatched before that call. Otherwise listing sessions would create a session merely to list them.
  • serveQuery derives work from r.Context(). A closed HTTP connection cancels the query. The reusable part begins after client lookup and includes workspace loading, schema construction, DagQL accounting, telemetry providers, and dagql.NewDefaultHandler(schema).
  • removeDaggerSession already contains the full terminal cleanup: stop services, close the resolver, cancel and drain DagQL work, release containers, shut down telemetry, release the engine cache session, and close shutdownCh.
  • internal/cmd/dagger/functions.go builds the final call through querybuilder.Selection. Selection.Build produces the GraphQL selection after argument values have been marshalled. Selection.Execute adds query Query, sends it, and unpacks the nested response.
  • internal/cmd/dagger/session.go currently owns a hidden bare dagger session command used by SDK launchers. P0 leaves that command and every SDK launcher unchanged.

4. Engine state model

Keep the existing initialized/removed state for safe initialization and teardown. Add detachable lifetime and attachment state instead of replacing that state machine.

type sessionLifetime uint8
const (
    sessionLifetimeAttached sessionLifetime = iota
    sessionLifetimeDetachable
)

type sessionAttachment struct {
    ID         string
    Generation uint64
    ClientID   string
    Ready      bool
    CreatedAt  time.Time
}

type daggerSession struct {
    sessionID string
    lifetime  sessionLifetime

    // Kept in P0 for existing callback behavior. It identifies the creator.
    mainClientCallerID string
    creatorClientID    string

    attachmentMu         sync.Mutex
    currentAttachment    *sessionAttachment
    nextGeneration       uint64
    createdAt            time.Time
    detachedAt           time.Time
    primaryQuery         *detachedQuery

    // Existing lifecycleMu, closingCtx, clients, services, DagQL counters,
    // telemetry, containers, and cleanup fields remain.
}

Ready represents only the connection-upgrade interval inside one attachables handler. false means that handler has claimed the attachment before upgrading the connection and owns a deferred release. true means sessionAttachableManager.Register has published the caller and connection death now owns cleanup. Ready never represents a reservation that survives its handler.

The P0 attachment is lifecycle control state. It does not redefine every callback call site. mainClientCallerID remains the creator ID until the later role/source-client audit. This makes the limitation explicit: attach can observe and terminate the primary query, but it does not make old client-backed operations portable.

releaseClientConnection keeps its current teardown behavior for an ordinary session. For a detachable session it records connection timestamps only. It does not clear the current attachment. Exactly two events may clear a detachable attachment: an explicit close presenting the current random attachment ID, and notification that the registered attachables connection died. Internal delayed events also compare the engine-recorded generation. The close-route handler deregisters attachables before it clears the matching attachment. Neither event calls cancelClosing, StopSessionServices, or Cache.ReleaseSession.

Creation and lost connections

The client generates the session ID and initial attachment ID before its first engine request. There is no create-session route and no request-ID replay index. A lost response cannot hide the session identity from the creator because the creator already knows it.

The first /sessionAttachables request carries the session ID, detachable-creation role, and client-generated attachment ID in ClientMetadata. getOrInitClient uses the existing session initialization path and records the detachable policy before publishing the initialized session and ready attachment. The engine assigns generation 1. If the connection fails before initialization is published, the engine has no session and the client retries the same IDs. If initialization was published, retry may collide with the stale attachables connection until health checking removes it; the client retries that specific error with capped backoff for up to 30 seconds. Session creation alone does not promise that work will run. Only a 202 response from primary-query submission provides that promise.

A later attachment generates a fresh attachment ID and sends an observer-attachment role in its attachables request. That request never enters the session-creation branch. It requires an existing initialized detachable session with no current attachment. Before the HTTP connection upgrade, the handler claims the attachment under attachmentMu, assigns the next internal generation, and installs a deferred claim release. This preserves the ability to return normal 404 and 409 responses. Connection hijack, the 101 Switching Protocols response, and the acknowledgment exchange occur while the handler owns that claim. Every failure before caller publication releases it. When sessionAttachableManager.Register publishes the caller, the handler marks the attachment ready and transfers cleanup ownership to a death notification carrying the attachment ID and generation. If the session was terminated before the claim, the request returns session not found; it never recreates the session. There is no attachment reservation that outlives its handler.

Explicit termination records the detachable session ID in an engine-memory terminal tombstone set before cleanup begins. Creator-role initialization checks that set and returns session terminated instead of recreating the session. The tombstone remains for one minute, which is longer than the 30-second creator reconnect deadline, and then expires without retaining session resources. Engine restart clears the set. This bound exists only to reject delayed creator retries after explicit termination; it is not a live-session TTL.

Observer locking

List and inspect never acquire lifecycleMu. They follow the existing observer rule used by Clients and activeClientIDs: take short registry, attachment, client, and query locks; copy an immutable descriptor; release those locks before encoding the response. Listing must remain responsive while initialization or the bounded terminal cleanup holds lifecycleMu.

Control errors use one JSON shape: {"error":{"code":"already_attached","message":"session sess_... already has an attachment"}}. CLI code switches on code, not English text.

The attachables endpoint also returns machine-readable retry information. A duplicate live or stale registration returns HTTP 409 with stable code attachment_connection_exists. Creator reconnect and observer attach retry only that status and code. They never parse the English message.

P0 uses strict generated identifiers: sess_, qry_, and att_ followed by 26 lowercase base32 characters. Parsing rejects any other length, prefix, or character before registry lookup or filesystem path construction. The creator client generates the session ID and its initial attachment ID. Every later attaching client generates a fresh attachment ID. The engine generates the query ID and assigns monotonically increasing attachment generations for state inspection and delayed internal-event checks. The token remains the existing random client secret and is not encoded in these identifiers.

6. Detached query execution and saved output

Submission boundary

The engine can validate the HTTP envelope and size before acceptance. It cannot promise GraphQL schema validation without beginning GraphQL execution. Therefore 202 Accepted means the complete request bytes and query record are stored and execution has been scheduled. A GraphQL parse, validation, or resolver error becomes the saved GraphQL result. The response does not claim that the GraphQL operation is valid.

Shared execution function

Extract the body of serveQuery after client lookup into a function used by both ordinary and detached paths:

func (srv *Server) executeGraphQL(
    ctx context.Context,
    client *daggerClient,
    w http.ResponseWriter,
    r *http.Request,
) error {
    // Existing DagQL in-flight accounting, workspace/module loading,
    // schema creation, telemetry setup, lease provider, and gqlgen handler.
}

func (srv *Server) serveQuery(w http.ResponseWriter, r *http.Request, client *daggerClient) error {
    return srv.executeGraphQL(sess.withClosingCancel(r.Context()), client, w, r)
}

func (srv *Server) runDetachedQuery(sess *daggerSession, q *detachedQuery) {
    ctx := sessionContextWithStoredTrace(sess.closingCtx, q.traceContext)
    req := q.newHTTPRequest(ctx)
    writer := newResultFileWriter(q)
    err := srv.executeGraphQL(ctx, q.creatorClient, writer, req)
    q.finish(writer.commit(), err)
}

The detached path reconstructs its context from an explicit checklist. It derives cancellation from the session closing context and srv.withShutdownCancel, installs the creator's ClientMetadata and analytics context, restores the submitted traceparent and baggage, and uses the creator's telemetry providers. It does not retain the HTTP request cancellation and does not increment or hold an active HTTP connection count. A valid restored span context is required because current query telemetry setup skips recording when trace.SpanContextFromContext(ctx) is invalid. The detached path enters the same dagqlInFlight accounting, so existing teardown waits for it.

q.newHTTPRequest sets Content-Type: application/json, sets a normal non-streaming Accept: application/json, restores the stored GraphQL body, and includes only headers required by GraphQL execution and telemetry propagation. It never negotiates multipart or streaming GraphQL output into the saved result file.

Files

Use <worker root>/session-results/<engine process ID>/<session ID>/. The directory is mode 0700; files are 0600. Session IDs are client-generated and query IDs are engine-generated. Both are strictly validated before joining paths.

request.json.tmp  → request.json     complete request, max 16 MiB
result.body.tmp   → result.body     exact response body, max 64 MiB
result.json                         status, headers, timestamps, error state

Write temporary files and rename them only after a complete write. Attach never reads a temporary file. Preserve Content-Type and the GraphQL HTTP status. Do not preserve hop-by-hop headers. If the response exceeds 64 MiB, continue draining the handler output, delete the body, and set result_discarded. The exact behavior of gqlgen after a ResponseWriter.Write error must be verified before implementation; the writer should absorb excess bytes and report the limit through its own state instead of relying on gqlgen to return the write error.

P0 has one primary result, so a separate 256 MiB per-session aggregate limit has no effect and should not be implemented yet. Add that limit only when more than one saved result exists.

CLI presentation data

The saved GraphQL body is command-independent. dagger call also needs enough data to print the nested leaf exactly once. The submit request carries a small presentation record:

type QueryPresentation struct {
    Kind         string   `json:"kind"`        // "call" in P0
    ResponsePath []string `json:"response_path"`
    ReturnKind   string   `json:"return_kind"`
    ElementKind  string   `json:"element_kind,omitempty"`
    JSON         bool     `json:"json"`
    Void         bool     `json:"void"`
}

querybuilder is an external module, so P0 does not add a new method to it. FuncCommand records field names and aliases while constructing the final selection. It records the response path after handleObjectLeaf rewrites the leaf to sync or id. The presentation record also contains the return kind and list element kind needed by the existing printer. Attach parses {"data":...}, walks the recorded path, and calls a pure formatting function. P0 supports void, scalar, enum, lists of scalar or enum values, and one object ID that needs no follow-up query. It rejects object lists, Changeset, lists of Changeset, LLM, terminal, pipe, --output, and any return handler that issues another GraphQL request or writes to the host.

7. Telemetry and result replay

The detached query uses the creator daggerClient and therefore its tracer, logger, meter providers, and client telemetry DB. Detach must not call ShutdownTelemetry. It may force-flush while the client connection is still healthy, but the providers remain session-owned until termination.

The current telemetry routes look up the client named by request metadata. A new attachment has a different client ID, so those routes cannot replay the creator's query history directly. Add session control telemetry routes that resolve the session, select creatorClientID, and call the existing TracesSubscribeHandler, LogsSubscribeHandler, and MetricsSubscribeHandler with that daggerClient. Do not copy telemetry into another database.

dagger sessions attach starts the normal frontend telemetry consumers against those three routes with no cursor. Existing SSE code replays all rows and follows live rows. The session telemetry routes call a parameterized form of sseHandler whose terminating signal is primaryQuery.done, not the creator client's shutdownCh. Query completion force-flushes the creator's providers with a bounded context, reads the current maximum trace, log, and metric row IDs, stores those three bounds in the primary-query record, and then closes primaryQuery.done. This occurs even when no client is attached at completion. Each SSE stream serves records only through its stored bound and exits when its cursor reaches that position. The database query or response trimming must enforce the upper bound; a batch may not include later rows. Only after all three streams finish does attach render the saved result. Ctrl+C closes only the new attachment and exits 130. It does not terminate the session.

Those captured positions define telemetry flushed at primary-query completion. Services and nested clients may continue writing rows afterward. Rows that arrive after the bounded flush returns, including rows delayed by a flush timeout, fall outside the captured positions. Later rows do not delay this attach and are not part of this query-completion replay.

The attach command's own local spans are separate from the creator query history. P0 sends them through the normal local frontend path but does not append them to or present them as records from the creator's telemetry database. The observer's engine-side providers remain idle because the observer issues no GraphQL work, and observer cleanup shuts them down.

8. Engine client changes

Connection modes

type Params struct {
    // existing fields
    Detachable bool
    AttachSessionID string

type SessionDescriptor struct {
    ID         string
    State      SessionState
    Attachment *SessionAttachment

Detachable and AttachSessionID are internal engine-client fields in P0. They are not public Go SDK options. Reject both together. Reject either for nested DAGGER_SESSION_PORT and engine-to-engine connections.

Refactor Connect into transport setup followed by session setup. Ordinary mode remains byte-for-byte equivalent in behavior. Detachable creation generates a sess_ ID and att_ ID locally, adds the lifetime and attachment metadata, then uses the existing startSession attachables request to initialize the session. It proceeds with telemetry setup and daggerConnect for schema discovery and final-query construction.

A later P0 attach uses a narrower path. It generates an attachment ID and directly registers attachables with the observer role; registration itself atomically claims the attachment. It does not call /init or /query, construct the generated Dagger client, request workspace or module loading, or submit new work. P0 does not route creator or source-client callbacks to those attachables; they establish attachment presence and health for later work.

The current server initialization path still creates a DagQL root, schema fork, telemetry providers, and client telemetry database keepalive for that observer daggerClient. P0 must not retain those objects across sequential attachments. When an observer attachment clears, after its attachables are deregistered, the engine removes that exact observer from sess.clients, shuts down its providers, closes its database keepalive, and releases observer-local resources. It never removes the creator client, which remains the owner of the running query and its telemetry. Repeated attach/detach tests verify that client count and observer-owned resources return to baseline.

Close behavior

func (c *Client) Close() error {
    if c.detachableAttachment != nil {
        // Best effort while transport is still open.
        closeAttachment(c.detachableAttachment)
    } else {
        shutdownServer()
    }
    return c.closeLocalResources()
}

Extract the common local cleanup from current Close. A detachable close never calls /shutdown. Terminate(ctx) calls the session delete route and then performs local cleanup. Control commands need a ControlClient that starts the engine transport but does not create a normal session, attachables, generated Dagger client, or telemetry subscription.

The terminate client uses a bounded observation timeout. The server begins cleanup with a context independent of the DELETE connection, so cleanup continues if the caller disconnects or reaches its timeout. Existing cleanup operations normally use the server's 60-second context, but the DagQL in-flight drain can exceed that period if a resolver ignores cancellation. The client timeout bounds observation, not cleanup. A timeout reports termination started but completion was not observed. A concurrently attached CLI sees its attachables and telemetry streams close and exits with a direct terminated-session message.

9. CLI implementation

call and api call

Add a persistent --detach flag to each FuncCommand, not to the root command. Set client.Params.Detachable before withEngine. Schema discovery and argument conversion continue through normal requests.

At the leaf, detached mode replaces makeRequest with submitDetachedRequest. Build query Query { ... }, construct the GraphQL JSON body, include presentation data and the current attachment ID, submit it, print IDs, and return without calling handleResponse. If the engine session was initialized but the CLI fails before it receives a query ID, it sends terminate as cleanup. Once the query ID is returned, normal CLI cleanup closes only the attachment.

Validate unsupported output before submission. Return Cobra usage exit 2 with direct messages such as --detach cannot be used with --output and --detach does not support LLM results in P0.

Provisional P0 management command

P0 adds a provisional dagger sessions command family. This name is intentionally not a final product decision. It avoids the existing hidden dagger session SDK transport. P0 does not modify that command or any SDK launcher.

dagger sessions list [--json]
dagger sessions inspect SESSION [--json]
dagger sessions attach SESSION
dagger sessions terminate SESSION [--json]

list and inspect use ControlClient. attach registers the narrow observer attachment described above, points frontend exporters at session telemetry routes, waits for the primary query, renders the saved result, and closes its attachment. terminate is usable while detached or attached. It does not require becoming the current attachment.

If attach receives already_attached, it prints Waiting for the previous client connection to be declared unavailable... once and retries with capped backoff for up to 30 seconds. It never steals the attachment. If the deadline expires, it returns exit 1. If the session has no primary query, attach returns exit 1 immediately with session has no primary query; inspect remains available and terminate removes the empty session.

12. Test plan

Follow skills/engine-debugging/SKILL.md. Run focused tests with dagger api call engine-dev test --pkg ... --run=..., save full output under /tmp, and do not use broad repository suites while iterating.

Engine server package tests

  • Ordinary session last-main disconnect calls full teardown. Detachable disconnect does not cancel closingCtx, stop services, release cache ownership, or delete the registry record.
  • Graceful close removes attachables immediately. Abrupt transport loss is detected by the existing health monitor; attach retries until the stale registration is removed.
  • Old attachment close after a new attach is a no-op because its random ID does not match. Delayed internal events also fail their engine-recorded generation check.
  • Two concurrent attach requests have one winner. Attach racing with terminate either completes before the terminal transition or gets a terminal error.
  • Terminate after an observer begins registration but before it claims the attachment cannot be followed by session recreation. Observer-role metadata never enters the creation branch.
  • Hijack, switching-protocol response, and acknowledgment failures after claim but before Register each release the transient non-ready attachment.
  • Two terminate requests share one teardown. Service stop, container release, telemetry shutdown, cache release, result deletion, and registry deletion each occur once.
  • Failure before first attachables initialization leaves no engine session and retrying the same client-generated IDs succeeds. Reconnecting after initialization uses the same token and session.
  • Creator retry paused until explicit termination has removed the session receives session terminated during the one-minute tombstone and cannot recreate it. Fake-clock expiry allows later reuse without retaining session resources.
  • Query body is fully stored before 202. Disconnect before storage gives no execution guarantee. Disconnect after 202 does not cancel execution.

Deterministic fault injection

Add package-private test hooks backed by channels at these points: session published, creator attachables registration, observer registration before and after existing-session validation, attachment published, explicit close, attachables-death notification, attachment cleared, observer-client cleanup, query body committed, query goroutine started, GraphQL handler entered, result body committed, creator telemetry flush, completion-cursor capture, SSE bounded final-row read, query status completed, terminal transition entered, each resource cleanup, and registry deletion. Use fake clocks only for timestamps. Do not use sleeps to decide race outcomes.

13. P0 acceptance criteria

  1. dagger call --detach and dagger api call --detach print their client-generated session ID and engine-generated query ID only after the engine stores the complete final request.
  2. The initiating CLI can exit gracefully or lose its network connection after acknowledgment without canceling the query or session.
  3. sessions list and inspect show attached/detached state and primary-query state without creating another session.
  4. sessions attach works before and after query completion, replays progress, prints the saved result, returns the query outcome, and never reruns the query.
  5. Only one attachment is current. Delayed close from an old attachment cannot clear a new one.
  6. A missing client callback fails the requesting operation and does not terminate the session.
  7. sessions terminate is race-safe and idempotent, including after the record has been removed. It releases all resources through the existing cleanup path and removes saved files.
  8. Explicit termination installs a bounded terminal-ID tombstone before cleanup, so a delayed creator retry cannot recreate the session during its reconnect window.
  9. Ordinary sessions retain their current IDs, startup, /shutdown, disconnect, and cleanup behavior.
  10. Engine restart ends all detachable sessions. No result file is treated as a restorable session.
  11. The hidden dagger session SDK transport and every in-tree launcher retain their current behavior.
  12. Focused package and end-to-end tests pass through the required engine-dev test path.

14. Known limits and implementation validation points

Cache ownership remains unresolved. P0 keeps the current session-wide DagQL ownership model. An indefinitely live session can keep a large result graph from pruning. P0 must measure this growth and is suitable for controlled evaluation only. Broad release requires a separate design that defines which results, services, and object IDs remain owned.
  • Result formatting: confirm every P0-supported FuncCommand result can be rendered from the saved GraphQL body without a follow-up query. Reject any type that cannot.
  • Response writer: verify gqlgen behavior when the result limit is crossed. Use a writer that drains and records overflow rather than depending on error propagation.
  • Telemetry completion: prove provider flush and SSE drain ordering under terminate and normal completion. Do not shut down creator providers on detach.
  • Attachable health delay: the existing monitor normally requires two failed checks and uses bounded RPC checks. Attach must retry with a visible status; it must not steal an attachment.
  • Callback semantics: P0 intentionally leaves role callbacks bound to current code behavior. The later audit must separate creator, current main, and concrete source client. Do not describe P0 attach as making old client-backed values portable.
  • Request acknowledgment: 202 proves storage and scheduling, not GraphQL validity or eventual success.
  • Empty session: a client that disappears after attachables initialization but before query submission leaves a discoverable session. The CLI terminates it when it can prove no query was acknowledged. Network loss can still leave one; inspect reports no primary query and explicit terminate is the recovery path.
  • Terminal tombstone bound: the one-minute in-memory ID tombstone rejects delayed creator retries after explicit termination. It retains no session resources, expires after the longer-than-retry bound, and disappears on engine restart.
  • Protocol version: detachable clients require an engine containing these routes and metadata fields. Return a direct incompatible-engine error. Do not add fallback behavior that converts a detachable request into an ordinary session.
Recommended implementation boundary: land P0 behind an experimental CLI flag if release policy requires it, but implement the production lifecycle and cleanup paths directly. Do not build a second prototype registry or a test-only execution path that must later be replaced.
