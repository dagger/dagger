1. Scope, approved policy, invariants, and non-goals

A source client is the concrete physical client identified by ClientMetadata.ClientID whose registered session attachable supplies data or performs an operation for an engine object. The term says where the callback goes. It does not create a general client role.

A source client's attachables belong permanently to that physical client. Graceful disconnect makes them unavailable immediately. Abrupt loss makes them unavailable when the existing connection-death path removes their registration. A later observer does not restore, replace, redirect, or rebind them.

Approved behavior: source-dependent work fails at the operation that needs the absent source. The failure does not close the detachable session. It does not cancel an unrelated query. It does not stop an unrelated service. Engine-owned work and data continue.

Invariants

  1. ClientMetadata.ClientID remains the physical callback identity.
  2. mainClientCallerID remains immutable for existing main-client and ancestry semantics.
  3. creatorClientID remains the root creator identity for detachable lifecycle only. Creator callbacks continue to use mainClientCallerID.
  4. currentAttachment.ClientID is lifecycle state. It never becomes a callback fallback.
  5. An observer registers no source attachables and cannot submit /query.
  6. A callback lookup never substitutes the observer, the current attachment, or another client.
  7. A separately registered value with the same session-resource handle may still be selected by the existing candidate algorithm. That is selection among independent bindings. It is not rebinding.
  8. Known source absence fails without the current ten-second lookup delay.
  9. Unknown initial publication retains its bounded wait. This preserves startup ordering.
  10. Ordinary non-detachable sessions retain their current user-visible behavior except that an already-failed host-to-container tunnel stops appearing live and releases its binding.
  11. Only explicit termination and engine shutdown cancel the detachable session root.

Non-goals

This phase does not add callback rebinding, new GraphQL work from an observer, public SDK behavior, dagger up, cache ownership changes, multiple queries, concurrent attachments, engine restart survival, TTLs, names, Cloud scale-out, shell, listen, interactive stream resumption, or cross-engine callback routing. The shared tunnel correction adds no new dagger up product support. It does not make copied data portable across engine restart. It does not change the hidden SDK transport.

Registration and lookup

engine/client/client.go::startSession registers SocketProvider, SecretProvider, Docker auth, TunnelListenerAttachable, terminal, Git, optional pipe, filesync source and target, optional prompt, and optional image-store services. NewSessionAttachablesServer also registers gRPC health. It advertises every method through X-Docker-Expose-Session-Grpc-Method.

startObserverSession calls ConnectSessionAttachables with no attachables. The observer advertises only gRPC health. It does not call daggerConnect. It has no GraphQL client.

initializeDaggerClient implements getClientCaller with context.WithoutCancel, a fixed ten-second timeout, and singleflight.Group. It then calls sessionAttachableManager.Wait. This wait ignores the GraphQL operation's cancellation until its own timeout.

core.Query.SpecificClientAttachableConn uses non-blocking Lookup only when IfAvailable is true. Session-resource candidate selection uses that form. Every other call uses the ten-second wait.

Lookup and request keys

  • sessionAttachableManager.callers, reservations, and waiters use physical ClientID as their only key.
  • sessionAttachableCaller.supported stores lower-case full gRPC method URLs advertised in X-Docker-Expose-Session-Grpc-Method. callerSupports tests a full service descriptor against that set.
  • dagql.Cache.BindSessionResource stores sessionResourcesBySession[sessionID][SessionResourceHandle].byClientID[clientID]. ResolveSessionResourceCandidates orders the requested client first, latestClientID second, and remaining client IDs lexically.
  • Filesync carries LocalImportOpts in X-Dagger-Local-Import-Opts and LocalExportOpts in X-Dagger-Local-Export-Opts. Compatibility import keys are dir-name, include-patterns, exclude-patterns, followpaths, and dagger.gitignore.
  • Socket forwarding carries the concrete URL in X-Dagger-Socket-URLEncoded. Basic image store RPCs carry the image name in dagger.store.tag.
  • GetSecretRequest.ID carries the secret URI. CredentialsRequest.Host carries the registry host. GitCredentialRequest carries Protocol, Host, and Path. ListenRequest carries Addr, Protocol, ConnId, Data, and Close.

Active code versus retained BuildKit code

The active Dagger server does not construct an internal/buildkit/session.Manager. The retained BuildKit local, Git, HTTP, upload, auth-token, cache importer, and cache exporter callback helpers are therefore not reachable through the current Dagger server wiring. Current client metadata still carries UpstreamCacheImportConfig and UpstreamCacheExportConfig, but no active server code consumes them.

This proposal catalogues the active Dagger paths. It records registered-but-unused RPC methods separately. It does not modify retained BuildKit compatibility code.

8.2 Race-safe one-time publication

Add one mutex and one source publication set to daggerSession. The set contains each detachable non-observer ClientID that completed attachable publication. It is not a role registry.

publishedSourceClients map[string]struct{}

func (sess *daggerSession) markSourceClientPublished(clientID string)
func (sess *daggerSession) sourceClientPublished(clientID string) bool

Use this protocol in serveSessionAttachables for a detachable non-observer source:

  1. Read the source publication set. Reject the request if the ID is present.
  2. Acquire a strict manager reservation. Strict reservation rejects a reservation or caller already stored for that ID, even when that caller is no longer active.
  3. While this request still logically owns the reservation, read the source publication set again.
  4. If the ID is now present, release the reservation and reject before hijacking the HTTP connection.
  5. Otherwise hijack, complete the handshake, and call Register. Its Published callback records publication before claim-specific lifecycle work.

The second read closes a real interleaving. Request B can pass its first read. Request A can then publish, disconnect, and be removed. Request B can then reserve the empty manager slot. Without the second read, request B publishes again.

Never hold sourceClientMu while calling Reserve, ReleaseReservation, Register, Wait, or any other operation that acquires sessionAttachableManager.mu. Each publication-set method takes and releases sourceClientMu within that method.

Add a channel-controlled test for the interleaving above. Pause request B after its first read. Publish and remove request A. Resume request B. Assert that its second read releases the reservation, returns the protocol error before hijack, and leaves no reservation or caller.

8.3 Blocking source lookup

getClientCaller first returns an active caller. If no caller is active and the detachable source has published, it returns the immediate source-unavailable error. Otherwise it keeps the existing bounded initial-publication wait.

Extend sessionAttachableManager.Wait with a terminal function. Wait invokes it under manager.mu after finding no active caller and before adding another waiter. The function may only read publication state and return an error. It must not invoke a callback or call another manager operation.

This lock order is safe because publication-set methods never hold sourceClientMu while entering the manager. The terminal function briefly takes sourceClientMu while manager.mu is held.

The terminal check in Wait is sound only because section 8.2 forbids another publication. If republishing remained possible, a published source with no caller could be temporarily absent and the immediate source-unavailable error would be wrong.

IfAvailable does not use the terminal function. It remains a non-blocking Lookup. Candidate exhaustion keeps its current aggregate error.

8.4 Detachable nested shutdown

For a nested client in a detachable session, serveShutdown uses this order:

  1. Flush workspace locks with the current uncancellable flush context.
  2. Flush that nested client's telemetry.
  3. Call sess.attachables.Deregister(client.clientID). Wait for the stored registration to be removed. Treat no manager entry as success.
  4. Close client.shutdownCh through client.closeShutdownOnce.
  5. Return the existing joined flush error, if any.

This order preserves the host callback needed by dirty workspace-lock export. It makes the callback unavailable before the client receives shutdown completion.

  • If dialContext returns and context.Cause(streamCtx) is non-nil, the receive goroutine calls finish(fmt.Errorf("host-to-container listener context ended: %w", cause)) before it exits. It closes any non-nil connection returned with cancellation and sends no connection message. This makes Wait complete when stream cancellation interrupts a dial.
  • Close calls finish(nil) before cancelLocal. A dial released by that cancellation attempts the non-nil finish, but the sticky nil result has already won. If stream cancellation happens without Close winning first, the non-nil context cause wins. A shared Recv or Send error that called finish earlier remains the more specific sticky result.
  • An unrelated dial error with a live streamCtx remains connection-local and sends that connection's close message when the shared stream is still usable.
  • A successful dial takes connsL. If closing is false, it adds the connection to conns and calls drain.Add(1) before releasing connsL. It can start the connection goroutine only after that accounting. If closing is true, it releases connsL, closes the returned connection immediately, and starts no goroutine.
  • Close is idempotent through closeOnce. It calls finish(nil) and then calls cancelLocal to cancel the RPC and its streamCtx. It then locks connsL, sets closing, snapshots and clears conns, and unlocks. It closes the snapshot without holding connsL.
  • After cancellation and connection close, Close acquires sendL, calls CloseSend, and releases sendL. This preserves grpc-go's rule that CloseSend must not run concurrently with SendMsg. Close then calls drain.Wait.
  • The receive goroutine is added to drain before it starts. Every positive connection-goroutine add occurs under connsL while closing is false. Close sets closing under the same lock before it starts drain.Wait. No new connection goroutine can be added after draining starts. A fake dial that ignores cancellation can still return late, but the receive goroutine is already accounted for and closes that connection before it exits.
  • The listener never holds connsL while it closes a connection, takes sendL, calls CloseSend, or waits. A connection goroutine removes its map entry under connsL, releases that lock, and only then closes or sends. finish releases completionMu before cancellation or cleanup. These rules avoid lock inversion among completionMu, connsL, and sendL.
  • In grpc-go v1.80, ClientStream.Context() returns the committed transport stream context. clientStream.finish cancels that context after terminal RecvMsg or client-generated SendMsg failure, caller cancellation, or ClientConn close. The context cause is normally cancellation-shaped. The exact RPC status still comes from Recv. The initial response has already been received before this design reads stream.Context(), as required by grpc-go's API contract.
  • grpc-go v1.80 documents ClientStream.CloseSend as always returning nil. google.golang.org/grpc/stream.go::clientStream.CloseSend and addrConnStream.CloseSend both implement that contract. Stream status comes from RecvMsg. Keep Close() error for the existing internal closer contract, but return nil from the production handle after draining. Do not add closeErr state or a production CloseSend-error branch.

var errTunnelListenerClosed = errors.New("host-to-container listener closed before publication")

AddOrClose appends a handle while the registry is open. If shutdown already marked it closed, AddOrClose copies firstCause, releases mu, and closes the late handle immediately. It records any close error through RecordCleanup and returns firstCause. startTunnel then aborts. The named-return defer joins the recorded cleanup error. This makes listener registration and shutdown atomic without closing a handle under the registry mutex.

BeginClose preserves an existing firstCause, or records its argument as the first cause. A nil cause becomes errTunnelListenerClosed. It marks the registry closed and snapshots all registered handles under mu. It returns the first cause and the snapshot after releasing mu. The caller performs no detach or handle work under mu.

RecordCleanup joins only non-nil cleanup errors under mu. Result reads the stored first cause and cleanup result under the same mutex. The first cause is never included in cleanupErr. This separation lets the startup return include the first cause exactly once.

The registry appends only a non-nil handle returned by a successful listen. It does not preallocate closer slots. A first ListenHostToContainer setup failure therefore closes an empty snapshot. A later-port setup failure closes only handles that were acquired. Neither path can call a nil closer.

One shutdown owner and unconditional resource release

The existing shutdown(cause) closure remains guarded by one sync.Once. It is the only upstream-binding and registered-listener cleanup owner. Setup failure, publication rejection through RunningService.Stop, explicit Stop, listener failure, and upstream exit all converge on it. AddOrClose closes only a late handle that never entered the registry.

Inside shutdownOnce, shutdown uses this exact sequence:

  1. Call BeginClose(cause). This stores the first cause and returns the registered handles in creation order.
  2. Cancel svcCtx with that first cause.
  3. Call Services.Detach once for this tunnel's upstream binding.
  4. Call Close once on each snapshot handle in creation order. Each Close publishes nil only if no terminal result already won, cancels its stream, closes active connections, and drains its goroutines.
  5. Pass only joined Close errors to RecordCleanup.

Shutdown never calls handle Wait. The listener monitor already obtained the sticky terminal result through Wait before it called shutdown. A sibling handle's Close publishes nil and drains it. The first terminal cause remains only in firstCause; it is not added to cleanupErr. This avoids waiting on the monitor that is executing shutdown and avoids duplicating the cause. Outside shutdownOnce, every call returns the current cleanup half of registry.Result. This includes a late-handle close error recorded after the first shutdown call. Another binder can keep the upstream running.

Explicit Stop versus listener completion

The first call that enters shutdownOnce wins the service result. Listener completion alone does not reserve the win. If the listener has finished but its monitor is paused before shutdown, an explicit Stop can win and RunningService.Wait returns the existing successful-stop result. If the monitor enters shutdown first, its listener error remains the service result and the later Stop only observes the stored cleanup result. Both orders close the same handles and detach the same binding once.

  • Use channels and fake clocks. Do not use sleeps to choose race winners.

14. Acceptance criteria

  1. Every active engine-to-client RPC and callback lookup in the catalogue has an exact source identity.
  2. Every value is classified as copied, lazy, permanently callback-backed, engine-owned, or inactive.
  3. Graceful source disconnect prevents new callback lookup immediately.
  4. Abrupt source loss follows existing health detection. Stale lookup during detection never redirects to an observer.
  5. A detachable non-observer source cannot publish again after successful publication, even with the same ID and matching secret.
  6. Pre-publication retry still works.
  7. The two publication reads and strict reservation close the delayed-request interleaving without lock inversion.
  8. A blocking lookup for a published source with no active caller returns SourceClientUnavailableError. The error is recognizable with errors.As.
  9. IfAvailable, secret candidate selection, and socket candidate selection keep their current return and aggregate-error behavior.
  10. Nested shutdown flushes workspace locks, flushes telemetry, deregisters and waits, closes client.shutdownCh, then returns.
  11. The failure does not cancel sess.closingCtx, terminate the session, release session cache ownership, or stop unrelated services.
  12. Copied host snapshots, imported images, plaintext secrets, explicit registry credentials, saved results, telemetry, and engine-owned services continue after source loss.
  13. Source-backed operations fail at their existing resolver, query, execution, or service boundary.
  14. A dead listener is never published as live. Completion is sticky and exactly once. Services.Detach releases only this tunnel's binding.
  15. Ordinary and detachable tests cover first-listener failure, later-port failure, death before publication, and death after publication. They leave no listener or binding behind and do not panic.
  16. Publication is serialized against each listener's actual completionMu. Monitor scheduling is not part of correctness.
  17. The synchronized listener registry closes a successful late handle after shutdown. If a first listener error cancels a later in-flight listen, startup returns that first cause once and does not replace it with the later cancellation error.
  18. Shared stream errors are listener-terminal. Connection-local errors are not. Close publishes local completion, cancels, marks connection registration closed, snapshots and clears active upstream connections, closes them, serializes CloseSend after cancellation, and drains.
  19. Every upstream dial uses the stored ClientStream.Context. External stream-context cancellation during a dial publishes a non-nil sticky result and reaches core shutdown. Close-first cancellation keeps the nil sticky result. A successful dial registers and adds its connection goroutine under connsL, or closes immediately after closing. No wait-group add or connection goroutine starts after Close begins draining.
  20. Shutdown calls BeginClose, cancels svcCtx, detaches once, and closes each snapshot handle in creation order. It does not call handle Wait or add the sticky terminal cause to cleanupErr.
  21. The production listener stores no CloseSend error state. grpc-go stream status remains a Recv/Wait result.
  22. Publication rejection, shutdown failure, and tracked-resource release failure are joined once. Tracked-resource release is attempted even when shutdown fails.
  23. An explicit Stop and an already-finished listener follow the first call into shutdownOnce. Either selected order detaches the binding and cleans up once.
  24. Observer reattachment remains health-only and provides observation, result/telemetry following, lifecycle control, and explicit termination.
  25. Ordinary sessions retain existing startup, wait, shutdown, disconnect, and cleanup behavior except that an already-failed host-to-container tunnel now stops appearing live and releases its binding.
  26. No callback rebinding, general role framework, observer GraphQL work, SDK work, or deferred feature enters the implementation.
  27. Focused unit, race, server lifecycle, CLI, and source-built integration tests pass under the engine-debugging workflow.

15. Explicit deferred work

  • Callback rebinding, replacement, redirection, or migration.
  • Any protocol for an observer to advertise itself as a source.
  • New GraphQL requests from an attached observer.
  • Multiple primary queries or concurrent attachments.
  • Interactive terminal, pipe, stdin, stdout, or stderr resumption.
  • Public SDK detach or attach APIs and SDK launcher changes.
  • dagger up, shell, listen, and other command support.
  • Cache ownership or DagQL pruning changes.
  • Engine restart survival, durable source metadata, TTLs, and names.
  • Cloud scale-out and cross-engine callback routing.
  • A general client-role framework.
  • Changing the existing attachable health policy.
  • Activating retained BuildKit cache importer/exporter or auth-token callbacks.
  • Richer per-callback transport diagnostics and callback-facing helper renames.
  • Changing Host.GetEnv error suppression, implicit Git credential fallback, or established pipe EOF behavior.
Recommended implementation boundary: implement the four required changes: one-time source publication, immediate blocking-lookup failure after source loss, ordered nested shutdown, and shared host-to-container tunnel completion. Do not add detachable-lifetime metadata or broader callback machinery.
