1. Scope, approved policy, invariants, and non-goals

A source client is the concrete physical client identified by ClientMetadata.ClientID whose registered session attachable supplies data or performs an operation for an engine object. The term says where the callback goes. It does not create a general client role.

A source client's attachables belong permanently to that physical client. Graceful disconnect makes them unavailable immediately. Abrupt loss makes them unavailable when the existing connection-death path removes their registration. A later observer does not restore, replace, redirect, or rebind them.

Approved behavior: source-dependent work fails at the operation that needs the absent source. The failure does not close the detachable session. It does not cancel an unrelated query. It does not stop an unrelated service. Engine-owned work and data continue.

Invariants

  1. ClientMetadata.ClientID remains the physical callback identity.
  2. mainClientCallerID remains immutable for existing main-client and ancestry semantics.
  3. creatorClientID remains the root creator identity for detachable lifecycle only. Creator callbacks continue to use mainClientCallerID.
  4. currentAttachment.ClientID is lifecycle state. It never becomes a callback fallback.
  5. An observer registers no source attachables and cannot submit /query.
  6. A callback lookup never substitutes the observer, the current attachment, or another client.
  7. A separately registered value with the same session-resource handle may still be selected by the existing candidate algorithm. That is selection among independent bindings. It is not rebinding.
  8. Known source absence fails without the current ten-second lookup delay.
  9. Unknown initial publication retains its bounded wait. This preserves startup ordering.
  10. Ordinary non-detachable sessions retain their current user-visible behavior except that an already-failed host-to-container tunnel stops appearing live and releases its binding.
  11. Only explicit termination and engine shutdown cancel the detachable session root.

Non-goals

This phase does not add callback rebinding, new GraphQL work from an observer, public SDK behavior, dagger up, cache ownership changes, multiple queries, concurrent attachments, engine restart survival, TTLs, names, Cloud scale-out, shell, listen, interactive stream resumption, or cross-engine callback routing. The shared tunnel correction adds no new dagger up product support. It does not make copied data portable across engine restart. It does not change the hidden SDK transport.

Registration and lookup

engine/client/client.go::startSession registers SocketProvider, SecretProvider, Docker auth, TunnelListenerAttachable, terminal, Git, optional pipe, filesync source and target, optional prompt, and optional image-store services. NewSessionAttachablesServer also registers gRPC health. It advertises every method through X-Docker-Expose-Session-Grpc-Method.

startObserverSession calls ConnectSessionAttachables with no attachables. The observer advertises only gRPC health. It does not call daggerConnect. It has no GraphQL client.

initializeDaggerClient implements getClientCaller with context.WithoutCancel, a fixed ten-second timeout, and singleflight.Group. It then calls sessionAttachableManager.Wait. This wait ignores the GraphQL operation's cancellation until its own timeout.

core.Query.SpecificClientAttachableConn uses non-blocking Lookup only when IfAvailable is true. Session-resource candidate selection uses that form. Every other call uses the ten-second wait.

Lookup and request keys

  • sessionAttachableManager.callers, reservations, and waiters use physical ClientID as their only key.
  • sessionAttachableCaller.supported stores lower-case full gRPC method URLs advertised in X-Docker-Expose-Session-Grpc-Method. callerSupports tests a full service descriptor against that set.
  • dagql.Cache.BindSessionResource stores sessionResourcesBySession[sessionID][SessionResourceHandle].byClientID[clientID]. ResolveSessionResourceCandidates orders the requested client first, latestClientID second, and remaining client IDs lexically.
  • Filesync carries LocalImportOpts in X-Dagger-Local-Import-Opts and LocalExportOpts in X-Dagger-Local-Export-Opts. Compatibility import keys are dir-name, include-patterns, exclude-patterns, followpaths, and dagger.gitignore.
  • Socket forwarding carries the concrete URL in X-Dagger-Socket-URLEncoded. Basic image store RPCs carry the image name in dagger.store.tag.
  • GetSecretRequest.ID carries the secret URI. CredentialsRequest.Host carries the registry host. GitCredentialRequest carries Protocol, Host, and Path. ListenRequest carries Addr, Protocol, ConnId, Data, and Close.

Active code versus retained BuildKit code

The active Dagger server does not construct an internal/buildkit/session.Manager. The retained BuildKit local, Git, HTTP, upload, auth-token, cache importer, and cache exporter callback helpers are therefore not reachable through the current Dagger server wiring. Current client metadata still carries UpstreamCacheImportConfig and UpstreamCacheExportConfig, but no active server code consumes them.

This proposal catalogues the active Dagger paths. It records registered-but-unused RPC methods separately. It does not modify retained BuildKit compatibility code.

A hard closed transport was observed at approximately ten seconds: the checks at five and ten seconds both failed immediately. The removal callback received context canceled, not a diagnostic health error.

The worst bounded blackhole window is larger. The first check starts within five seconds and can consume its 30-second timeout. The queued second check can then use 1.5 × 30s = 45s. Fatal detection can therefore approach 80 seconds. One failed check remains armed through one to four successful checks. Five consecutive successes reset it.

This phase follows the existing death-detection policy. It does not shorten those timeouts. During the detection interval, callbacks retain their current transport behavior. Observer attachment remains independent and never becomes the source.

Explicit termination and engine shutdown

startSessionTermination calls removeDaggerSession. That path calls beginClosing, stops all session services, closes resolver and analytics state, drains DagQL work, releases containers and engine cache session state, shuts down telemetry, and removes result files. Source-unavailable handling never calls this path.

Stale events

sessionAttachableManager.Register currently allows a new registration to replace an inactive caller before the old registration's deferred cleanup runs. The old cleanup suppresses Removed when its exact sessionAttachableCaller no longer owns m.callers[clientID]. That ordinary-session replacement behavior cannot apply to a detachable source after publication.

The detachable non-observer path must reject an already-published source ID. Before it replaces an inactive caller, it must reserve the manager entry and check the source publication set again. The set remains after manager deletion. Observer registrations do not change it. detachAttachment continues to check attachment ID and generation, so a stale creator event cannot clear a separate observer.

7. Reattachment semantics

P0 reattachment provides observation, saved-result retrieval, telemetry following, lifecycle control, attachment close, and explicit termination. It does not provide a GraphQL client. It does not register filesync, secret, socket, auth, tunnel, terminal, Git, pipe, prompt, or image-store services.

The detached query keeps the creator daggerClient and creator metadata. detachedQueryContext restores that identity. mainClientCallerID remains immutable. sessionMainClientConn resolves that immutable ID. No current callback path reads currentAttachment.ClientID.

8.2 Race-safe one-time publication

Add one mutex and one source publication set to daggerSession. The set contains each detachable non-observer ClientID that completed attachable publication. It is not a role registry.

sourceClientMu          sync.RWMutex
publishedSourceClients map[string]struct{}

func (sess *daggerSession) markSourceClientPublished(clientID string)
func (sess *daggerSession) sourceClientPublished(clientID string) bool

Use this protocol in serveSessionAttachables for a detachable non-observer source:

  1. Read the source publication set. Reject the request if the ID is present.
  2. Acquire a strict manager reservation. Strict reservation rejects a reservation or caller already stored for that ID, even when that caller is no longer active.
  3. While this request still logically owns the reservation, read the source publication set again.
  4. If the ID is now present, release the reservation and reject before hijacking the HTTP connection.
  5. Otherwise hijack, complete the handshake, and call Register. Its Published callback records publication before claim-specific lifecycle work.

The second read closes a real interleaving. Request B can pass its first read. Request A can then publish, disconnect, and be removed. Request B can then reserve the empty manager slot. Without the second read, request B publishes again.

Never hold sourceClientMu while calling Reserve, ReleaseReservation, Register, Wait, or any other operation that acquires sessionAttachableManager.mu. Each publication-set method takes and releases sourceClientMu within that method.

Add a channel-controlled test for the interleaving above. Pause request B after its first read. Publish and remove request A. Resume request B. Assert that its second read releases the reservation, returns the protocol error before hijack, and leaves no reservation or caller.

8.3 Blocking source lookup

getClientCaller first returns an active caller. If no caller is active and the detachable source has published, it returns the immediate source-unavailable error. Otherwise it keeps the existing bounded initial-publication wait.

Extend sessionAttachableManager.Wait with a terminal function. Wait invokes it under manager.mu after finding no active caller and before adding another waiter. The function may only read publication state and return an error. It must not invoke a callback or call another manager operation.

This lock order is safe because publication-set methods never hold sourceClientMu while entering the manager. The terminal function briefly takes sourceClientMu while manager.mu is held.

The terminal check in Wait is sound only because section 8.2 forbids another publication. If republishing remained possible, a published source with no caller could be temporarily absent and the immediate source-unavailable error would be wrong.

IfAvailable does not use the terminal function. It remains a non-blocking Lookup. Candidate exhaustion keeps its current aggregate error.

8.4 Detachable nested shutdown

For a nested client in a detachable session, serveShutdown uses this order:

  1. Flush workspace locks with the current uncancellable flush context.
  2. Flush that nested client's telemetry.
  3. Call sess.attachables.Deregister(client.clientID). Wait for the stored registration to be removed. Treat no manager entry as success.
  4. Close client.shutdownCh through client.closeShutdownOnce.
  5. Return the existing joined flush error, if any.

This order preserves the host callback needed by dirty workspace-lock export. It makes the callback unavailable before the client receives shutdown completion.

8.5 Shared tunnel completion

Apply the same correction to ordinary and detachable host-to-container tunnels. Listener death routes through the existing per-tunnel shutdown(cause). It does not cancel the session. Services.Detach releases this tunnel's binding. It stops the upstream only when no other binding remains.

}
  • The private finish(result) method locks completionMu. The first call stores result, sets completed, and closes done. Later calls do nothing.
  • finish publishes the sticky result and returns. It does not cancel or drain work. This prevents a receive or connection goroutine from waiting for itself.
  • Wait waits for done, briefly locks completionMu, and returns the stored result. It returns the same result before or after Close.
  • WithCompletionGuard holds completionMu while it either reports the stored result or invokes its function. It never drains or invokes cleanup.
  • A local upstream connection dial, read, or write failure removes and closes only that connection. The listener sends that connection's close message when possible and continues accepting other connections. Failure of that shared stream Send, or of any other runtime Send or Recv, calls finish with the stream error and is listener-terminal. CloseSend after local Close is the cleanup exception described below.
  • Close is idempotent through closeOnce. It calls finish(nil). It then calls CloseSend under the existing send mutex, cancels the stream context, closes active connections, and drains all receive and connection goroutines. It performs the drain even when completion already contains an error.
  • If CloseSend fails after local Close won completion, Wait still returns nil. Close returns the CloseSend cleanup error. Later Close calls return the same closeErr. If a stream error won first, Wait keeps that stream error and Close still reports only its cleanup result.

AddOrClose appends a handle while the registry is open. If shutdown already marked it closed, AddOrClose releases mu, closes the late handle immediately, and returns errors.Join(closeCause, closeErr). startTunnel then aborts. This makes listener registration and shutdown atomic without closing a handle under the registry mutex.

BeginClose preserves an existing closeCause, or records its argument as the first cause. It marks the registry closed and snapshots all registered handles under mu. It returns the first cause and the snapshot after releasing mu. The caller performs Close, Wait, and Services.Detach only after that release.

The registry appends only a non-nil handle returned by a successful listen. It does not preallocate closer slots. A first-listener failure therefore closes an empty snapshot, and a later-port failure closes only handles that were acquired. Neither path can call a nil closer.

startTunnel creates the registry and the sync.Once-guarded shutdown closure immediately after StartResult acquires the upstream binding. It then assigns startupRollback = shutdown and publishIfReady = registry.Publish. Other service kinds leave both fields nil. The upstream-exit monitor starts at this point, so upstream exit during listener setup uses the same rollback.

startWithKey preserves its existing context.Cause(svcCtx) check under Services.l. If that check passes, it calls publishIfReady before releasing Services.l or inserting the service.

registry.Publish is called while Services.startWithKey holds Services.l. It locks registry.mu. A closed registry rejects publication with its first cause. An empty cause becomes errTunnelListenerClosed. An open registry nests WithCompletionGuard for every handle in listener creation order. The final guarded function inserts the service into Services.running and sets its binding count. If a guard reports completion, Publish marks the registry closed and records that result, or errTunnelListenerClosed for a nil result. It then returns the result without invoking cleanup. The stable lock order is:

Services.l
  → tunnelListenerRegistry.mu
    → hostToContainerListener.completionMu in listener creation order

If completion records first, WithCompletionGuard reports it and Publish rejects synchronously. This does not depend on the monitor goroutine. If publication holds the guard first, insertion commits before completion can record. The same completion records after the guards are released and becomes runtime shutdown.

Terminal completion never calls cleanup while holding completionMu. A monitor calls Wait without registry or completion locks. It calls shutdown(cause) only after Wait returns. An unexpected nil result becomes errTunnelListenerClosed. shutdown releases registry.mu before it closes handles or calls Services.Detach. This prevents inversion with Services.l.

One shutdown owner and deferred startup rollback

startWithKey registers one deferred startup rollback before it calls svc.Start. The deferred function reads running.startupRollback after Start returns. This lets startTunnel install the closure immediately after binding acquisition while keeping the defer active through publication.

For a service with startupRollback, pre-publication error branches leave running.stopFromManager to this deferred function. The function first calls startupRollback(primaryErr). It then calls running.stopFromManager, which reaches the same shutdown closure and performs the existing tracked-resource cleanup. The direct rollback result is not joined separately. The deferred function joins the cached shutdown or resource-cleanup result returned by stopFromManager to the primary error once. This order makes the setup or listener error the cause that wins shutdownOnce.

The insertion callback sets a local published boolean while Services.l and all completion guards are still held. The deferred function sees published == true and skips only the startup invocation. It does not clear or replace shutdown. The same closure remains active for explicit Stop, listener failure, and upstream exit.

The existing shutdown(cause) closure remains guarded by one sync.Once. It is the only binding and registered-listener cleanup owner. Setup errors, publication rejection, the deferred startup rollback, explicit Stop, listener failure, and upstream exit all converge on it. Replace the current startTunnel defer that directly calls stop on rerr; the outer deferred rollback now supplies the original setup error to shutdown. AddOrClose closes only a late handle that never entered the registry. It is the rejection half of the same registry protocol, not another binding cleanup path.

On publication rejection, Publish releases every completion guard and registry.mu. startWithKey then releases Services.l and returns the listener result as its named primary error. Only then does the deferred function call startupRollback and running.stopFromManager. No cleanup path enters the registry or Services.Detach while a publication lock is held.

shutdown calls BeginClose and uses its returned first cause to cancel svcCtx. It releases this tunnel's binding through Services.Detach and closes the snapshot of listener handles. Another binder can keep the upstream running. During setup or publication rejection, listener cleanup errors are joined to the primary setup or listener error. They never replace it. During runtime shutdown, RunningService.Wait keeps the primary terminal cause and cleanup errors are logged. Explicit Stop returns its cleanup error.

After each successful ListenHostToContainer call, startTunnel calls AddOrClose before parsing the returned address or starting the next listen. It starts that handle's Wait monitor immediately after the add. The monitor remains active after publication. First-listener failure, address parsing failure, later-port failure, and a late handle rejected by AddOrClose all return through the deferred startup rollback. Every handle successfully added before failure is in the registry snapshot.
