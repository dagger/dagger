1. Summary and recommended decisions

The current main-client disconnect is a policy trigger for the existing session teardown routine. It is not the only cancellation mechanism available to engine work. The session already has a single session-scoped cancellation context, DagQL session ownership, service leases, container references, telemetry stores, and an explicit teardown sequence. A detachable lifetime can retain those objects by changing when the existing terminal transition occurs.

The proposal makes these choices:

  1. Every top-level session has one engine-owned lifetime policy: attached or detachable. The default remains attached.
  2. The session has one terminal cancellation root. Main-client loss invokes it for an attached session. Main-client loss only clears the current attachment for a detachable session.
  3. A detachable session has one current main attachment at a time. Different main clients may attach sequentially. Concurrent main attachments are rejected.
  4. The engine issues a stable session ID. A user may also assign an optional, engine-wide unique name. IDs are the authoritative identity.
  5. An accepted detachable GraphQL operation runs on the session lifetime context, not on the HTTP connection context. The engine acknowledges acceptance before execution and retains bounded status and result data.
  6. Future role-based callbacks target the current main attachment. Objects that contain a concrete SourceClientID remain bound to that physical client. They are not silently redirected to a different machine.
  7. dagger up needs a session-owned controller that separates engine-native services from client-owned host port publishers. The engine services remain running while detached. Host ports exist only while a main client is attached.
  8. Explicit termination and engine shutdown are terminal. There is no default live-session TTL. Engine restart does not preserve a detachable session.
  9. The public dagger session command provides list, inspect, attach, and terminate operations. The current hidden SDK transport moves to dagger session serve in the same hard protocol cut.
  10. A long-lived detachable session cannot keep every DagQL result it has ever touched as an unprunable active-session root. The first vertical slice may retain the current ownership model for controlled evaluation, but broad availability is blocked on a separate cache-ownership design.

2. Terms, invariants, and scope

Terms

TermDefinition
sessionThe engine-owned lifetime, DagQL ownership scope, clients, services, telemetry stores, and retained operations identified by one session ID.
main attachmentThe current top-level client connection allowed to supply role-based callbacks and submit new top-level work. This is mutable for a detachable session.
creator clientThe physical client that created the session. Its ID is historical metadata. It is not permanent lifecycle authority.
source clientThe physical client ID recorded in a client-backed value such as Secret.SourceClientID or Socket.SourceClientID.
detachClose the current main attachment without terminating the session.
terminateEnter the one terminal transition, cancel session work, release resources, and remove the session from discovery.
retained operationA GraphQL operation that the engine accepted for detachable execution and whose status and bounded final response remain available.

Required invariants

  • Default compatibility: a normal session still ends when its main client disconnects.
  • One authority: only the session terminal transition cancels session-owned work. Detach does not create or cancel a second lifetime tree.
  • Operation isolation: a missing callback may fail the operation that requested it. That error does not terminate the session.
  • Explicit cleanup: a successfully created detachable session remains until explicit termination or engine shutdown.
  • Identity stability: the engine never changes or reuses a live session ID. A name is an alias, not an ownership credential.
  • Source accuracy: a value backed by one client is never presented as if it came from a later client.
  • Bounded retained output: completion data has explicit size limits and is deleted at termination.

Out of scope

This proposal does not add accounts, authentication protocols, authorization policy, ACLs, sharing tokens, multi-tenancy, engine high availability, distributed scheduling, checkpoint and restore, arbitrary stdin resumption, or a workflow database. It uses the same engine connection trust and client metadata that Dagger uses today.

Engine restart boundary

A detachable session survives a main-client disconnect only while the same engine process remains alive. Graceful engine shutdown already removes every session before closing the DagQL cache in Server.GracefulStop. DagQL cache persistence stores cache results and snapshots; it does not persist live session ownership, client attachables, operation goroutines, service processes, or in-memory session metadata. On startup, the engine removes stale retained-operation spool directories. A post-restart list is empty and an old ID returns 404 session not found on this engine process.

3. Current lifecycle

Current connection and teardown sequence

engine/client.Connect
  ├─ choose random Client.ID, SessionID, SecretToken
  ├─ startEngine
  ├─ startSession → GET /sessionAttachables (long-lived h2c connection)
  ├─ subscribeTelemetry
  └─ /init and GraphQL /query

engine/server.getOrInitClient
  ├─ lookup or create daggerSession by client-supplied SessionID
  ├─ first client becomes immutable mainClientCallerID
  ├─ initializeDaggerSession and initializeDaggerClient
  └─ increment daggerClient.activeCount for every HTTP request

last main-client request closes
  └─ releaseClientConnection
       └─ background reapDaggerSession
            ├─ recheck activeCount under lifecycleMu
            └─ removeDaggerSession
                 ├─ beginClosing
                 ├─ stop services and resolver
                 ├─ drain DagQL queries
                 ├─ release containers and telemetry
                 ├─ engineCache.ReleaseSession
                 └─ close shutdownCh and delete registry entry

The central types and paths are daggerSession, releaseClientConnection, reapDaggerSession, and removeDaggerSession.

Current request cancellation

serveQuery calls sess.withClosingCancel(r.Context()). The resulting context ends when either the HTTP request ends or the session begins closing. A network disconnect therefore cancels the in-flight GraphQL handler even before the last-connection reap completes. Session-scoped background APIs can already call SessionScopedContext to remove request cancellation while retaining session cancellation.

Current service behavior

core.Services starts a service with a request-independent context and gives container services dedicated BuildKit resource leases. They run until service detach/stop, dependency exit, or StopSessionServices. Session teardown currently stops them because main-client loss invokes the terminal teardown. The main-client connection is not intrinsically required by an ordinary container service.

Required concern: long-lived session cache ownership

The current DagQL ownership model is acceptable for short sessions but not for indefinitely live detachable sessions. This is a release blocker for broad use, not a reason to delay the first controlled end-to-end slice.

At the refreshed revision, Cache.trackSessionResult records each cache-backed result reached by a session and increments its session ownership. Cache.ReleaseSession removes those roots and decrements ownership only when the session terminates. Detach must not call ReleaseSession, because live operations, services, and retained object IDs still need valid ownership.

The new structural metadata pruner does not solve this lifecycle problem. Cache.PruneMetadataEstimate snapshots active session roots, and pruneActiveClosure excludes their dependency closure from pruning. A detachable session can therefore retain its historical result graph, dependency closures, and associated snapshot ownership until explicit termination even when the global metadata estimate exceeds its pruning target.

The follow-up design must decouple “the session exists” from “every result ever observed by the session remains owned.” It must define narrower ownership scopes for active operations and attachments, plus explicit pins for retained results, live services, and object IDs that reattach promises to preserve. It must also define what becomes invalid when an unpinned result is released. This document does not choose that model yet. The P0 slice keeps current ownership, requires explicit termination, records cache growth in tests, and is not declared ready for broad long-running use.

Fundamental dependencies versus lifecycle coupling

  • Fundamental to a physical client: its filesystem before import, export destination, Unix/SSH socket, host service, host listener, image store, credential helper, credentials file, terminal, pipe, stdin/stdout, prompt that is already in flight, and local SDK process state.
  • Role-based but not tied to the creator: future registry credential fallback, future prompt, future main-only operation, and future host publishing. These may target the current main attachment.
  • Engine/session native: imported snapshots, DagQL results and ownership, explicit in-memory secrets/registry credentials, engine container services, resource leases, engine networking, resolver caches, local telemetry DBs, operation status/results, and session metadata.
  • Accidental lifecycle coupling: main last-connection loss currently calls full teardown, serveQuery uses the HTTP request context, main-role checks compare with immutable creator ID, and up combines engine service ownership with a client host tunnel.

7. Proposed session model

Identity

  • The engine issues an opaque ID in the form sess_ plus 26 lower-case base32 characters. It is unique for the engine process and never abbreviated or reused.
  • A detachable session may have an optional name matching [a-z][a-z0-9._-]{0,62}. Names beginning with sess_ are rejected so ID/name resolution is unambiguous.
  • A name is unique among allocated, attached, detached, and terminating detachable sessions. It is released only after terminal cleanup finishes.
  • All mutating protocol operations resolve a name to an ID once and then operate on the ID. The CLI prints both where available.
  • Session names and IDs do not grant authority. The current engine transport trust remains unchanged.

Session and operation states

allocatedEngine record exists. The initial attachment reservation has not completed.
attachedExactly one current main attachment is registered and healthy.
detachedNo current main attachment. Session resources and accepted work remain.
terminatingTerminal cancellation has begun. New attach and operation submission are rejected.
create detachable ──► allocated ──attachables ready──► attached
                           │                              │
                           │ reservation expires          │ client close/loss
                           ▼                              ▼
                       detached ◄────new attach────── detached
                           │                              │
                           └────explicit terminate───────► terminating ──cleanup──► removed

attached lifetime: last-main loss goes directly from attached to terminating.
engine shutdown: every visible state goes to terminating.

operation: accepted → running → succeeded | failed | canceled | result_discarded
session completion and operation completion are separate facts.

Attachment ownership

A detachable session permits sequential main attachments and rejects concurrent main attachments with HTTP 409. list and inspect are read-only and do not attach. There is no force-steal operation in the first release. An attachment contains a random attachment ID and a monotonically increasing generation. All close and health events clear the attachment only when both values match. This prevents a delayed close from client A from clearing client B.

The session stores both creatorClientID and currentMainClientID. Code that needs historical Cloud/trace metadata reads creator/session metadata. Code that needs a future user callback reads the current attachment. Code that owns a concrete client resource reads its stored SourceClientID.

Recommended first implementation slice (P0)

P0 is one production-shaped vertical path. It proves that the engine, protocol, CLI, and retained GraphQL execution share one coherent detachable lifetime. It does not attempt to make every Dagger feature usable without a client.

Deliberately deferred after P0

Ordered P0 work

  1. Land the lifetime and control foundation. Add the shared wire types in engine/session.go, the registry and control handlers in engine/server/session_control.go, and explicit attach/detach/terminate operations in engine/client/client.go. Split last-main loss from terminal teardown in engine/server/session.go. Preserve the ordinary default and existing cleanup routine.
  2. Land one retained GraphQL operation. Add engine/server/session_operation.go.   3. Land the CLI vertical path. Expose dagger session list|inspect|attach|terminate. Move the hidden SDK transport to dagger session serve and update all in-tree launchers in the same hard cut.   4. Prove the boundary end to end. P0 is complete only when all four layers work together. A session registry without retained execution, or retained execution without the CLI create/attach/terminate path, is not the requested first deliverable. P0 may use current session-wide DagQL ownership for evaluation, but its tests must measure retained metadata growth and broad release remains blocked on the cache concern above.

8. Retained state and result handling

Accepted operation boundary

A detachable client does not send its operation directly to /query. It submits a complete GraphQL request to the operation endpoint. The engine reads and validates the request, creates the operation record, and returns 202 Accepted with the operation ID. Only then does it execute against a context derived from session.lifetimeCtx. If the client disappears after the acknowledgment, execution continues. If the client disappears before the engine accepts the request, no operation is promised.

This boundary is intentionally narrower than workflow persistence. dagger call performs client-side schema discovery and argument conversion before the primary request exists. A crash before primary submission leaves an allocated session with no primary operation. A crash after primary acceptance leaves a resumable engine operation. The engine does not replay unsubmitted CLI steps.

Storage limits and cleanup

The recommended first implementation stores response bodies in session-owned files under <workerRoot>/session-results/<engine-process-id>/<session-id>/. It uses a 16 MiB request-body limit, a 64 MiB response limit per operation, and a 256 MiB total response limit per live session. Completed non-primary responses are deleted after the submitting client acknowledges delivery. The primary response remains until termination. Recent non-primary status summaries contain no response body.

If a primary response exceeds 64 MiB, the work may finish but the operation ends as result_discarded with operation result exceeded the 64 MiB detachable-session retention limit. The session remains live. Termination recursively removes the exact validated session spool directory. Engine startup removes directories from prior process IDs. No result file is used to reconstruct a session after restart.

There is no default session TTL. A TTL would contradict explicit lifetime and could stop a legitimate long-running service. Bounded result storage, startup cleanup, listing by age, and explicit termination address the concrete leak and disk concerns without adding a second terminal clock.

The create/attach response is registered in engine memory before the response is written. The attachment reservation expires after 30 seconds if attachables never register.   • Replace top-level /shutdown lifecycle behavior with the attachment close route. Add one current-client close route for nested client telemetry/lock flushing. Remove the old constant and handler in the same protocol cut; do not keep it as an alias.
  • Keep direct /query for attached sessions and nested clients. Top-level detachable clients route GraphQL through retained operations.
  • Bump MinimumClientVersion/MinimumEngineVersion for the release containing the cut. Old launchers fail version/command negotiation; there is no dual old/new authority.

Attach output and exit behavior

  • A running call/query replays telemetry from its stored cursor, follows live telemetry, prints the final result, and returns the stored operation exit status.
  • A completed call/query prints the retained result immediately and returns 0 for success or 1 for GraphQL/command failure.
  • An up attach creates host publishers, prints current URLs, and follows logs/health. Ctrl+C removes publishers and returns 130. The engine services remain.
  • --no-follow claims the attachment, prints current status/publishers, and exits. Closing the client immediately detaches it.
  • Attaching to a currently attached session returns exit 1 with the current client ID and attachment age. There is no implicit takeover.
  • session terminate returns 0 after cleanup. A repeated engine-issued ID returns 0. An unknown name returns 1.

12. Required subsystem behavior

up controller

The current runUpLocally immediately wraps the module service in host.tunnel and retains only a ready span. The implementation must split it into:

  1. evaluateUpService: evaluate each +up function, keep the engine Service result and a service-manager binding, and wait for engine-side health.
  2. upController: session-owned list of service result IDs, desired port mappings, health/error, ready span, and terminal cleanup.
  3. publishUp: attachment-owned host.tunnel services and actual localhost ports. It starts on attach and stops on detach without releasing the controller's engine bindings.

For explicit fixed host ports, attach fails if the new host cannot bind the port; the backend remains running. For random/zero ports, each attachment may receive a different port. inspect reports backend health and either “not published” or current publisher URLs.

Callbacks

  • Future role callback: resolve current attachment once at call start. If absent, fail immediately. If the RPC fails because that attachment disconnects, do not retry automatically against a new attachment.
  • Concrete source callback: resolve the recorded source client ID through SpecificClientAttachableConn. Equal session resource handle candidates may choose another available binding only through the existing candidate mechanism.
  • Copied value: continue without any attachment.
  • Cloud OAuth refresh: the captured creator credentials file remains creator-bound. Failure affects Cloud export, not the operation/session. A later main is not a safe write target for another host's credentials file.

Telemetry and observability

  • Add structured transition logs with session_id, name, lifetime, old/new state, attachment generation, client ID, operation ID, reason, and duration.
  • Add aggregate engine metrics: live detachable session count, detached count, oldest detached age, retained result bytes, running retained operation count, and terminating count. Do not add per-session metric labels.
  • Expose resource counts and last cleanup/callback error in session inspect.
  • Keep existing telemetry DB cursor replay. Record operation ID and session ID as telemetry attributes so a replay can select the primary operation.
  • Log a warning for sessions detached longer than a configurable engine log threshold, but do not terminate them.

Cleanup order

  1. Under lifecycleMu, transition to terminating, remove name from attach resolution, and reject new attachments/operations.
  2. Attempt bounded workspace/telemetry flush for a live current attachment. Record but do not block on unavailable source clients.
  3. Cancel lifetimeCtx. This cancels retained operations, LLM session-scoped work, and attachment publishers.
  4. Stop the upController bindings and call StopSessionServices.
  5. Close the resolver.
  6. Mark DagQL closing and drain all direct/retained operations.
  7. Stamp final profiling/telemetry completeness and release session containers.
  8. Flush/shut client telemetry providers, keepalive DB references, Cloud exporters, and analytics.
  9. Call engineCache.ReleaseSession(sessionID).
  10. Delete the validated operation spool directory, close shutdown channels, remove registry/name entries, and schedule normal cache GC.

14. Ordered implementation plan

The phases below describe the complete target. Implementation should begin with the P0 vertical slice above, not by completing each broad phase across every subsystem. After P0 is usable, these phases provide the exact follow-up map.

Phase 1: protocol, registry, and lifetime split

  • engine/session.go (new): wire types, lifetime/state enums, descriptors, control endpoint constants, and protocol errors.
  • engine/opts.go: add attachment ID/generation and remove top-level client-chosen session authority.
  • engine/server/session_control.go (new): create/list/inspect/attach/detach/terminate handlers, name and request-ID indexes, attachment reservation, and JSON errors.
  • engine/server/server.go: control routing before session initialization, process instance ID, aggregate metrics, and graceful stop through terminateSession.
  • engine/server/session.go: add lifetime/metadata/attachment fields; rename creator/current-main concepts; split detachAttachment from terminateSession; keep one lifetime context; make reap policy-dependent.
  • engine/server/session_attachables.go: validate attachment reservations, publish ready state, expose health by generation, and produce explicit unavailable errors.
  • engine/client/client.go: create/attach handshake, descriptor, lifetime-aware Close, explicit detach/terminate, and control-only connection for CLI management commands.
  • Remove the old top-level shutdown lifecycle path and bump minimum versions in the engine version constants. Do not add an alias.

Phase 2: retained operation transport

  • engine/server/session_operation.go (new): operation registry, state machine, bounded response writer, spool ownership, wait/result delivery, and cleanup.
  • engine/server/session.go: extract the body of serveQuery so direct and retained operations share schema/workspace/DagQL accounting while choosing different cancellation roots.

Acceptance criteria

  1. Without opt-in, main-client loss has the same user-visible result as the starting revision.
  2. After engine acceptance, a detachable call/query continues when the current main disappears.
  3. A later client can list, inspect, attach, obtain retained status/result, issue new work, and explicitly terminate.
  4. At most one current main attachment exists. Sequential attachments work and stale disconnects cannot clear a newer attachment.
  5. Engine-native services and their leases survive detach. up host publishers accurately reflect the current attachment.
  6. A missing source/role callback fails only its operation. The session and unrelated services remain.
  7. Source-client objects are never silently redirected. New equal session resource bindings work only through explicit handle candidate logic.
  8. Termination cancels operations and releases services, containers, leases, resolver state, telemetry providers/DB references, DagQL session ownership, names, and retained result files exactly once.
  9. Completed primary results and telemetry are available until explicit termination within documented bounds.
  10. Engine restart is documented and tested as terminal. No cache artifact is presented as a reattached session.
  11. CLI help, output, errors, and exit statuses match this document. Go SDK API signatures and close semantics match this document.
  12. No old/new lifecycle RPC coexistence, compatibility alias, or second cancellation authority is introduced.
