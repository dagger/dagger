Detachable dagger up

dagger up --detach starts the project's services in a detachable session, publishes their local ports, prints the addresses, and exits. The engine owns the running services. Local ports are a separate, re-creatable attachment: a small background process serves them, and if it dies or you move to another machine, dagger sessions expose creates them again. dagger sessions terminate stops everything.

The design in one paragraph. Detached up is a real detached session doing real detached work. The invoking CLI creates the detachable session, submits one stored primary query (the existing #13851 machinery), and that query — running in the engine, independent of any client connection — starts the backend services and pins them for the session's lifetime. Ports are deliberately not part of that retained work. A local port is a per-client, per-machine attachment to a running engine service: any client attached to the session can create a fresh host.tunnel against the retained backends at any time, using public API that already exists. up --detach spawns one background port-serving process by default; losing it costs you the ports and nothing else. One gate is lifted to make this work: a client that attaches to a detachable session may now submit work, not just observe.

Decisions Erik has made in review, treated as settled here:

  • SETTLED Lift the observation-only gate: the session's attached client may submit GraphQL work.
  • SETTLED Concurrent port publishing from several clients at once is phased out of this slice, and must not be ruled out by the design.
  • SETTLED The re-publish command is dagger sessions expose.
  • SETTLED Published ports must be visible in the sessions commands.
  • SETTLED Both engine additions are ratified: the internal UpGroup._startDetached field (section 5) and the SessionDescriptor services exposure (section 9).
  • SETTLED Windows support is deferred: this slice returns a clear "not yet supported on Windows" error and adds no Windows handle-inheritance plumbing.
  • SETTLED Names and defaults stand as documented: the --port SERVICE=F:B/PROTO syntax, the --replace and --stop flags, and the state-directory pid/log locations.

1. What happens today

CODE Ordinary dagger up:

  1. upCmd connects with LoadWorkspaceModules, resolves CurrentWorkspace().Services(include: patterns), and calls UpGroup.Run().ID(ctx) — a GraphQL request that blocks until Ctrl-C, which the CLI treats as success.
  2. UpGroup.Run: phase 1 checks declared port collisions and starts every service in parallel via ModTreeNode.RunUp; phase 2 blocks on <-ctx.Done().
  3. runUpLocally evaluates the +up function to get a Service, then immediately wraps it: it selects host.tunnel(service, ports…/native) and starts the tunnel through the session's service manager. Service.startTunnel starts the backend as the tunnel's dependency, waits for health, then asks the client to bind each port.
  4. The bind happens inside the CLI process: TunnelListenerAttachable.Listen runs net.Listen(protocol, "0.0.0.0:port") there and proxies connections over its gRPC stream. Actual ports (including OS-chosen random ones) surface only in a telemetry span name.

CODE The couplings that make plain up die with its client, and the facts that let this design undo them:

  • The backend's only binding is held by its tunnel. When the tunnel dies, Services.Detach releases it and the backend stops. This is why "client went away" currently means "service gone" — it is bundling, not necessity.
  • Tunnel death itself is clean and isolated. The tunnel-lifecycle work on this branch (commits fe85906c3f…90136f800a) makes listener loss converge on one per-tunnel shutdown(cause): sibling listeners close, the tunnel leaves the running set, exactly one detach of its backend binding. Nothing else is touched.
  • Tunnels are per-client by construction. The public Service.start resolver starts tunnel services client-specific (svcs.StartResult(ctx, parent, parent.Self().TunnelUpstream.Self() != nil)), so two clients publishing ports for the same backend get two independent tunnel services. Multi-client publishing is a property the service layer already has.
  • A service started through the public Service.start field keeps running for the whole session in practice: StartResult discards its internal release callback (inside StartResultWithOpts, core/services.go), so that binding drops only at StopSessionServices — or when the service itself exits, which erases its running entry and its binding state (handleExit). Two sharp edges in this machinery matter here and are addressed in section 5: every further start of an already-running service increments a binding count that nobody releases, and Services.Detach releases by service key without checking that the releasing caller's service generation is still the one currently running — a delayed release from a dead old generation can decrement and stop a newer one.
  • Service.ports on a started tunnel returns the running tunnel's actual resolved ports (core.Service.Ports reads RunningService.Ports through a client-specific lookup). A client can learn its real bound ports in-band.

2. Baseline pieces this design runs on

SETTLED CODE From PR #13851, all used as-is:

  • Detachable sessions: client-generated sess_ ID, opt-in via client.Params.Detachable, session survives client disconnect, explicit idempotent DELETE /v1/sessions/{id} termination with tombstone, engine restart terminal, no TTL.
  • The stored primary query: POST …/queries/primary stores the exact request, returns 202, runs it on the session's lifetime context with the creator's client identity, and saves the exact result bytes for GET …/queries/primary/result. Detached up submits its one query through this route — this design uses the machinery exactly as built. One fact to build against: the result route has no wait mode — it returns 409 while the query runs (servePrimaryQueryResult), so completion is observed by polling the status route GET …/queries/primary until a terminal state.
  • The modern ID surface: object id fields return a handle-form ID — an engine-local pointer to the retained result — and Query.node(id: ID!) resolves a handle by direct lookup, typed via an inline fragment. The per-type load<T>FromID root fields and <T>ID scalars are legacy surface, gated BeforeVersion("v0.22.0") in core/schema/legacy_id.go and absent from the schema view current clients execute in. internal/cmd/dagger/up.graphql is the in-repo pattern (node(id: $id) { ... on UpGroup { … } }); every query in this design uses that form. Handle IDs stay resolvable for the whole session because the session retains its results until close (settled cache-lifetime rule) and node resolves them through the session result store.
  • One attachment at a time, sequential, generation-checked; attach retries while a dead holder's registration is being cleaned up.
  • One-time source publication: a physical client's callback services may publish once, ever. After it disconnects they are permanently unavailable and blocking lookups fail fast with SourceClientUnavailableError. No rebinding. (Each new attaching client is a fresh client ID publishing its own attachables once — fully consistent with this rule.)
  • Control routes and CLI: sessions list / inspect / attach / terminate; engine-transport admission is the authorization boundary for all of them.
  • Session-lifetime cache ownership: the session retains the results it used until it closes. A long-lived detached up pins its evaluated results until terminated; the baseline's known metadata-growth limit applies unchanged.

engine.QueryPresentation, for the record, is the small stored record that tells a later sessions attach how to print the saved result (which JSON path, scalar/list/void, raw JSON or not). This design uses it in the smallest possible way: a new kind value "up" whose formatter prints a service table from the saved body instead of walking a response path.

3. The core split: retained services vs. re-creatable ports

The design separates two things that attached up fuses:

Backend servicesLocal ports
What they areThe containers the +up functions return, running in the engine.host.tunnel services: a listener in some client process, proxied to a backend.
OwnerThe session. Started by the stored primary query under a session-retained mark (section 5) that only session termination clears.Whichever attached client created them. Each client's tunnels are its own (client-specific service keys).
LifetimeUntil sessions terminate (or the service itself exits).Until that client goes away or closes them. Dying costs nothing else.
RecoveryNot needed while the session lives.Re-creatable at any time, from any machine that can reach the engine: dagger sessions expose.

Loss in either direction is contained. A port-serving client that dies takes down only its tunnels; the engine-side cleanup for that is the already-landed tunnel-shutdown path, minus the backend stop (the backend's key is session-retained, so the tunnel's binding release does not stop it). A backend that exits does not invalidate the session; the next expose starts it again through its tunnel where the engine can (section 13 covers where it cannot), and the retention mark keeps the restart session-owned.

4. dagger up --detach, step by step

$ dagger up --detach web db
… normal progress rendering: connect, load workspace, start services, publish ports …

Detached session sess_q3h57mabcdefghijklmnop234567
  web  http://localhost:8080
  db   tcp://localhost:15432
Ports served by a background process on this machine (log: ~/.local/state/dagger/expose/sess_q3h57m….log)

Inspect:    dagger sessions inspect sess_q3h57m…
Re-expose:  dagger sessions expose sess_q3h57m…
Terminate:  dagger sessions terminate sess_q3h57m…
$ echo $?
0

In this example web declares port 8080 natively (frontend = backend) and db has a workspace-config [ports.15432] mapping to backend 5432. Those are the only two port shapes dagger up declarations produce — see section 12.

NEW The exact sequence. The CLI stays connected — with its normal frontend — through all of startup, so progress rendering needs nothing special:

  1. Validate flags: --detach with --list is usage exit 2; nested clients (DAGGER_SESSION_PORT) are rejected exit 1 by the existing baseline check ("detachable, observer, and control-only modes are not supported through DAGGER_SESSION_PORT", engine/client/client.go; engine-to-engine connections are rejected the same way). Cloud scale-out needs no new rejection: EnableCloudScaleOut is set only by dagger check and cannot reach up. Old engines fail with the existing ErrDetachableSessionsUnsupported.
  2. Connect as the detachable creator (Params.Detachable, LoadWorkspaceModules) — the existing P0 path. Resolve CurrentWorkspace().Services(include: patterns) and take the UpGroup ID. Zero matching services: error, terminate the session, exit 1.
  3. Submit the primary query through the existing stored-query route: query ($id: ID!) { node(id: $id) { ... on UpGroup { _startDetached } } } with presentation {kind: "up", response_path: ["node", "_startDetached"]}. This is the modern ID surface (section 2); it is the same shape the CLI's own up.graphql uses today, and the legacy load<T>FromID fields are not available in the executing schema view. 202 means the engine owns the request; from here on, CLI death no longer stops the services from coming up.
  4. Wait for the saved result: poll GET …/queries/primary until the query reaches a terminal state (there is no result-route wait mode — section 2), bounded only by command cancellation, then fetch GET …/queries/primary/result. Decoding is two-stage because core.JSON is serialized as a JSON string on the wire (core/json.go marshals the value with json.Marshal(string(p))): walk the response path to data.node._startDetached, then JSON-decode that string into the services payload. One shared decoder serves up --detach, sessions expose, and sessions attach. While the query runs, the creator's identity is live, so module evaluation and secret callbacks during startup route to this still-connected CLI. Query failure: print the saved GraphQL error, terminate the session, exit 1 — before acknowledgement, --detach leaves nothing behind.
  5. Close the CLI's attachment (existing graceful close: creator attachables deregister, attachment clears). The creator's callback services are now permanently unavailable — settled one-time publication — and by this point nothing running needs them.
  6. Run the same ensure-ports step sessions expose performs (section 7): spawn the background port server, which attaches as the session's next sequential attachment, creates the tunnels, binds the ports, and reports the addresses over a pipe.
  7. Print the summary; exit 0. Any failure in steps 5–6 terminates the session and exits 1: no session, no daemon, no ports left from an unacknowledged detach.

The acknowledgement boundary. Exit 0 requires, in order: the saved result (every backend healthy, per _startDetached semantics), then the port server's ready message (every requested listener bound, real ports known), then the CLI's commit byte to the port server (section 7's two-phase handshake). Everything after commit survives the CLI's exit by construction — the services belong to the engine, the ports to the now-independent port server.

5. The stored primary query: UpGroup._startDetached

NEW One internal field. Introspection omits _-prefixed fields (dagql/introspection/types.go), so codegen and every SDK never see it — while the validation schema still contains it, so a wire client can select it. The repository already uses this shape for Host._sshAuthSocket and Query._httpState.

# core/schema/up.go
dagql.Func("_startDetached", s.startDetached).
    DoNotCache("Starts services and retains them for the session").
    Doc("Internal: start all selected services with session-lifetime retention and return their identities. Used by dagger up --detach.")

# Returns core.JSON (serialized as a JSON string on the wire — see section 4):
{"services":[
  {"name":"web",
   "serviceId":"<handle-form Service object ID>",
   "native":true,
   "portMappings":[],
   "backendPorts":[{"port":8080,"protocol":"TCP"}]},
  {"name":"db",
   "serviceId":"<handle-form Service object ID>",
   "native":false,
   "portMappings":[{"frontend":15432,"backend":5432,"protocol":"TCP"}],
   "backendPorts":[{"port":5432,"protocol":"TCP"}]}
]}

portMappings entries carry the nullable frontend field of core.PortForward, and in a recorded payload it is always set: dagger up declarations are either native (native: true, empty mappings, frontend = backend per container port) or fixed-frontend workspace-config mappings, whose frontend is the [ports.<host>] TOML key. A frontend-less (OS-assigned) mapping never appears here; it can only be introduced later by an expose --port override (section 12). Dropping the frontend from a recorded mapping would silently turn a fixed port into a random one, so the round-trip is pinned by tests (section 17).

  • Who calls it: only the stored primary query submitted by up --detach.
  • What it does: the backend half of UpGroup.Run phase 1 — same rollup, same declared-port collision check, same parallel +up evaluation — but instead of wrapping each service in a tunnel, it marks each backend's service key session-retained (the retention mark below), starts it, and waits for health. It creates no tunnels and binds no ports. It rejects a +up service that is not Container-backed, for exact parity with attached up, which fails the same service inside host.tunnel ("tunneling to non-Container services is not supported"); detach must not report success where attached up fails.
  • The retention mark (NEW, core/services.go): the per-session Services manager gains a set of retained service keys, each carrying the service's display name. Semantics: a marked key's service is started normally, but Detach's stop-at-zero path does not stop it while the mark exists; startWithKey re-applies the mark's retention and display name on any later start of that key, so a backend that exited and is restarted by a later tunnel's upstream join stays session-owned; StopSessionServices clears the marks and stops current generations exactly once at termination. Alongside the mark, Detach becomes generation-safe: it ignores a release whose *RunningService is no longer the current entry for its key, so a delayed release from a dead old tunnel cannot stop a newer generation (today it can — Detach decrements by key without that identity check). This is engine-internal implementation of the ratified retention promise, not new product surface: it replaces the earlier idea of leaning on discarded Service.start release handles, which leaks one binding count per call and cannot survive the exit-and-restart window. The mark is session-wide state and records no attachment ID, client ID, PID, or machine state — phase-2 concurrent publishers need no change to it.
  • What each field means: name is the up node's canonical path string, Up.Name() = PathString() (e.g. hello-with-services:web — the same form workspace config's backendService uses). It is the form expose --port SERVICE=… matches against and is plumbed into the running service as a display name for inspect; display layers may separately apply cliName, as up --list does today. serviceId is the evaluated Service's handle-form object ID — an engine-local pointer to the session-retained result; any attached client can later pass it to the public host.tunnel(service:) (the argument is the unified ID scalar) or load it with node(id:). native/portMappings record the declared port semantics exactly as runUpLocally would have applied them (native or fixed-frontend — see the payload note above), so a port server can recreate the tunnels faithfully. backendPorts is display metadata for inspect.
  • Why the result is the persistence: the saved result bytes (existing P0 storage) are the durable record a later expose reads — service IDs plus port specs. No new session metadata store, no new state machine. The handle IDs stay loadable because the session retains its results until termination (settled cache-lifetime rule) and node(id:) resolves a handle by direct lookup in the session result store.
  • Why JSON + DoNotCache: internal-docs guidance: DoNotCache fits scalar-returning fields; starting services is a side effect that must run when called. One caller, one call per session. The underlying Services manager is idempotent per key regardless.
  • Failure: a failed backend start fails the field; the error becomes the saved result. Any siblings that started remain session services; the CLI's pre-acknowledgement rule (terminate on failure) stops them. A CLI that crashed before observing the failure leaves an inspectable session whose saved result is the error — terminate is the recovery, same as any failed call --detach.
  • Attached up untouched: UpGroup.Run, runUpLocally, and module-level Service.up keep their exact current code. The new field shares the evaluation helpers, not the tunnel path.

6. Lifting the observation-only gate

SETTLED Erik approved lifting P0's observation-only restriction: the client holding a detachable session's attachment may submit work. NEW The concrete change:

  • CODE The gate is one check: engine/server/session.go rejects every request from an attach-role client except /sessionAttachables ("observer attachment role is valid only for /sessionAttachables"). Lift it: an attach-role client may use /init, /query, telemetry, and the attachment-close route exactly like an ordinary client of the session. /shutdown stays rejected for detachable attachments (existing check, unchanged) — session lifetime remains control-plane only.
  • Client side, the narrow observer connect path (startObserverSession: no attachables, no generated client) becomes the full path: an attaching client registers the standard attachable set through the existing startSession code and connects the generated client. The consolidation must preserve what each path has today: the observer attach retry loop and OnAttachWait currently live only in startObserverSession, while startSession retries only creator connections — the merged path keeps observer-coded retry while enabling attachables and daggerConnect (which observer mode skips today). Its attachables count as a source publication for its own fresh client ID, so the strict one-time-publication protocol now applies to attach-role registration too (today's code exempts observers; that exemption goes away with the role).
  • NEW Client.Done() is a dedicated, exactly-once signal — not the existing closeCtx, which today is canceled only by local Client.Close, never by transport death. Done() closes when the client's engine-side session connection ends for any reason: attachables/session transport ends, the session is terminated, the engine stops, or the client closes locally. It must never fire early.
  • Per-attachment engine-side cleanup is the existing path and continues to apply: detachAttachment removes the exact attach-role client from the session and runs cleanupObserverClient → cleanupResources (telemetry shutdown, DB-keepalive close). An attach client's own /query work is connection-scoped and ends with its connection; the port server additionally completes all of its startup GraphQL before signaling ready (section 7), so no query is in flight during normal serving. Repeated full attach/detach must return engine state to baseline — the P0 observer test, re-proven for full clients (section 17).
  • Telemetry split. The session telemetry routes replay the creator's stored-primary-query history and stop at its completion bounds (serveSessionTelemetry caps each stream at the bound captured when the query finished). An attached client's own submitted work emits through its own client telemetry (/v1/*) and never appears on the session routes — attach replay cannot observe expose work, and expose work cannot extend or contaminate the stored trace. The port server does not subscribe to telemetry at all: its own log file records its startup and errors (section 9's deferred-live-logs note).
  • What does not change: one attachment at a time, sequential, generation-checked claims and clears; termination authority; the creator's identity as mainClientCallerID for the historical role-callback lookups (retargeting role callbacks to "current attachment" remains future work, exactly as P0 left it). An attached client's own submitted work routes callbacks to itself because callback lookup keys on the requesting client's ID — that is current code, not a change.
  • Scope note: the capability is general (an attached client could submit any query), but the only new consumer in this slice is port publication. sessions attach for call-shaped sessions keeps its current observe-and-print behavior.

Why this is safe under the settled rules: it adds no identity, no route, and no authority that an ordinary same-session client doesn't already have in an attached-lifetime session; it keeps the single-attachment boundary; and every attaching client is a fresh physical client whose sources publish once and die with it. What it deliberately changes is one product restriction P0 chose for its first slice, with Erik's explicit approval.

7. dagger sessions expose and the port server

The command

dagger sessions expose SESSION [--port SERVICE=[FRONTEND]:BACKEND[/PROTO]]... [--replace] [--stop]

Make the session's service ports available on this machine.
Idempotent: if ports are already being served here, prints them and exits.

NEW Behavior, in order:

  1. Control-plane checks (no attachment needed): the session exists; its primary query has presentation kind up (otherwise: "session has no up services"). Then resolve the query's state: running — print "services are still starting" and poll the status route until terminal, bounded only by command cancellation (this is how expose completes the job after a creator crash-after-202, section 11); failed / canceled / result-discarded — print the saved GraphQL error or a state-specific message and exit 1; succeeded — fetch and decode the saved result (the shared two-stage decoder of section 4) for service IDs and default port specs.
  2. Local idempotence via a lock the server itself holds: the port server takes an exclusive flock on <xdg state dir>/dagger/expose/<session>.lock at startup and holds it until process exit, writing its pid record atomically while holding it. expose probes by trying the lock: acquirable means no live server, regardless of what the pid file says — stale records and PID reuse cannot misidentify a stranger process, and signals are only ever sent while the lock shows a live protocol owner. Lock held and the server ready: print its current addresses — read from the engine descriptor (section 9), not from local state — and exit 0. Lock held but not yet ready: report "starting" and wait for readiness rather than printing incomplete addresses. --replace: signal the lock holder, wait for lock release and for its attachment to clear, then continue as a fresh spawn. --stop: same stop-and-wait, then exit — ports gone, session untouched. --stop combines with no other port flag: --stop --port and --stop --replace are usage errors.
  3. Spawn the port server: the same binary with a hidden serving flag, detached from the terminal (Setsid; stdout/stderr to the log file next to the lock file; a status pipe back to the command; a liveness pipe). The handshake is two-phase: the child binds everything, writes its ready message (addresses included), and then waits for a single commit byte from the parent before considering itself independent; if the liveness pipe closes before commit, the child closes its attachment and exits — an abrupt parent death before commit leaves no daemon. After commit the server is on its own: a parent that crashes after committing may leave the acknowledged server and session running, which is exactly the detached behavior the session promises (section 11). On a pre-commit child error: print it, exit 1 — the session is never touched by an expose failure after acknowledgement.

--port adds or overrides mappings relative to the saved defaults (Erik's "add more local ports dynamically"). The merge contract: defaults and overrides are keyed by (service, backend, protocol); an override for an existing key replaces its frontend; a new key adds a mapping; repeated identical keys take the last declaration; an unknown service name (canonical form, section 5) is a usage error. Frontend and backend ports must be in 1..65535; an omitted frontend (--port db=:5432) means the OS assigns one at bind time — this is the only source of random ports in this design (section 12). Fixed (frontend, protocol) collisions are checked across the complete merged set before any tunnel is opened. /udp is rejected up front with a clear error: the h2c listener implements stream listeners only (net.Listen), so UDP tunnels cannot work — attached up has the same limitation today, it just surfaces as a bind error. Changing the port set of a live server is --replace; this slice does not grow a side channel for mutating a running server.

The port server

Definition, once: the port server is the background process that serves a session's local ports on one machine. It is deliberately narrow — no workspace, no module loading, no session ownership:

  1. Attach to the session as the next sequential attachment, via the now work-capable attach path. The existing retry loop (30 s, coded-conflict-only) already covers the window where a dead predecessor's registration is still being cleaned up — with one honest caveat: abrupt-death detection can take up to ~80 s in the worst blackhole case, so an expose racing a blackholed predecessor can exhaust its retry and fail; a later retry succeeds once health clears the registration. If a live holder exists — another machine's port server, or a sessions attach — fail with a message naming the holder's client and hostname (from the attachment metadata in the session descriptor, section 9): concurrent publishing is phase 2.
  2. For each service in the saved result: submit ordinary GraphQL — host.tunnel(service: <saved handle ID>, ports/native), the tunnel's start, then the tunnel's ports for the real bound ports. Every piece of this is existing public API. The tunnel's own upstream join starts the backend if it is running (join) or has exited (restart), and the section-5 retention mark keeps any such restart session-owned — no separate backend start call is needed, which also keeps repeated expose runs from accumulating binding counts. The listeners bind inside the port server via its own h2c attachable; tunnel services are client-specific, so its tunnels are its own.
  3. Write the ready message (name → urls/ports per service) to the status pipe, then wait for the parent's commit byte (section above); all startup GraphQL has completed by this point, so no query is in flight during normal serving. From then on: serve. Exit paths: Client.Done() (section 6) — log, release the lock, and exit 0; SIGTERM/SIGINT — close the attachment (its tunnels die engine-side through the existing shutdown path) and exit 0, leaving the session and backends untouched. A pre-ready or pre-commit failure closes the attachment, waits for its own request cleanup, writes the error to the pipe, and exits nonzero.

Operating-system assumptions: one — a setsid child survives its parent and its terminal, which POSIX guarantees. SETTLED Windows is deferred: the pipe handshake needs Windows-specific handle inheritance; --detach and expose return a clear "not yet supported on Windows" error in this slice, and no Windows handle-inheritance support is added or tested now.

No credential crosses the pipes, argv, or environment. The port server is a normal client: it generated its own client ID and secret, and its right to serve these ports is the attachment claim plus the fact that it created the tunnels it serves — both existing, exact checks.

  • NEW The engine already knows all of this; it is just not exposed. SessionDescriptor gains a services array filled by a new read-only Services.Describe(sessionID) — a point-in-time snapshot of the per-session running map under its existing mutex (a snapshot, not a transaction). Each entry: display name (plumbed through a new ServiceStartOpts.DisplayName, set from the section-5 retention mark for backends — so the name survives a backend restart — hostname fallback otherwise), a kind (container/tunnel/reverse-tunnel, recorded at start time), ports with the existing descriptions, the owning client ID with its hostname from stored ClientMetadata, and — for tunnels — a structured reference to the upstream service's key, recorded at tunnel start. Tunnel-to-backend mapping uses that structured field; the human-readable description strings ("tunnel 0.0.0.0:8080 -> abc123:80") stay presentation-only and are never parsed. The attachment entry in the descriptor also carries its client's hostname, so the expose conflict message can name the holder even when the holder owns no tunnels yet. Because it is a view of live state, it cannot drift: a dead port server's tunnels leave the running map when their streams die, so PORTS drops to 0 on its own — that is the at-a-glance "backends up, no ports anywhere" signal for headless sessions, which matters since there is no TTL.
  • Counting semantics, pinned for the tests: SERVICES counts live non-tunnel backend rows; PORTS counts currently live tunnel frontend ports. An exited backend is absent from the live counts even though it remains restartable from the saved result — inspect shows that truthfully as fewer running services than the saved result declares.
  • What an observer (any transport-admitted client) can do: list, inspect, attach when free (startup replay + saved summary), expose (become the port server), terminate. What it cannot do: take ports away from a live port server (short of terminate), reach ports on another machine through the engine, or — this slice — follow live post-startup logs through the engine. The P0 telemetry routes replay only the creator's stored-query history to the query-completion bound; an attached client's own work never appears there (section 6's telemetry split), live following is deferred, and the port server's log file plus inspect cover the need.

15. Cleanup order and idempotency

  1. Session teardown is the existing removeDaggerSession sequence, unchanged, and remains the only place backend retention ends: StopSessionServices clears the retention marks and stops current generations exactly once. Detached up adds no resource classes to teardown beyond that mark set.
  2. Every tunnel converges on its single sync.Once shutdown — client death, explicit close, teardown — releasing exactly one backend binding, and only against the generation it actually held (section 5).
  3. The port server's local cleanup (attachment close if reachable, pid-record removal, log flush) runs once on any exit path; a SIGKILL skips it harmlessly — the OS releases the held flock with the process, so the next expose sees an acquirable lock and treats the record as dead regardless of PID reuse, and the engine side cleans through stream death and health.
  4. The foreground processes hold no engine resources; their cleanup is closing pipes.

18. Acceptance criteria

  1. up --detach exits 0 only after backends are healthy (saved result) and every requested port is bound (port-server ready, parent-committed); before the commit boundary, any failure or interrupt leaves no session, service, or daemon process (a hard crash of the CLI itself leaves at most the discoverable session states of section 11 — never an uncommitted daemon).
  2. After exit 0: killing the CLI's terminal changes nothing; killing the port server closes ports only; expose restores them from the same or another machine; backends run untouched throughout — including a backend restarted by an expose attempt that later failed, which stays retained.
  3. sessions list/inspect show services and published ports truthfully from live state under the pinned counting semantics (section 9), including the backends-up/no-ports condition.
  4. terminate stops backends, tunnels, and port servers, clears retention marks, releases every engine resource exactly once — with tunnel releases generation-checked — and is idempotent under concurrent signals.
  5. The attach gate lift preserves: one attachment at a time, generation checks, one-time source publication, control-plane-only session lifetime, unchanged ordinary-session behavior, and per-attachment cleanup that returns engine state to baseline across repeated full attach/detach cycles.
  6. Ordinary up and call --detach pass their existing tests unchanged, with golden-output coverage pinning ordinary up's behavior; no SDK surface changes.

19. Phasing and non-goals

  • Phase 2, explicitly not precluded: concurrent port servers (several machines at once). The service layer already supports it — tunnels are client-specific, and each server would hold its own tunnel binding against the retained backends — so the entire cost is the sessions model: allowing multiple concurrent attachments and defining their close/health semantics. Nothing in this slice stores state that assumes one publisher: the retention mark is session-wide and records no attachment ID, client ID, PID, or machine state, and Describe already reports tunnels per owning client. When the attachment rule is relaxed, expose works from N machines with no changes to the port server itself.
  • Deferred with phase 2: sessions attach creating ports interactively (the umbrella design's original attach-and-publish picture). In this slice it would fight the background port server for the single attachment; once concurrent attachments exist it becomes natural.
  • Deferred: live post-startup log following through the engine (the P0 telemetry routes are bounded at query completion); Windows support for the background spawn; role-callback retargeting to the current attachment (P0 status quo); module-level dagger call … up --detach.
  • Non-goals, unchanged from settled scope: engine-restart survival, TTLs, names, Cloud scale-out, callback rebinding, new auth machinery of any kind, workflow history.
