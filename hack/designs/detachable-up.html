Detachable dagger up

This design adds dagger up --detach. The command starts the project's services, prints their local addresses, and exits. The services keep running and their local ports keep working. A small background copy of the dagger CLI keeps them alive. dagger sessions terminate stops everything.

The whole design in one paragraph. dagger up --detach launches a second, hidden copy of the dagger binary. That background process — called the helper in this document — does everything the foreground dagger up process does today: it connects to the engine as an ordinary client, creates a detachable session (from PR #13851), loads the workspace, starts the services, and binds the local ports inside its own process. The visible command only spawns the helper, relays startup progress, prints the final addresses, and exits. Because the helper is the client that created the session, nothing is ever handed from one process to another. There is no new route, no capability, no claim, no token, no publisher role, and no new state machine. The previous design's entire section 7 is deleted, not renamed.

1. What happens today

CODE Ordinary dagger up is one process talking to the engine. The exact chain:

  1. upCmd connects with LoadWorkspaceModules, resolves CurrentWorkspace().Services(include: patterns), and calls UpGroup.Run().ID(ctx). That GraphQL request blocks forever. runServices treats context cancellation (Ctrl-C) as success.
  2. UpGroup.Run runs in the engine. Phase 1: check declared port collisions, then start every service in parallel through ModTreeNode.RunUp. Each start returns only when that service is healthy and its listeners are bound. Phase 2: block on <-ctx.Done(). Nothing after phase 1 watches for service failure; a service that dies later is removed from the running set but Run keeps blocking.
  3. runUpLocally evaluates the +up function to get a Service, selects host.tunnel(service, …), and starts that tunnel service through the session's service manager with Services.Start(…, clientSpecific: true).
  4. Service.startTunnel does the real work. It starts the backend service (health check included), then asks the CLI to bind each port: it calls ListenHostToContainer, which is a gRPC call to the CLI's registered TunnelListener service.
  5. TunnelListenerAttachable.Listen runs inside the CLI process. It calls net.Listen(protocol, "0.0.0.0:port") and proxies every accepted connection over the gRPC stream to the engine, which dials the backend container. The listening socket lives in the CLI process, on the CLI's machine.
  6. The actual bound ports (including OS-chosen random ports) end up in RunningService.Ports. The engine puts them into a telemetry span named ready http://localhost:8080 …. That span is the only place the user sees the addresses. The CLI never receives the port list programmatically.

CODE Ownership facts that this design depends on, all verified in the baseline:

  • Services are session state, not request state. core.Services is per-session (daggerSession.services). Every running service has a binding count. A started tunnel holds one binding to its backend and itself has binding count 1. Bindings drop only through Services.Detach or StopSessionServices at session teardown. A service does not stop because the GraphQL request that started it returned.
  • Host-listener death is observable and convergent. This was fixed in this branch (commits fe85906c3f through 90136f800a). When the CLI-side listener stream dies, the engine-side listener handle's Wait() returns an error, the tunnel's single shutdown(cause) runs once, all sibling listeners of that tunnel close, the tunnel is removed from the running set, and Services.Detach releases the backend binding exactly once. If that was the backend's last binding, the backend is stopped.
  • Partial listener startup rolls back. The tunnel's listener registry closes every acquired listener and releases the backend binding if any listener in the set fails to bind. Multi-port publication is atomic per service.
  • Ctrl-C on ordinary up works because client exit tears down the whole session, which runs StopSessionServices.

The consequence is simple. Everything durable about up already lives in the engine session. The only thing that dies with the CLI process is the process itself: its listening sockets and its callback services. So the correct fix is not to move the listeners somewhere else. It is to make the process that owns them survive.

2. What the sessions baseline provides

SETTLED CODE PR #13851 (this branch) implements detachable sessions. The parts this design uses:

  • A client opts in with the internal engine-client field Params.Detachable. The client generates its own sess_… session ID before connecting (connect). The client's first attachables request creates the engine session and claims its single attachment.
  • Client disconnect does not end a detachable session. Only DELETE /v1/sessions/{id} or engine shutdown does. Termination is idempotent and installs a short-lived tombstone so a delayed creator retry cannot recreate the session.
  • One attachment at a time, sequential, generation-checked. Observers are health-only: they register no callback services and cannot submit queries.
  • A creator's callback services (filesync, secrets, sockets, registry auth, Git, the port tunnel service, and so on) may be published once. After the creator disconnects, the same client can never publish them again, and blocking lookups fail immediately with SourceClientUnavailableError. There is no rebinding.
  • Control routes: GET/DELETE /v1/sessions[/{id}], attachment close, primary-query submit/inspect/result, and telemetry streams. Any client the engine transport admits can call them. dagger sessions list|inspect|attach|terminate already exist.
  • Engine restart is terminal. No TTL. Retained telemetry and any saved query result belong to the session and are deleted at termination.

The baseline piece this design does not use

REC The baseline can also store one "primary query": the engine keeps the exact GraphQL request, runs it detached from the submitting connection, and saves its exact result bytes. Alongside it, engine.QueryPresentation is a small record the CLI stores with the request. Its literal job: tell a later dagger sessions attach how to print the saved result — which JSON path to extract, whether the value is a scalar, list, or void, and whether to print raw JSON. That machinery exists for dagger call --detach, where the product is a result value.

Detached up does not need any of it. The product of up is not a result value. It is a set of running services and bound ports, and those already live in the session's service manager. The query that starts them (section 7) finishes in seconds and its response is consumed on the spot by the helper. Storing that request and its bytes would add nothing a user can see: "attach and print the saved result" is meaningless for a service that is either running or not. So this design submits an ordinary GraphQL request, stores nothing, and QueryPresentation does not appear anywhere in it. What an observer sees instead is defined in section 12.

3. The design: the helper is the creator

NEW dagger up --detach splits into two processes:

  • The foreground process is the command the user typed. It starts the helper, relays startup progress, prints the final summary, and exits. It never connects to the engine, except for one optional best-effort cleanup call on failure.
  • The helper is a hidden mode of the same dagger binary, launched detached from the terminal. It is a complete, ordinary Dagger client. It creates the detachable session, loads the workspace, starts the services, owns every local listening socket, serves every callback, and stays alive until the session ends.

The structural property that makes everything else simple: there is no handoff. The foreground process never owns a session, a listener, a stream, or an engine resource. So there is nothing to transfer, and no moment where ownership is ambiguous. The helper is the original physical creator client, in exactly the sense the source-callback design uses that phrase. The no-rebinding rule is satisfied trivially: callbacks are bound to the helper, and the helper is the process that survives.

Answering the role question directly: the helper is not a new client role. It is the creator, using connectionModeDetachableCreator, which exists today. Its machine, filesystem, environment, and credentials are the same as the user's, because it is a child of the user's command with an inherited environment and working directory.

4. Why no new security mechanism is needed

The rejected design invented a one-use 256-bit capability because it had two processes and needed the second one to prove it was allowed to serve ports for a session created by the first. This design has no such gap. The chain of existing checks:

  1. CODE The helper reaches the engine exactly as any dagger command does: _EXPERIMENTAL_DAGGER_RUNNER_HOST if set, else the default provisioning driver (engine/client/drivers). Reaching the engine transport is the engine's admission boundary today, for every client and every session-control route. The independent-peer-sessions design states this explicitly and this design does not change it.
  2. CODE The session ID is client-generated (engine.GenerateSessionID in connect). The helper generates its own ID. No process needs to pass it identity material; the ID is printed for humans, and it is not a credential.
  3. CODE Every engine request from the helper is checked against its client ID plus its random SecretToken, like any client (getOrInitClient). The helper generated both itself.
  4. SETTLED The right to serve listeners and callbacks for the session belongs to the client that published its attachables first, once, ever. That is the helper. Nothing else can take that role afterward, by the baseline's one-time-publication rule.

Multi-user exactness: every ownership check involved is exact and already exists — client ID + secret token for client requests, attachment ID + generation for attachment operations, one-time source publication for callback identity, and session ID for service keys and teardown. This design adds zero identity fields, zero comparisons, and zero routes. The transferred secrets between foreground and helper: none. The pipes described in section 6 carry status messages and no credentials.

5. CLI surface and command catalogue

The one new flag

dagger up [--detach] [-l | --list] [pattern...]

      --detach   Start services, print their addresses, and exit.
                 Services keep running until 'dagger sessions terminate'.

NEW Rules, each enforced in the foreground process before anything is spawned:

  • --detach with --list is a usage error, exit 2.
  • --detach inside a nested client (DAGGER_SESSION_PORT set) fails with exit 1 and a direct message. The engine client already rejects detachable creation on that path.
  • --detach with Cloud scale-out enabled fails with exit 1, matching the baseline's existing rejection for detachable creation.
  • Engines older than the sessions baseline fail with the existing ErrDetachableSessionsUnsupported message before any service starts.
  • REC The first slice supports Linux and macOS. On Windows the flag returns exit 1 with "not yet supported on Windows" (reason in section 6).

6. The helper process in detail

Spawning and surviving the parent

NEW The foreground process spawns os.Executable() with argv ["up-helper", pattern...] plus the relevant persistent flags, inheriting environment and working directory. Process attributes:

  • Linux/macOS: SysProcAttr{Setsid: true}. The helper gets its own session and process group, has no controlling terminal, receives no terminal-generated signals (Ctrl-C, hangup), and is not adopted-then-killed when the terminal closes. This is the only operating-system lifecycle assumption: a setsid child survives its parent's exit, which POSIX guarantees.
  • Windows: the equivalent is DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP, but Go's ExtraFiles pipe inheritance does not work on Windows; the handshake would need AdditionalInheritedHandles plus handle numbers passed by command line. That is mechanical but fiddly. REC Cut Windows from the first slice rather than ship an untested handshake; the error message says so plainly.

The helper's stdin is /dev/null. Its stdout and stderr are a log file the foreground process creates at <xdg state dir>/dagger/detached-up/<session-id>.log (the xdg.StateHome/dagger directory already exists for the stable client ID). Panics, progress, and post-detach service log lines all land there. The file is a user artifact; termination does not delete it.

The two pipes

NEW Two ordinary OS pipes are passed as inherited file descriptors 3 and 4. They carry status, not secrets, and not identity.

PipeDirectionContent
status (fd 3)helper → foregroundJSON lines. {"event":"session","session_id":"sess_…"} immediately at startup, before connecting. Then exactly one of {"event":"ready","services":[{"name":"web","urls":["http://localhost:8080"],"ports":[{"port":8080,"protocol":"TCP","description":"tunnel 0.0.0.0:8080 -> abc:80"}]}, …]} or {"event":"error","message":"…"}.
liveness (fd 4)foreground → helperNever written. The foreground process holds the write end open. The helper reads it; end-of-file means the foreground process is gone or gave up. Closing this pipe is also how the foreground process tells the helper to abort — it is the portable replacement for forwarding Ctrl-C.

Helper sequence

  1. Verify fds 3 and 4 exist; otherwise exit with "internal command, not for direct use".
  2. Generate the session ID with engine.GenerateSessionID(); write the session event.
  3. Start the liveness watcher: on end-of-file before ready, cancel everything and go to the failure path.
  4. Force plain progress (never the interactive TUI: no terminal, no raw mode, no stdin reading). Connect with client.Params{Detachable: true, SessionID: id, LoadWorkspaceModules: true}. This is the existing creator path: it registers the standard attachables, including the port tunnel service, and claims the session's attachment.
  5. Resolve CurrentWorkspace().Services(include: patterns), then send one ordinary GraphQL request selecting the new field UpGroup._start (section 7). If zero services match the patterns, treat it as a failure ("no services matched") instead of parking an empty daemon.
  6. On success, write the ready event built from the field's response. From this exact write onward the helper is committed: the liveness watcher stops mattering, and only session end or a signal stops it.
  7. Steady state. Nothing to compute. The helper's attachables server keeps serving listener streams and callbacks. Its telemetry subscription keeps feeding the plain frontend, so service startup/exit lines keep appending to the log file. The helper blocks on:
    • Client.Done() (new, section 7): the engine-side session connection ended — termination, engine restart, or network loss. Log the cause, close local resources, exit 0.
    • SIGTERM/SIGINT: call DELETE /v1/sessions/{id} with the same 70-second observation bound the CLI's terminate command uses, then exit. Killing the helper politely therefore equals terminating the session.
  8. Failure path (any error before the ready event was written): write the error event, terminate the just-created session (idempotent; tolerate not-found), and exit nonzero. This mirrors the baseline CLI rule "a failure before acknowledgment terminates the session it created".

Foreground sequence

  1. Validate flags (section 5). Create the log file and both pipes. Spawn the helper.
  2. Copy appended log bytes to its own stderr while waiting (a follow loop on the log file; plain progress is line-oriented and colorless because the helper's stderr is a file). Read JSON events from the status pipe.
  3. On ready: stop the log follow, print the summary and the inspect/terminate/log hints to stdout, exit 0.
  4. On error: print the message and the log path, exit 1.
  5. On status-pipe end-of-file with neither event (helper crashed): print a failure message with the log path; if the session event was received, best-effort terminate through the existing ControlClient; exit 1.
  6. On SIGINT/SIGTERM before ready: close the liveness pipe's write end, wait bounded (30 s) for the helper's error event or exit, print "canceled", exit 130.

The acknowledgement boundary, stated exactly

The foreground process prints success only after all of the following, in order: every backend service passed its health check and every requested listener was bound with its real port known (that is what a successful _start response means, because startTunnel returns only then); the helper wrote ready, which is also the moment it stops aborting on parent loss. Survival of the handoff needs no further proof because there is no handoff: at ready time the helper already owns everything and already runs in its own OS session. The previous design needed an engine readiness endpoint to close a gap between two owners; with one owner the pipe message is sufficient and race-free.

7. Engine and client changes

Three small changes. Everything else in this design is existing code.

7.1 UpGroup._start — start and return, instead of start and block

NEW The problem it solves: today the CLI has no way to learn "all services are up, here are the real ports". UpGroup.run blocks forever and the ports exist only inside a telemetry span name. The helper needs both a completion signal and the port list, in-band.

# core/schema/up.go — internal field, hidden from every SDK
dagql.NodeFunc("_start", s.start).
    DoNotCache("Starts services and binds host listeners on each call").
    Doc("Internal: start all selected services, wait for health and host listeners, and return their bound ports. Used by dagger up --detach.")

# Returns core.JSON:
{"services":[
  {"name":"web",
   "urls":["http://localhost:8080"],
   "ports":[{"port":8080,"protocol":"TCP","description":"tunnel 0.0.0.0:8080 -> abc123:80"}]}
]}
  • Who calls it: only the helper, through a raw GraphQL query (the CLI already sends raw queries this way for up --list via up.graphql).
  • When: once per detached up, right after workspace load.
  • What it does: exactly phase 1 of UpGroup.Run — the same checkPortCollisions, the same parallel RunUp calls, the same started tunnel services — then it ends the per-service ready spans and returns instead of blocking. Run and _start share one extracted function so they cannot drift; Run's behavior stays byte-identical.
  • What each response field means: name is the up node's path string (what --list shows). ports.port is the real bound frontend port from RunningService.Ports, after random-port resolution. protocol and description are the existing core.Port fields. urls is built by the same rule runUpLocally uses today (http, https for port 443, tcp otherwise).
  • Why an underscore field: code generators skip _-prefixed schema surface (verified in cmd/codegen/generator/*/templates), which is the repository's existing convention for internal fields such as Host._sshAuthSocket and Query._httpState. So no SDK gains API, which keeps the settled "no broad SDK additions" boundary. Version gating is therefore not needed for SDK output; the field is still gated to the current view like any new field.
  • Why a JSON scalar and DoNotCache: the internal-docs guidance is that DoNotCache fits scalar-returning fields and fits badly on object-returning ones. This field has one internal caller, returns a small scalar, and starting services is a side effect that must run on each call. The underlying Services.Start is already idempotent per service key, so even a repeated call cannot double-start anything.
  • Failure: any service or listener failure fails the field with the existing error. Started siblings are left to the session, and the helper's failure path terminates the session, which stops them — the same convergence attached up gets from client exit today.

To carry the name and ports out of the shared phase-1 code, runUpStartResult (which today holds only the ready span) gains Name string and Ports []Port. runUpLocally already computes both.

7.2 Running services in the session descriptor

NEW The problem it solves: after the terminal scrollback is gone, the user needs to re-discover what a detached session is running and on which ports. That information exists in the per-session service manager; it is simply not exposed.

# engine/session.go
type SessionService struct {
    Name  string        `json:"name"`            // display name; falls back to the service hostname
    Ports []SessionPort `json:"ports,omitempty"` // bound ports, tunnels only have these on the host
}
type SessionPort struct {
    Port        int    `json:"port"`
    Protocol    string `json:"protocol"`
    Description string `json:"description,omitempty"` // e.g. "tunnel 0.0.0.0:8080 -> abc123:80"
}
# SessionDescriptor gains: Services []SessionService `json:"services,omitempty"`
  • Who fills it: snapshotDetachableSession, from a new read-only method Services.Describe(sessionID) that snapshots the running map under the existing mutex. No stored state is added; this is a view of what already exists, so it can never disagree with reality.
  • Who reads it: sessions list (count) and sessions inspect (full block), for every detachable session — a call --detach session that starts module services shows them too, which is accurate.
  • Name plumbing: ServiceStartOpts gains DisplayName string, stored on RunningService; runUpLocally sets it to the up node's path string. Services started elsewhere leave it empty and fall back to the existing hostname. This is display metadata, not identity; nothing keys on it.

7.3 Client.Done() — let the helper notice the session ended

NEW The problem it solves: when the engine tears the session down (terminate, engine stop) or the network dies, the helper's attachables connection closes and SessionAttachablesServer.Run returns — but nothing outside engine/client can observe that today. Add:

# engine/client/client.go
// Done is closed when the engine-side session connection has ended.
// After Done, callbacks and listeners can no longer be served.
func (c *Client) Done() <-chan struct{}

Implemented by closing a channel when the existing goroutine around sessionSrv.Run returns. The helper blocks on it; nothing else changes. No engine-side change, no protocol change.

Helper-loss semantics: one recommendation, from evidence. REC When the helper dies, everything it was publishing stops: ports close because the sockets lived in it, and backends stop because the tunnels held their only bindings. This is not a policy this design adds — it is what the baseline's tunnel-lifecycle code does, and it is covered by existing tests (core/service_tunnel_test.go, engine/engineutil/client_tunnel_test.go). It is also the right product answer: up services exist to be reached from the host, and a headless, unreachable service burning resources serves nobody. The session itself remains, so the failure is visible in sessions list, diagnosable via inspect and the log file, and cleaned by explicit terminate. The alternative — keeping backends running with no ports, as the rejected design's "publication lost" state did — would require running the up query detached from the helper's connection (the stored-primary-query machinery) and would deliver exactly the unreachable-services state. I looked for a reason to prefer it and found none; this is a recommendation, not an open question.

11. Credentials and callbacks

The rejected design needed a long table of "works after creator loss / breaks after creator loss" because its creator exited at detach time. Here the creator stays. That collapses the analysis into two rows:

PhaseBehavior
While the helper runs (the normal state, indefinitely)Every callback behaves exactly as in attached up, because the same process with the same environment serves it: plaintext and URI/command secrets, Docker credential helpers on a registry challenge, Git credential/config helpers, host directories and files, Unix sockets and the SSH agent, reverse tunnels (host.service dependencies), image load/import. Values already copied into engine storage (imported snapshots, setSecret plaintext, explicit withRegistryAuth, fetched Git snapshots) are engine-owned as always. The only exception: anything needing a live terminal — interactive prompts and terminals fail after detach because the helper has none. up does not use them on its happy path.
After the helper is lostSETTLED semantics apply: fresh callback attempts fail fast with SourceClientUnavailableError; copied values keep working; nothing rebinds. In practice the question barely arises for up, because helper loss also stops the services (section 9) — there is no surviving workload left to request a callback. A failure between the two (a callback in flight during the death window) fails that operation only.

One inherited limitation to state honestly: a detachable creator never calls /shutdown, and /shutdown is where workspace lock-file changes are flushed back to the host. So dagger up --detach does not write lockfile updates produced during module loading back to the workspace. dagger call --detach has the same property in the baseline. Ordinary dagger up is unaffected.

14. Cleanup order and idempotency

Every resource has exactly one release path, and each is already once-only:

  1. Engine session teardown (terminate/engine stop) is the existing sequence in removeDaggerSession: mark removed → stop session services (tunnels first close their listeners via stream teardown, each under its sync.Once; backends force-stopped) → close resolver → drain DagQL → release containers and client resources (this closes the helper's connection) → telemetry/analytics shutdown → release engine cache session → delete registry entry. Nothing new is inserted; detached up adds no resource classes to this list.
  2. Tunnel-level cleanup (helper loss, listener failure, upstream exit, explicit stop) converges on the per-tunnel shutdown(cause), which detaches the backend binding exactly once. Verified by the branch's tunnel tests.
  3. Helper-local cleanup: on Done() or after its own DELETE, the helper runs the existing closeLocalResources (stops the attachables server, closes listeners implicitly with the process, closes the log file) and exits. Running it twice is already guarded by closeCtx.
  4. Foreground-local cleanup: pipes and the log-follow loop end with the process. The foreground process holds no engine resources, so its crash cannot leak any.

16. Tests and fault injection

Unit and package tests

  • core: _start through the existing testListenHostToContainer seam — success returns names, resolved random ports, and URLs; single-listener failure fails the field and rolls back that tunnel; the shared phase-1 function keeps Run's existing tests green unchanged. Describe snapshots names/ports and reflects tunnel death.
  • engine/client: Done() closes when the attachables connection drops and after local close; never closes early.
  • engine/server: descriptor includes services for a detachable session and hides nothing during termination (snapshot remains consistent with the terminating flag).
  • CLI: flag conflicts and exit codes (0/1/2/130); status-pipe event parsing including out-of-order and truncated input; foreground state machine against a scripted fake helper (helper argv injectable for tests); helper refuses to run without fds 3/4; helper failure path terminates its session (asserted against a fake control server).

Integration (through dagger api call engine-dev test, per skills/engine-debugging/SKILL.md; capture to /tmp)

  1. Vertical slice: module with an HTTP service on a fixed port and one on a random port → up --detach exits 0 with both addresses → foreground process gone → HTTP request through each port succeeds → sessions list shows the session with 2 services.
  2. Kill the helper (SIGKILL) → ports refuse connections; backends stop; inspect shows 0 services; session still listed; terminate returns 204 and the session disappears; a second terminate also returns 204.
  3. sessions terminate on a healthy detached up → ports close, containers stop, helper process exits by itself (poll its PID), nothing leaks.
  4. SIGINT during startup → exit 130, sessions list empty, no helper process remains.
  5. Fixed-port conflict (pre-bind the port) → exit 1 with the bind error, no session, no helper.
  6. Callback liveness: a service depending on a host Unix socket (reverse tunnel) keeps serving after the foreground process exits, proving callbacks route to the helper.
  7. Ordinary up regression: unchanged output and cleanup on Ctrl-C; call --detach unaffected.

Fault-injection seams

Reuse, do not invent: the engine's session test hooks (engine/server/session_hooks.go) for terminate/attachment interleavings; the tunnel test seams (testListenHostToContainer, listener completion guards) for port failures; a CLI-level seam substituting the helper executable and the pipe endpoints for handshake races. The only new hook is a channel gate in the helper between _start returning and the ready write, to make the terminate-vs-ready and Ctrl-C-vs-ready windows deterministic in CLI tests.

17. Acceptance criteria

  1. dagger up --detach prints addresses and exits 0 only after all services are healthy and all listeners are bound; closing the terminal afterwards changes nothing.
  2. Killing the foreground process at any moment leaves either nothing (pre-ready) or a fully working detached up (post-ready), never a half state.
  3. Killing the helper closes the ports, stops the services, and leaves an inspectable session showing 0 services; terminate then removes it. No goroutine, container, lease, listener, or process outlives termination.
  4. sessions list/inspect report services and ports from live state; attach fails fast with the documented message; terminate is idempotent under concurrency with helper signals.
  5. Ordinary up, up --list, module-level up, and call --detach pass their existing tests unchanged; no SDK or generated file changes.
  6. All new behavior is covered by the tests in section 16, run through the engine-dev workflow.

18. What the previous design invented, and why none of it is needed

Invented mechanismWhy it existedWhat replaces it
"Publisher" role and processA second process had to serve ports for a session it did not create.The surviving process creates the session. Role gone.
One-use 256-bit capability, stored hashed, consumed atomically; claim routeAuthenticate the publisher to the engine.The helper is a normal client with the normal client ID + secret token it generated itself. Nothing to claim.
GET …/up/publisher restricted h2c routeGive the publisher a listener-only connection.The helper's ordinary attachables connection, which already carries the tunnel service.
GET …/up/readiness endpointLet the parent learn readiness across the two-owner gap.The _start response plus one pipe message inside one owner.
SessionUp state machine (starting/published/lost, publisher generations)Track publication as stored session metadata.Live views of existing state: the services map (ports, names) and the attachment (helper connected or not). Honest costs of this design instead: one hidden CLI mode with a pipe handshake (~the complexity of any daemonizer, fully local and unit-testable); one internal schema field; one exported client channel; display metadata on running services. The helper is a long-lived process on the user's machine — but so is any process serving local ports; that is intrinsic to the product, not to this design.

19. Decisions for Erik

  1. Approve the single engine API addition: UpGroup._start (internal, codegen-hidden, JSON, DoNotCache). It is the only schema change and the load-bearing one. Alternatives examined and rejected: parsing readiness out of telemetry spans (couples the CLI to span names), and exposing each up's Service so the CLI could drive host.tunnel itself (more public API, duplicated engine logic client-side).
  2. Approve the descriptor/services addition (SessionDescriptor.Services + Services.Describe + DisplayName): read-only, derived, and it is the entire observability story for this slice.
  3. Scope cut: Windows deferred. The handshake needs Windows-specific handle inheritance; I recommend a clear error now and a follow-up. Veto means adding that plumbing to the first slice.
  4. Deferred, flagged for a later slice, not blocking: streaming a detached up's live logs through the engine (a sessions attach or sessions logs experience). The engine already retains the telemetry; the session telemetry routes currently require a primary query and a completion bound, so query-less streaming is a small but real extension. The helper's log file covers the need until then.

No other open questions. Helper-loss semantics, the no-stored-query decision, attach behavior, and port semantics are recommendations grounded in current code, stated with their evidence in sections 2, 9, 10, and 12.
