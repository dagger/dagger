1. Glossary: read this first

Every term below is used later in the document. The definitions are concrete: each names the Go type or field it refers to.

Accessor
LazyAccessor: a slot with isSet and a value, guarded by its own RWMutex. The container's snapshot-bearing state lives in accessors; metadata lives in plain fields.
Attempt
One execution of a group's callback, recorded as a lazyEvalAttempt published on the group's cache record: done channel, cancel func, waiter count, final outcome, retry flag.
Body
The function a group runs. On the object side it is wrapped by LazyState.EvaluateGroup; on the cache side by an attempt.
Bookkeeping
The cache-side work after a body: syncResultSnapshotLeases and the operation lease release. Its failure sets syncPending.
Consumed
Object-side: the group's body ran to success (done), or, for an op, every group did (Lazy == nil).
Complete
Cache-side: the group's attempt succeeded through bookkeeping (lazyGroupState.complete). A part is complete exactly when its group is.
Delegation group
A group named by the part it fills whose body evaluates the parent's same part and copies the value.

Waiting on a published attempt instead of leading one.

Whole group

Cache record

Group record

Lease
A containerd lease: a reference that prevents a snapshot from being garbage collected. The cache attaches one lease per snapshot a result holds, after the group body that produced the snapshot finishes.

A converted operation's op implements LazyContainerParts and can run one group at a time. An unconverted op has one whole-value body. The code calls these "refined" and "unrefined".
Per-part evaluation
The change this document describes: evaluating a lazy container one part at a time instead of all at once. In earlier internal documents it was called "stage 2" of the remote-cache work; section 22.3 maps those names.

2. Summary, and the items that need a decision

2.1 What changed

Before this change, a lazy container was evaluated all at once. Reading any piece of it, even the working directory, ran every exec in its chain and materialized every snapshot. Now a container is evaluated per part. There are four kinds of parts: the metadata (config, ports, mount list, and every other plain field), the root filesystem, the exec-metadata snapshot (stdout, stderr, exit code), and one part per mounted directory or file. Each part is produced on demand.

Concretely, for chains built from converted operations:

  • Reading metadata (workdir, envVariable, entrypoint, labels, platform, exposedPorts, mounts, and the rest) runs no exec and materializes no snapshot.
  • container.directory("/out") materializes only the part that /out lives in. Other mounts and the rootfs stay pending.
  • stdout() runs the exec, because the run produces the output, but does not copy the container's read-only mounts.
  • An exec still fills its rootfs, exec metadata, and writable mounts in one process run. One run produces all three.

A second set of conversions landed after this record was first written: from, every mount mutation, every rootfs content writer, and the export family (section 10.5). The operations that still keep one whole-value body are the sources import and dockerBuild, plus services and terminals. Section 10.4 records why the mount and writer conversions mattered more than the earlier design record suggested, and section 17 assesses each deferral, including the ones now done.

2.2 The whole model in one screen

A lazy container is a shell: plain fields plus a handful of accessor slots, and a stored recipe (the Lazy op). Before this change the recipe was one opaque function. Demanding anything ran it, and the function filled every slot.

Per-part evaluation splits the value into parts: metadata, fs, execMeta, and one mount:<target> per directory- or file-backed mount. A caller asks for parts. The container's op maps each requested part to the group whose body fills it. The cache runs at most one attempt per (result, group); the object side runs the body at most once per group. When a body succeeds, every part in its group becomes complete at the same moment, because the body wrote all of their values in one run.

Delegation is what an op does for a part it does not itself produce: the group for that part has a body that evaluates the parent's same part through the cache, then copies the parent's value into this container's slot. Chains of such copies bottom out at the nearest ancestor whose op actually produces the part. Only that ancestor's body does real work; every level above it makes one cheap copy and records that it did, so the copy is never repeated.

There is no per-part attempt anywhere. A part is complete exactly when its group is complete verified (dagql/cache.go:3900 keys the loop by group; no part-level state exists in lazyGroupState, dagql/cache.go:2119).

3. Background: lazy evaluation before this change

This section is self-contained. It describes the machinery that existed before per-part evaluation, because per-part evaluation reuses almost all of it.

3.1 The pieces

  • A cache record (sharedResult in dagql/cache.go) holds one value produced by one API call, the call that produced it, its dependency edges, and ownership counts. Every container returned by the API is wrapped in one.
  • A lazy value is a shell plus a recipe. The container's plain fields are filled in at construction by copying the parent. Its snapshot-bearing state sits in accessors (LazyAccessor): FS for the rootfs, MetaSnapshot for the exec metadata, and one source accessor per mount. The recipe is an op object stored in Container.Lazy. For withExec it is a *ContainerExecLazy. Calling withExec runs nothing; it stores the op.
  • Cache.Evaluate forces a lazy value. Per cache record it keeps at most one run of the recipe in flight, called an attempt. The first caller starts it and runs the recipe's body in a goroutine. Other callers wait on the same attempt. The last waiting caller that gives up cancels the body. A failed body leaves the record retryable.
  • Bookkeeping after the body. When the body succeeds, the cache attaches one containerd lease per snapshot the value now holds (syncResultSnapshotLeases), so the snapshot store cannot garbage-collect them while the record exists. If the body succeeded but this step failed, a flag (syncPending) makes the next attempt rerun only the bookkeeping, never the body.
  • The schema decides eager versus lazy per mutation. A resolver such as withEnvVariable clones the parent's shell, applies its edit, and installs an op only if the parent is still pending (cloneContainerForSchemaChild, core/schema/container.go:3390; the fork at core/schema/container.go:2118). Snapshot-producing mutations (withExec, withDirectory, every mount mutation) install an op unconditionally. Section 10.4 lists which is which.

3.2 The problem

The recipe was one body for the whole value. Every container mutation body began by evaluating its parent completely and copying all of the parent's state (materializeContainerStateFromParent, core/container.go:1048). Every metadata resolver, for example workdir, called Evaluate on the whole parent. So one metadata question at the tip of a lazy chain ran every exec in the chain and materialized every snapshot, including uploads of mounted host directories that the question did not need.

3.3 What this change adds, in one sentence each

  • A value can declare that its deferred work splits into named groups, and can map each part of itself to the group that produces it.
  • The cache keeps one attempt per (record, group) instead of one per record, using the same attempt machinery.
  • The op keeps one run-once flag per group instead of one per op.
  • Converted operations produce only the parts they change and copy the rest from the parent on demand. Copying on demand is called delegation.
  • Unconverted operations behave exactly as before: one group, one body, everything at once.

4. What a part is

A part is a name for one separately demandable piece of a value. In dagql it is an opaque string (PartKey, dagql/types.go:179). The container package defines four kinds verified (core/container_parts.go:19-31):

Things that are not parts, and why:

  • Cache, volume, and tmpfs mounts. They have no snapshot accessor. Their existence is metadata; their content is a dependency result (a cache volume) or nothing. containerSnapshotParts skips them verified (core/container_parts.go:311).
  • Secrets, sockets, services. Dependency results referenced from metadata, not pieces of this value.
  • Directory and File. They keep one implicit whole-value unit. They implement only HasLazyEvaluation, so the cache treats them as a single LazyGroupWhole group (core/directory.go:128, dagql/cache.go:3801).

4.1 Mount parts are keyed by target path

A mount list never holds two entries with the same target: ContainerMounts.With drops any existing mount at the same target or beneath it before appending verified (core/container.go:5209). So mount:/src is a stable name across add, remove, and replace, and a child can find "the parent's same part" with a lookup by target (mountAt, core/container_parts.go:551) instead of an index translation. Persisted lease roles stay positional (mount_dir:%d, core/container.go:1229); that is safe because the mount list is settled by the metadata part before any mount part fills (section 7.2).

4.2 A part is a name, not a thing that runs

This is the first idea to hold on to. A part has no attempt, no mutex, no callback. It is a label a caller uses to say what it wants, and a label the value uses to say what is done. Everything that runs is a group.

5. What a group is, and why it is not a part

A group is one unit of deferred work: one body, one attempt record in the cache, one done flag on the op. Every part of a value maps to exactly one group. A group may fill many parts. That many-to-one direction is the entire reason groups exist as a separate idea.

5.1 Why the exec needs a many-part group

Running a process produces the new rootfs, the meta snapshot, and the new content of every writable mount in one physical run. You cannot ask a process for "just the rootfs". So the exec maps fs, execMeta, and every writable mount:<t> to one group, execOutputs verified (core/container_exec.go:138-160). Demanding any one member joins the single run; when the run succeeds, all members are complete at once.

5.2 Why a metadata-only op needs one group per part

withEnvVariable produces nothing but a field edit. Its rootfs, meta snapshot, and mounts are the parent's, copied. If those copies shared one group, demanding the child's fs would also force the parent's execMeta and every mount. So Template A gives every snapshot part its own group, named by the part itself verified (templateAContainerGroups, core/container_parts.go:325; containerDelegationGroup, core/container_parts.go:53).

The distinction in one sentence. A part answers "what do you want, and is it done?". A group answers "what has to run to make it done, and has that run?". They are distinct because one run can make several things done, and because the bundling differs per op while the names do not.

6. Where the "is it done" state lives

Three Go structs hold "done" information about one lazy container. They are in different packages. They are updated at different moments. They are protected by different mutexes. This section shows the actual fields of each struct, explains every field in plain words, and then shows the values of those fields at four moments for one concrete container.

Terms used in this section:

  • Result. The cache's entry for one value. Go type sharedResult in dagql/cache.go. Every container returned by an API call has one.
  • Op. The recipe object stored in the container's Lazy field. For withExec it is a *ContainerExecLazy. Every op embeds a struct named LazyState.
  • Accessor. Go type LazyAccessor. A struct with three fields: a value, a bool isSet, and a mutex. The container's rootfs, its exec metadata snapshot, and each mount's source are stored in accessors.
  • Attempt. One run of a group's work by the cache. Go type lazyEvalAttempt. It exists from the moment a goroutine is started for the group until that goroutine finishes.
  • Bookkeeping. Work the cache does after a group's body succeeds. Concretely: for every snapshot the container now holds, attach a containerd lease so the snapshot cannot be garbage collected while this result exists. Function syncResultSnapshotLeases, dagql/cache.go:1519.

6.5 One ordering fact

Inside the attempt's goroutine, the order is: run the body, which sets place 2's done to true; then run bookkeeping; then take lazyMu and set place 1's complete to true and attempt to nil. So there is a window in which done is true, complete is false, and attempt is non-nil. 8. Delegation, exactly

Definition. A delegation group is a group whose body does two things and nothing else: (1) evaluate the parent result's part with the same name, through the cache; (2) copy the parent's value for that part into this container's accessor for that part. The group is named by the part it fills. Delegation is not a pointer, a redirect, or a shared slot: the child ends up with its own accessor holding its own copy. 

core/container_parts.go:430-511, the fs and mount armsfunc delegateContainerPart(ctx, dst *Container, parent dagql.ObjectResult[*Container], part dagql.PartKey) error {
    parentCtr := parent.Self()
    switch {
    case part == ContainerPartFS:
        cache.EvaluateParts(ctx, parent, part)                              // (1) parent's same part, via the cache
        cloned, _ := CloneContainerDirectoryAccessor(ctx, parentCtr.FS)     // detached *Directory, reopened snapshot ref
        copyContainerDirectoryAccessorValue(dst.ensureFSAccessor(), cloned) // (2) overwrite dst's slot, unconditionally
        return nil
    case strings.HasPrefix(string(part), "mount:"):
        target := strings.TrimPrefix(string(part), "mount:")
        dstMnt := dst.mountAt(target)          // dst's mount list is settled metadata by now
        cache.EvaluateParts(ctx, parent, part)
        parentMnt := parentCtr.mountAt(target) // parent's mount at the same target
        cloned, _ := CloneContainerDirectoryAccessor(ctx, parentMnt.DirectorySource)
        copyContainerDirectoryAccessorValue(dstMnt.DirectorySource, cloned)
        return nil
    }
}

8.1 The recursion: how a request on the child reaches the ancestor that owns the work

Consider base = from(img).withExec(cmd), A = base.withEnvVariable(k, v), B = A.withWorkdir("/w"), all pending. A caller asks for B.fs.

8.2 Ownership: whose attempt does the work

  • Each result owns its own group attempts. The caller's EvaluateParts(B, fs) leads (B, fs). Inside that body, B's delegation code calls EvaluateParts(A, fs), which leads (A, fs) in a new attempt on A's shared result, with its own operation token, its own goroutine, its own waiter count. The chain is a stack of nested leaders, not one attempt spanning results verified (every level calls cache.EvaluateParts, core/container_parts.go:441, 371; every call goes through beginEvaluateOne and takes a token, dagql/cache.go:3732).
  • The physical work is owned by the ancestor that produces the part. In Figure 4 that is (base, execOutputs). If another caller had already run base's exec, A's and B's delegation bodies find base.fs complete and only copy.
  • Cancellation cascades by waiter count. Each attempt runs on a context detached from its caller's cancellation (WithoutCancel plus its own cancel cause, dagql/cache.go:3998). The last waiter to abandon an attempt cancels its callback context (dagql/cache.go:3680-3686). If B's attempt is canceled, B's body (a waiter on A's attempt) leaves; if it was A's last waiter, A's attempt is canceled; and so on down. A later healthy caller that joins an attempt which died of its own cancellation retries it (dagql/cache.go:3662-3670; tested at dagql/cache_parts_test.go:555).

8.3 Pre-seeding: why "already set" is not "already right"

Schema resolvers build a child's shell by cloning whatever the parent's accessors hold right now, without evaluating the parent verified (cloneContainerForSchemaChild, core/schema/container.go:3390-3430, uses CloneContainerDirectoryAccessor, which only Peeks). For an evaluated parent that clone is the final value, and the schema applies the mutation eagerly with no lazy op. For a pending parent the clone can be stale: 

evaluated E (FS = /old)  ->  P = E.withDirectory("/x", d)   (unrefined; shell keeps a clone of /old; body will produce /new)
                         ->  C = P.withEnvVariable(k, v)     (Template A; shell clones P's shell: /old again)

C's FS accessor is set at construction and holds the wrong rootfs. A delegation that trusted set-ness would serve /old and never run P's body. So the rule, enforced in code: a delegation body always evaluates the parent's part and always overwrites the destination slot verified (core/container_parts.go:441-449 has no "if set, skip" branch; pinned by core/container_parts_test.go:326). The exec goes further and resets its output accessors to fresh empty ones at construction (core/container_exec.go:1278-1293), but that reset is belt on top of the rule, not a substitute.

The metadata copy has a matching rule. materializeContainerMetadataFromParent rebuilds the mount list from the parent's shape and carries over the child's existing accessor record for a mount whose target and kind match, so the pointer the delegation group will later fill stays stable; it never copies parent accessor values verified (core/container_parts.go:379-409).

8.6 A delegated copy runs as soon as the parent's part is final decided and implemented 2026-09-04

The record originally said a delegation group runs only when its part is demanded. That rule was wrong when the parent's part is already final: the copy costs one clone and forces nothing, and leaving it unconsumed keeps the op pointer set. Two bugs followed. A from on the scratch root kept its execMeta and mount copy groups unconsumed after the pull, so it reported pending forever and the TUI rendered it as never finished. An exec with a read-only mount kept that mount's copy unconsumed after stdout(), so the container was persisted as a recipe and the exec ran again after a restart (section 19.4).

The corrected rule: after any group body of a refined op succeeds, and before the op checks whether it can clear its pointer, it runs every not-yet-consumed delegation group whose parent part is already final. "Final" means the parent container's op pointer is nil, or the parent's op is refined and reports that part's group consumed. A copy whose parent part is not final is never run, because that would force parent work nobody asked for. The copies run through the normal delegation body under their own group mutex, inside the current attempt's callback, so their snapshots get leases in the same bookkeeping pass.

Consequences: a from is fully consumed after its pull; an exec with read-only mounts is fully consumed after its run, because the run already evaluated the parent's mount parts; a Template A child on a pending parent is unchanged, since none of its parent's parts are final yet.

11.5 Concurrent callers requesting different groups

Caller 1 runs EvaluateParts(A, fs); caller 2 runs EvaluateParts(A, execMeta) at the same time.

  1. Both resolve. Both self-demand (A, metadata). Whichever arrives first leads it; the other joins the published attempt or finds it complete.
  2. Caller 1 leads (A, fs); caller 2 leads (A, execMeta). Two attempt records, two goroutines, two operation tokens.
  3. Object side: EvaluateGroup gives each group its own lazyGroupOnce.mu. The two bodies run concurrently. LazyMu is held only for the map lookup.
  4. Both bodies demand X's parts; both end up at (X, execOutputs). One leads, the other joins. The process runs once.
  5. Each attempt finishes with its own syncResultSnapshotLeases(A); those two syncs serialize on leaseSyncMu, which is the only place the two callers wait on each other beyond short critical sections.

Tested with rendezvoused bodies at dagql/cache_parts_test.go:305.

11.6 Concurrent callers requesting the same group

Caller 1 and caller 2 both run EvaluateParts(A, fs). The first to reach the top of the loop under lazyMu finds no attempt and leads, publishing an attempt with waiters = 1. The second finds g.attempt != nil, increments waiters, and waits on attempt.done. Both get the same error or success. Three refinements verified:

  • If caller 2 cancels its own context, it decrements waiters and returns its own cause; the attempt keeps running for caller 1 (dagql/cache.go:3677-3687).
  • If every waiter leaves, the last one cancels the callback context. The body returns the cancellation; the attempt records retry = true. A caller 3 that joined just before the attempt finished sees retry, and, being healthy, loops and leads a fresh attempt instead of returning someone else's cancellation (dagql/cache.go:3662-3670; tested at dagql/cache_parts_test.go:555).
  • Waiters retain the attempt record they joined. A retry publishes a new record, so an old waiter never reads or decrements a successor's state (dagql/cache.go:1904-1910).

A direct object-side caller (for example A.Evaluate(ctx)) racing the cache attempt on the same group blocks on g.mu and then observes done. It does not consult the cache attempt, and its completion is not recorded in the cache record (section 19, open question 1).

11.9 Nested lazy container chains, including an unrefined link

Figure 4 covered a fully refined chain. Now put an unrefined op in the middle: E evaluated, Q = E.withDirectory("/x", d) (unrefined), C = Q.withEnvVariable(k, v). The caller runs EvaluateParts(C, fs).

  1. C resolves: self-demand (C, metadata) → body calls EvaluateParts(Q, metadata).
  2. Q's ResolveLazyEvalGroups sees a non-LazyContainerParts op and returns [whole] with no self-demand verified (core/container_parts.go:161-163).
  3. evaluateGroup(Q, whole) leads; LazyEvalFuncForGroup(whole) returns Q's old-style body: Evaluate(E), materializeContainerStateFromParent (all of E, copied wholesale), WithDirectory, consumeLazyOp (core/container.go:3739-3756). Q is now fully materialized; everything about Q is complete in one attempt.
  4. Back in C: the metadata copy reads Q's settled fields. Then C's fs delegation group demands EvaluateParts(Q, fs): Q's resolution now finds Lazy == nil, returns no groups, and the cache routes to pendingLazyGroups(), which is empty because (Q, whole) is complete and settled; the call returns immediately (dagql/cache.go:3817-3833). C copies Q.FS, which now holds /x.

So an unrefined link costs exactly what it cost before this change, and laziness resumes above it. The converse composition is also conservative: an unrefined child's whole body calls cache.Evaluate(parent) on a refined parent, which runs every group of the parent.

11.10 The intended future single-part remote-cache pull (not implemented)

Nothing in this branch pulls a snapshot. The seam is the shape of the two interfaces, and it is worth seeing exactly what the seam is and is not.

  • What exists. ResolveLazyEvalGroups is computed per call from the op and settled metadata. LazyEvalFuncForGroup returns one body per group. A future learned result could, in principle, answer fs → "pull:fs" and expose a body that fetches the rootfs snapshot into the FS accessor. The cache would run it as any other group: one attempt, one complete flag, retry on failure.
  • What does not exist. No pull group. No body that fetches anything. No notion of "this group is viable" or "this group is exhausted". No way for a group's failure to change the mapping for the next caller. No exclusion between two groups that would both fill fs. clearLazyWhenConsumed asks the op for the full group set by shape and expects that set to be static.
  • What the current code asserts instead. Once metadata is settled, a part's group is deterministic and does not change (the contract comment at dagql/types.go:195-202; the design's PartServedByItsGroup model invariant).

11.11 The unimplemented fallback/remapping and the two-producer race

Suppose a future resolver did remap: caller 1 resolves fs → pull:fs, the pull fails or is exhausted, and caller 2 later resolves fs → execOutputs. Here is what the implemented machinery would and would not do, so the boundary is concrete inference:

14. Observable behavior changes

14.1 A failing exec no longer fails a metadata read verified

from(img).withExec(["/bin/false"]).workdir() used to fail, because workdir evaluated the whole chain and the exec returned nonzero. It now returns the working directory, because the exec's metadata group copies from the parent without running the process. sync(), stdout(), directory(), or any other demand of an exec output still runs the exec and still fails. This is the existing laziness contract applied consistently: an exec nobody demanded never ran before either. It is the one change a user can notice without reading code. A test asserts it on purpose (core/container_exec_parts_test.go:33).

14.2 Expanding a stale volatile variable name now errors instead of expanding to empty verified

Before: after an exec ran, the container's VolatileEnv list was filtered down to names that resolved in the current session, as a side effect of the exec body resolving values. So a later expand: true reference to a volatile name whose session binding was gone expanded to the empty string, because the name had been dropped from the list.

Now: the list is copied from the parent unfiltered, and that reference errors with "expand cannot be used with volatile env variable". Reaching this requires a container reloaded in another session, or across a restart, that carries a stale volatile name, plus an expand: true reference to that name. The implementation team ruled the new explicit error acceptable, because preserving the old behavior exactly would require either a snapshot body writing metadata or metadata reads that run execs. A test pins the new behavior (core/container_exec_parts_test.go:131). This ruling was made without Erik; it is listed in section 18.

14.3 Syncing a container no longer materializes every ancestor inference

Evaluate(child) demands only the ancestor parts the child's groups consume. Example: the child is withEnvVariable on an exec whose parent is another Template A op. Syncing the child runs the exec, which materializes its parent's rootfs and mounts, but the parent's own execMeta delegation group is never demanded and stays pending. Before this change every ancestor was materialized completely. Nothing user-visible depends on that today, but code that assumed "synced means all upstream results are materialized" no longer holds.

14.4 Mount mutations on an evaluated parent apply at call time verified

After the conversion of the metadata-only mount mutations, their resolvers fork on parent state like the other metadata-only mutations: on an evaluated parent the edit is applied at the API call and no op is installed. One consequence is observable. withMountedCache's helper initializes the cache volume's snapshot when the volume has none (core/container.go:6153-6157), so on an evaluated parent that initialization, and any error it produces, now happens at the mutation call instead of at the first evaluation. On a pending parent it still happens inside the metadata group.

14.5 Ownership by name still reads the parent's rootfs verified

withMountedSecret and withUnixSocket accept an owner. When the owner is a name rather than a numeric id, resolution reads /etc/passwd from the parent's root filesystem (ownership, core/container.go:7270-7293, through the file selector). After their conversion that read happens inside the metadata group, so a metadata demand on such a child evaluates the parent's rootfs part. This is narrower than before, when it evaluated the whole parent, and it is not a rule violation, because the demand is on the parent. It is an exception to the general statement that metadata groups never touch snapshots, and it is stated here so the exception is not mistaken for a defect.

14.6 A bad Dockerfile-compat mount source path errors at first demand verified

After the conversion of the Dockerfile-compat mount, the resolver decides at call time whether the source path is a file or a directory and records that kind in the mount entry. A source path that names a file but carries a directory hint (a trailing slash) used to fail at the mutation call. On a pending parent it now fails when the mount part is first demanded, with the same error. On an evaluated parent it still fails at the call.

14.7 What does not change

Lookup, hit selection, cache identity, the e-graph, session-resource enforcement, release, prune, shutdown, and persistence formats are untouched. An engine whose workloads never read metadata on pending chains behaves as before at the same hot-path cost: the completed-result fast path is one mutex lock and one bool check, and values that never split allocate no new state.

14.8 What the telemetry goldens exposed on the pull request verified

The TUI golden tests in dagql/idtui failed on the first CI run of the pull request. Twenty subtests, three causes, none of them acceptable as a golden update. All three were fixed and the goldens passed unchanged on the next CI run (section 10.5).

  • from rendered as never finished. The TUI marks a call pending when it returns a lazy result and clears pending when a resume span for that result completes. A from whose rootfs was consumed still had unconsumed copy groups, so it was reported pending forever and never reported cached. Fixed by the rule in section 8.6.
  • A blocked call rendered as succeeded. A call now has one resume span per group. In the pending fixture the last withExec after a failing exec had its metadata resume span complete cleanly and its output resume span blocked; the TUI cleared pending and rendered a process that never ran as done. Fix: a resume span is marked partial when the result still has outstanding work when that attempt ends, and the TUI ignores partial resume spans when clearing pending. The decision is made in the same critical section that retires the attempt, so two groups finishing together cannot each see the other as unfinished and both be marked partial, which would leave a fully evaluated call pending forever.
  • An abandoned attempt rendered as a failure. With the groups of one call running concurrently, one group's failure cancels the others' waiters; a sibling attempt whose last waiter left is canceled, and its resume span ended with a cancellation error that the TUI treated as a real failure, so a call such as withoutMount beneath a failing exec rendered as failed. Fix: an attempt whose error is its own cancellation (the same condition that marks it for retry) marks its resume span blocked, because the work is still pending and will be retried.
  • The generator lost its error line. The directory selector settled metadata first, then issued a nested rootfs call on the parent before the parent's rootfs had been evaluated. The nested call appeared as a new pending row and the exit code: 3 line disappeared from the generator. Fix: the selectors evaluate the parent's located part before issuing the nested call, so the failing exec surfaces where it did before.

15. Persistence and session resources

15.1 Persistence: no format change verified

  • A container is stored in the "ready" form (data) only when Container.Lazy is nil, and in the "lazy" form (recipe) otherwise (core/container.go:1539-1546). Lazy becomes nil only when every group is consumed. So a partially evaluated container persists as its recipe, exactly like an unevaluated one.
  • Partial progress is therefore discarded across a restart and re-derived on demand. What is discarded is cheap: metadata copies and delegated accessor clones. Expensive work that ran, such as an exec, is recorded on the ancestor's own cache record, which persists independently.
  • A lazy-form container holding some snapshot links already existed before this change: an exec on an evaluated parent holds its read-only mount references before its own body runs. Persistence collects links regardless of form.
  • Persisted lease roles for mounts are positional (mount_dir:%d, core/container.go:1229). They stay stable because the mount list is settled by the metadata part before any mount part fills.
  • Decode after restart re-installs the op with every group pending, which is exactly what the recipe encodes (core/container.go:4893-4910 for withRootfs).

15.2 Session resources: no new serve path verified

  • EvaluateParts requires an attached result the caller already holds. How callers obtain results is unchanged, including the requirement-subset filter at selection and the re-validation at serve time.
  • A result's required resources derive from dependency edges recorded at attachment time, which happens at publication regardless of evaluation state. A partially evaluated result carries the same requirement set as a fully evaluated one.
  • Delegation bodies evaluate parent results from inside a callback. Bodies already did that before. Per-part evaluation only narrows which ancestors get evaluated. Secret plaintext and socket mounts still resolve against the current session's bindings and still fail without them.

15.3 One bookkeeping gap, pre-existing open question

If every group of a container is consumed through a direct object-side path, such as the pre-v0.12.0 stdout resolver, the cache never runs lease bookkeeping for that container. Section 19.2 gives the evidence and the call path.

17.1 Mount list mutations (ten operations)

Status: done, commits “core: evaluate mount metadata mutations by part” and “core: evaluate mounted snapshot sources by part” (section 10.5). The assessment below is kept as written before the work.

  • Operations. withMountedDirectory, withMountedFile, withMountedCache, withMountedTemp, withMountedSecret, withMountedVolume, the Dockerfile-compat mount, withoutMount, withUnixSocket, withoutUnixSocket.
  • Today. One whole-value body each, installed unconditionally (section 10.4). The body evaluates the parent completely, evaluates the source (for directory and file mounts), copies the parent's whole state, then edits the mount list (core/container.go:3844-3862).
  • Stated reason. "Mechanical extension behind the same templates; explicitly allowed to slip past tonight."
  • Assessment judgment. A scope cut, not a technical obstacle. Six of the ten have bodies that are pure metadata edits: withoutMount deletes a mount entry and a secret entry (core/container.go:6247-6280); withMountedCache, withMountedTemp, withMountedVolume, withMountedSecret append an entry whose source is a dependency result, not a part (core/container.go:6142-6200); the socket mutations edit the sockets list. Those six are Template A conversions with no new snapshot logic: metadata group applies the edit, every snapshot part delegates. One detail: withMountedCache initializes the cache volume's snapshot inside its body; that call belongs to the dependency result, not to a part, so it can stay in the metadata group. The remaining four (withMountedDirectory, withMountedFile, the Dockerfile-compat mount, and by extension withMountedSecret's owner handling) need one more group: the new mount's part, whose body evaluates the source directory or file, applies the optional ownership change through the existing directory chown selector, and stores a detached clone into the mount's accessor (core/container.go:5881-5925). Every other part delegates.
  • The reason the deferral costs more than the record suggested. These resolvers install their op even on an evaluated parent, where a Template A resolver would apply the edit eagerly with no op at all. So they are whole-value links in every chain that contains them. A metadata read below one of them evaluates it completely, including its parent and its source. Section 18.1 gives the worked example.
  • Cost and value. Cost: one or two focused days, no cache-layer changes, one delegation test per op. Value: the metadata-read and single-part-selector benefits start holding for ordinary chains.

17.3 from(image): config without pulling layers

Status: done, commit “core: evaluate container image sources by part” (section 10.5).

  • Today. from has one whole-value body that pulls and unpacks the image (core/container_image.go:126-185). Any part demand on a chain rooted at an unevaluated from pulls the image.
  • Stated reason. Deferred to a distant later stage ("from(image) metadata without layers"), on the assumption that it needs registry work to fetch config without layers.
  • Assessment verified, then judgment. The assumption does not hold. The resolver already fetches the image config at call time with ResolveImageConfig, merges it into the shell's Config, sets Platform and ImageRef, and stores a copy of the config in the op (core/schema/container.go:1185-1215). The op's body re-applies that stored config and then pulls. So the metadata part of a from container is fully known before any pull. The tag path (a non-digest address) first resolves the digest through the lockfile and the registry, and then re-invokes from with the digest address through the schema (core/schema/container.go:1421-1430), so it reaches the same op and the same conversion covers it. Converting from therefore needs a metadata group that copies the parent's metadata and re-applies the stored config, image reference, and platform; an fs write group that pulls and unpacks; and delegation groups for execMeta and every mount part. The delegation groups are required, not optional: the current body starts with materializeContainerStateFromParent (core/container_image.go:128), which takes the exec metadata and mounts from the evaluated parent, so from on a derived container keeps them today. No registry work.
  • Cost and value. Cost: small, one op and one test. Value: the largest single item, because from is the base of nearly every chain and the headline example in the earlier record, from(x).withExec(e).withEnvVariable(k,v).workdir(), still pulls the image until this is done.

17.4 Export-family narrowing (publish, export, asTarball, manifest, layer)

Status: done, commits “core: narrow container image preparation” and “core: preserve parallel image part evaluation” (section 10.5). The first version serialized the platform variants; the fix restored the fan-out.

  • Today. Each resolver calls cache.Evaluate on the container and its platform variants (core/schema/container.go:2649, 4114), which runs every group.
  • Stated reason. "Only after verifying no export path reads mounts or exec meta."
  • Assessment verified. The verification is now done. The shared preparation path collects, per variant, only the rootfs snapshot, Config, and Annotations (getVariantRefs, core/container.go:6925-6965). It reads no mount accessor and not MetaSnapshot. Narrowing is safe: replace Evaluate with EvaluateParts(metadata, fs) in the four resolvers, and change the direct variant.Evaluate(ctx) inside getVariantRefs to the direct narrow force for the same two parts.

Value today: small, because an exec's run already materializes its parent's mounts, so the only work skipped is copying read-only mounts into the exported child.   • Stated reason. Their deferred work is one snapshot's worth; a directory body needs the parent snapshot to produce either the path or the snapshot, so a split buys no laziness; paths are pre-seeded at construction where cheap.
  • Assessment judgment. Justified. I found no directory or file operation whose body could produce one accessor without producing the other. Splitting later is additive.

17.6 Groups of one call run one after another

Status: decided 2026-09-04, being implemented. The assessment below was too mild: the old bodies evaluated a parent and a source together, so running the groups of one call one after another was a regression, not a first choice. Section 18.8.

  • Stated reason. "Sequential matches today's one-body execution most closely, keeps failure attribution simple, and the joint exec group dominates cost anyway; parallelizing groups within one result is an optimization nobody has asked for."
  • Assessment judgment. A defensible first choice that becomes wrong once section 17.1 lands. The exec body's demand on its parent is one call naming the rootfs and every mount (core/container_exec.go:1321-1328). With three pending mount sources, they materialize one at a time. Different callers already run different groups concurrently and a test covers it, so the machinery is ready. Section 18.8.

17.7 Per-part persistence, and a regression the current fallback causes

Status: the regression is being fixed by the rule in section 8.6. Per-part persisted forms remain future work.

  • Today. A container is written in the data form only when Lazy is nil, which requires every group consumed; otherwise it is written as its recipe (core/container.go:1539-1546). After a restart a recipe re-arms with every group pending. The decode path for an exec restores the rootfs and writable-mount accessor values when they were persisted with values, but always resets the exec-metadata accessor and installs a fresh op with no group done (core/container_exec.go:2384-2418). Restored values are therefore pre-seeds in the sense of section 8.3: the first demand of any exec output runs the process again and overwrites them.
  • Stated reason. Per-part persisted forms are the next piece of work. The record argued the fallback is harmless: "the discarded work is metadata copies and delegated accessor clones, cheap by construction, while expensive work (an exec that ran) was latched in the parent's own row."
  • Assessment open question, severity medium. That argument has a hole. The expensive group and a cheap pending group can sit on the same container. An exec container with at least one read-only directory or file mount has its execOutputs group and, separately, one delegation group per read-only mount. After stdout(), directory("/out"), or any demand short of a full sync, the exec has run but the read-only mount copies were never demanded, so Lazy stays non-nil and the container is written as a recipe. After a restart, the first demand runs the exec again. Before this change the same demand consumed the whole body and the container was written in the data form, so the run was kept. Section 19.4 gives the code path. Read-only mounts are opt-in (readOnly: true), so the regression is limited to chains that use them, which is common for source mounts in CI.
  • After the mount conversions. A converted withMountedDirectory or withMountedFile link has its own delegation groups for fs and execMeta. A demand short of a full sync leaves them unconsumed, so that link is also written as a recipe. After a restart its write group runs again: one evaluation of the source result, which persists on its own, and one clone. That is cheaper than repeating an exec, but the canonical chain then has two recipe-form links instead of one.
  • Options. (a) Per-part persisted forms, the planned work: correct and general, but a format change. (b) Have the exec's output body also fill the read-only mount accessors and mark their groups done: the run has already evaluated the parent's mount parts to mount them, so the copy is free, and afterwards every group is consumed and the data form is selected. Demanding only a read-only mount part still copies without running the exec, because the delegation group keeps its own body. (c) Have stdout and the selectors force every group of an exec: simple, but gives back the single-part benefit. Section 18.9.

17.8 Everything remote, and part remapping

  • Stated reason. Later stages: snapshot pull, learned results, a second producer for a part.
  • Assessment judgment. Justified and necessary. Section 11.11 shows exactly which mechanisms would fail if two groups could produce one part; that must be modeled before it is built.

18.8 Decide whether independent groups in one call should run concurrently

  • Situation. Section 12. Groups resolved for one call run one after another. The exec body's demand for its parent's rootfs and every mount is one such call, so a parent with three pending mount sources materializes them serially.
  • Mechanism. A for loop in evaluateResolved (dagql/cache.go:3831-3835). Per-group attempts are already safe to run concurrently; different callers do it today, and a test exercises it.
  • Recommendation. Run the non-metadata groups of one call in an errgroup, the same way Evaluate(a, b, c) already runs different results. Keep metadata strictly first.
  • Tradeoffs. Failure attribution becomes "first error wins" instead of "first group in order", the same as the multi-result path today. 18.9 Close the persistence regression for execs with read-only mounts

Decided and fixed 2026-09-04 by the rule in section 8.6, landed on the pull request and covered by a test that asserts the data form is selected. The option list below is kept as the record of what was considered.

  • Situation. Section 19.4. An exec container that has at least one read-only directory or file mount is written to persistence as a recipe after stdout(), directory(path), or any other demand short of a full sync. After a restart, the first demand of an exec output runs the process again. Before this change the same demand kept the run.
  • Mechanism. The data form is selected only when Container.Lazy is nil (core/container.go:1539-1546), which requires every group consumed (core/container_parts.go:234-254). The exec's read-only mounts are separate delegation groups (core/container_exec.go:161-168) that those demands never touch. Decode re-arms every group (core/container_exec.go:2384-2418).
  • Why it matters. Repeated exec work after an engine restart, for a common CI shape: source mounted read-only, build run, output read. No wrong results.
  • Recommendation. Have the exec's output body also fill the container's read-only mount accessors and mark their delegation groups done. The body has already evaluated the parent's read-only mount parts to mount them, so the copy costs one clone per mount. Implement the copy through LazyState.EvaluateGroup for the mount's group, so it runs under that group's mutex and a concurrent delegation body for the same mount either runs first (then the exec body finds done and skips) or waits (then finds done and skips). Lock order is the output group's mutex then the mount group's mutex; delegation bodies never take the output group's mutex, so there is no cycle. Add a test that persists a partially demanded exec and checks the data form is selected.
  • Tradeoffs. One rule bends: the read-only mount part then has two possible writers, the delegation body and the exec body, with identical content. The mutex makes them exclusive, so the part is still written once. The simpler alternative, mapping read-only mounts into the execOutputs group, removes the second writer but makes directory("/src") on an exec child run the exec, which a current test forbids. The general fix, per-part persisted forms, is larger and remains planned work.
  • What changes with the decision. Yes: execs persist in the data form after any output demand, as before this change. No: users must sync before shutdown to keep a run whose container has read-only mounts.

There is no correctness or performance change. The implementer mentioned it only because the new write-group code could in principle handle several paths in one operation, which would change the persisted shape. Nothing needs deciding.

19.3 Open question 2: whole evaluation of a child leaves ancestors partially pending open question

Evaluate(A) in section 11.1 demands only the ancestor parts the chain actually consumes. A Template A ancestor's execMeta delegation group, or any ancestor part nobody below touches, stays pending, and that ancestor persists in the lazy form. This is consistent with the design's intent (partial progress is cheap to re-derive) and is not a correctness issue. It is worth stating because sync() readers may assume "synced means every upstream result is materialized", which is no longer true. inference

19.4 Finding: an exec with a read-only mount is persisted as a recipe after a partial demand, and its completed run is repeated after a restart fixed 2026-09-04

Status: fixed by the rule in section 8.6 (commit “core: consume final container delegations”). A test evaluates an exec child with a read-only mount through its output group and asserts the op pointer is nil and the persistence encoder selects the data form.

Evidence.

  • The data form is selected only when Container.Lazy is nil; otherwise the recipe is written (core/container.go:1539-1546).
  • Lazy is cleared only when every group of the op is consumed (core/container_parts.go:234-254). The exec's groups are metadata, execOutputs, and one delegation group per read-only directory or file mount (core/container_exec.go:161-168).
  • stdout, stderr, combinedOutput, and exitCode demand only execMeta (core/schema/container.go:1629). directory(path) and file(path) demand metadata plus the one part the path lives in (core/container.go:3422, 3461). None of them demands a read-only mount the path does not touch.
  • Decoding a persisted exec recipe installs a fresh op with no group done, keeps restored rootfs and writable-mount values only as accessor contents, and always resets the exec-metadata accessor (core/container_exec.go:2384-2418). A restored accessor value does not stop a group from running (section 8.3).

Call path. from(img).withMountedDirectory("/src", src, readOnly: true).withExec(build), then stdout(). The exec's execOutputs group runs. The mount:/src delegation group is never demanded, so Lazy stays non-nil and the container is persisted as a recipe. After a restart, stdout() resolves to execOutputs again, whose done flag is fresh, and the process runs again.

Before this change. The same stdout() consumed the whole body, Lazy became nil, the data form was written, and the run survived the restart.

Consequence. Repeated exec work after a restart. No wrong results. Read-only mounts are opt-in (readOnly: true defaults to false, core/schema/container.go:2457), so the regression is limited to chains that use them, which is a common shape for source mounts in CI. No test covers persistence of a partially demanded exec. Fix options are in section 18.9. inference from the cited code; not reproduced by running.

19.5 Inspected and dismissed

  • Pointer writes to FS/MetaSnapshot during a body. ensureFSAccessor and ensureMetaSnapshotAccessor write the plain field when it is nil (core/container_parts.go:536-549), and a sibling attempt's lease sync reads the same fields through PersistedSnapshotRefLinks (core/container.go:1229). That would be a race only if the field were nil during evaluation. Every constructor I found allocates both accessors (NewContainer core/container.go:867, cloneContainerForSchemaChild core/schema/container.go:3405-3410, WithExec core/container_exec.go:1279-1280), so I could not build a real path. Low consequence either way.
  • A failing exec re-runs on every demand. The group stays retryable and no output is applied on failure. Same as whole-result bodies before this change; not a change introduced here.
  • Empty resolution setting lazyEvalComplete. Defended by the every-known-record check and the pending-groups routing; the regression test at dagql/cache_parts_test.go:656 drives the exact sequence.
  • Mapping a mount part on a shell whose mount list is not final. The metadata-first self-demand settles the list before ContainerLazyGroups reads it; the unrefined mount mutation also adds the mount to its shell at construction (core/schema/container.go:2519), and the metadata copy rebuilds the child's list from the parent's settled shape regardless.

  1. Close the persistence regression of finding 19.4 by having the exec's output body also fill the read-only mount copies and mark their groups done (section 18.9), and add a test that persists a partially demanded exec.
  2. Convert from and the mount mutations next (sections 18.1 and 18.2); until then the headline metadata-read benefit does not hold for ordinary chains.
  3. Route the legacy stdout/stderr resolvers through cache.EvaluateParts(parent, execMeta) exactly like the current ones. Two lines each; closes the only API-reachable direct-force path I found.
  4. Consider evaluating independent groups concurrently inside evaluateResolved when a call names parts in more than one group. The per-group attempts are already concurrency-safe and tested that way; the exec body's parent demand (fs plus every mount) would be the first beneficiary. Keep metadata strictly first.
  5. Add a test that documents the intended semantics of "direct path consumed, then cache Evaluate": either it should sync leases (and the code changes) or it should not (and the test pins that no sync is expected). Today that behavior is implicit.

21. Check your understanding

1. You call EvaluateParts(X, execMeta) on an exec child whose parent P is also an exec. Which processes run?

X's process runs (group execOutputs). Its body demands P's fs and every P mount part, which resolve to P's execOutputs, so P's process runs too. P's execMeta is produced as a side effect of P's run but is never demanded. Nothing above P runs unless P's inputs require it.

2. After that call, is X.mount:/src (read-only) complete?

No. It is its own delegation group on X. The run evaluated P's /src part to mount it, so P's side is complete, but X's copy has not been made. X.Lazy stays non-nil.

3. Two callers ask for A.fs and A.execMeta concurrently, where A is a Template A child of an exec. How many attempts exist on A, and how many processes run?

Up to three attempts on A: metadata (led by one, joined or found complete by the other), fs, and execMeta. One process, because both delegation bodies reach the parent's single execOutputs group.

4. A shell's FS accessor is set. What does that tell the delegation body?

Nothing. It may be a pre-seed cloned through an unevaluated writer. The body evaluates the parent's part and overwrites unconditionally.

5. The last group's body succeeds and clears Lazy, then that attempt's lease sync fails. What does the next Evaluate do?

Resolution returns no groups. The cache routes the demand to every group record with live state, which is that group with syncPending. It leads a bookkeeping-only attempt (no body). If that fails again, the error propagates and lazyEvalComplete is not set.

6. Does Evaluate(A) fully evaluate A's parent?

Not necessarily. It demands only the parent parts A's groups delegate to. If the parent is an exec, its joint group makes most of it complete anyway; if the parent is a Template A op, any part nobody demanded (typically execMeta) stays pending.

7. Which lock is held while an exec body runs?

Only that group's lazyGroupOnce.mu on X's op. Not lazyMu, not LazyMu, not lazyOpMu. The cache's attempt is a record, not a lock.

8. Why can the exec body read container.Mounts without evaluating anything?

Because the resolution phase settled X's metadata via EvaluateParts(X, metadata) before returning the group list, and the cache only runs the execOutputs attempt after resolution returned. The completion of the metadata attempt under lazyMu orders the metadata body's writes before the exec body's reads.

9. What would break first if a future op mapped fs to two different groups over time?

The one-production rule. Nothing at either layer excludes two groups from writing the same accessor, and the exec's joint group would also write execMeta and writable mounts, so provenance could mix within one result.
