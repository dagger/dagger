Preserve evaluated container parts across restart

Revised local design draft · September 5, 2026 · source base 563d9211a5a368b414c11a329a34753c42520910

A retained container should remember which computation finished. Restart should restore its metadata and open each completed snapshot only when that part is demanded. Work that remains pending should keep its existing recipe and group boundaries.

This is a design and implementation plan. Source was inspected; the feature, tests, and model extension have not been implemented or run. Council approval of this revision and Erik’s design approval remain pending.

Proposal and boundary

Chosen mechanism. Store final state by part, including explicit completion and legitimate absence. Decode a container into plain metadata, descriptors of its completed values, and its remaining recipe. A restore operation uses ordinary DagQL group attempts: open:<part> for completed local snapshots, and the original recipe’s groups for pending computation. Keep descriptors visible to snapshot ownership and usage accounting throughout the container’s lifetime.

The larger goal is warm CI on a fresh engine. Cloud chooses which results to collect or preposition within an organization. The engine supplies ordinary cache identity, execution, ownership, and transfer mechanics. This local change provides a useful foundation without deciding remote transfer or service policy.

The scope is container part persistence and deferred local snapshot opening. Keep the existing result graph, checkpoint timing, startup validation, shutdown quiescence, session-resource contracts, and local pruning. Cut the persisted format version; do not migrate old rows. Do not add a second cache lookup, distributed reservations, a command queue, or a remote service simulation.

Exact opening guarantee. Decoding a container, reading its already consumed metadata, reporting its usage identities, and encoding it again do not open its closed stored snapshot parts. Demanding one such part opens that stored part; other stored parts stay closed until demanded. Ordinary final parent copies may still run after a successful group callback or a direct metadata visit, and those copies can clone/open handles for already available values. Snapshot lease attachment and snapshot-size queries may inspect local metadata. A pending recipe may decode standalone Directory/File dependencies that open snapshots today; the guarantee does not cover that dependency closure or every snapshot-manager call.

Preserving a mounted content writer’s completed output saves its copy and snapshot commit even if decoding its inputs still opens some standalone snapshots. A fully computed container with no remaining recipe also avoids traversing that recipe during decode. These are sufficient local benefits to keep standalone Directory/File decoding outside this proposal. Any broader promise would need a separate scope decision.

Local retained-snapshot failures remain errors. A missing snapshot during boot lease attachment still makes import fail and follows the current reset path. An open failure after successful boot surfaces on the first demand for that part, rather than on metadata decode. It never silently reruns completed work. Future remote download failure and recipe fallback are separate decisions.

Current problem and saved work

Container.EncodePersistedObject chooses a recipe whenever Lazy remains set. It can also encode snapshot values, but it does not encode the groups’ consumption. The recipe decoder creates a fresh LazyState. Values restored into accessors are therefore seeds, not proof that the writer finished. A later group demand runs its body again.

Use no owner lookup and an absolute destination inside the directory mount. Settling metadata does not execute P. Demanding X’s mount causes M’s source group to finish, then X’s write group copies the payload into that mount. Its rootfs and exec metadata still come from P’s unconsumed execOutputs group.

ContainerWithDirectoryLazy maps the destination with containerPathWriterGroups. Its body calls Container.WithDirectory on a detached mount value. That calls Directory.WithDirectory directly, which allocates a mutable snapshot, copies content with layercopy, and calls CommitWithUsage. The selected parent directory and the source directory may be independently cached. The output mutation itself has no separate withDirectory result lookup inside this body.

The write obtains its base through targetParentDirectoryForContainerPath, which selects M.directory("/work"). Loading or evaluating that Directory can reopen the base snapshot independently of X’s accessor. This happens in the initial write and may happen in the current post-restart rerun, even when the selector call is cached. Count that base-selector access separately from source decoding, X’s stored owner open, and the final output selector. With the proposal, demanding X’s stored mount does not invoke this write helper or its base selection.

Today X persists its recipe because the other groups remain pending. A new demand for its mount after restart repeats that direct mutation, even if a snapshot of its prior output was retained. The proposal restores that output as completed and only opens it. The source test TestContainerMountedSourceWriterParts establishes the pending-sibling shape; this content-writer extension establishes meaningful saved work by source inspection. It needs the focused execution evidence described below.

Other useful cases, with narrower claims

  • A metadata-only chain above a pending exec keeps its computed metadata across restart. Ordinary config edits save small copies; do not call this a large execution saving.
  • A plain withMountedDirectory or withMountedFile partial row preserves its source copy, but the source result persists independently. Do not count its source computation as a second saved run.
  • A fully computed exec can reopen just execMeta to read its output after restart. Container decode currently opens rootfs, exec metadata, and mount snapshots eagerly. This is a separate benefit from preserving partial computation.

The old exec-with-read-only-mount example is already fixed. TestContainerExecSuccessConsumesFinalReadOnlyMount checks that the sweep consumes the remaining copy, clears the op, and selects the data form. Retain that regression test. It is not evidence of a newly preserved partial exec.

Persisted representation

Replace the container’s recipe-versus-data choice with one container payload. Keep the generic result envelope, dependency rows, and result-to-snapshot link table. Increment cachePersistenceSchemaVersion in dagql/cache.go from its current value of 17 at the format change. The field names below specify the intended shape; they are not an implemented API.

container payload
  metadata: { consumed, value: existing plain container metadata }
  parts: map[PartKey] final-part-record // empty while metadata is pending
  recipe: existing lazy JSON, present only while computation remains

final-part-record
  pending                          // no final value; recipe supplies it

  file      { path, platform, services, role }
  snapshot  { role }                // execMeta

Every non-pending record means consumed computation. Each present Directory/File descriptor has a nonempty local snapshot link, its path string, platform, and service references. Keep the existing path normalization: an empty persisted path leaves its accessor unset. Do not add accessor-presence flags or a nested absent-snapshot form. Current scratch directories obtain a real snapshot through loadCanonicalScratchDirectory; a consumed present value without a snapshot is an encode error. The actual absent container rootfs and execMeta cases use absent and restore an unset accessor.

Use a container-owned descriptor decoder for embedded values. Calling the standalone Directory/File decoder here would reopen their snapshots during container decode. When metadata is consumed, the parts map contains exactly fs, execMeta, and the snapshot mounts named by its settled list. When metadata is pending, its canonical parts map is empty and the recipe is required. Reject any nonempty map in that case, including completed records, using this structural rule before consulting dynamic group mapping.

Capture consumption, not cache latches or accessor contents

  1. If the container has no op, all current parts are consumed. Preserve any legitimate empty fields explicitly.
  2. For a refined op, read metadata consumption first. Only after it is true enumerate snapshot parts and map each part through the original operation’s settled mapping. Read that group’s object consumption. An active shared cache attempt, complete=false, or syncPending=false does not override successful body consumption.
  3. For a decoded restore operation, descriptors of previously completed parts stay completed whether opened or not. For its remaining recipe parts, use the recipe’s current body consumption. Never use the open: group’s done bit as the saved computation bit.
  4. If metadata is pending, emit an empty parts map. Current refined bodies cannot complete snapshot work before metadata. Keep their recipe and provisional plain shell without evaluating or reading dynamic mapping.
  5. The currently unrefined ContainerImportLazy remains one whole pending recipe. Its body evaluates its parent and source and replaces parent state before import. It has no partial completion to save.

Omit snapshot pre-seeds for unconsumed parts from the new payload. The refined writer paths reconstruct required inputs through their parent/source demands; ContainerImportLazy reconstructs its whole input state. Such seeds may still have live leases before shutdown, but are not durable outputs of this row. Keep ordinary dependency edges, including those retaining their input results. This removes no final output and introduces no snapshot opening at encode time.

When a recipe remains, its existing JSON still describes the whole operation. Do not split it into new recipes. Decode seeds the original group latches for completed members, so only unfinished groups can execute. Require completion to be uniform within each original joint group. A stored execOutputs group cannot have completed fs and pending execMeta in a valid local row.

A missing required descriptor or link for a consumed nonempty value is an encode/decode error, not an excuse to declare it pending. Do not force evaluation to make encoding succeed. Absent container rootfs or execMeta is valid; a consumed mount requires its Directory/File value and snapshot. These checks catch internal format mistakes, without adding a new untrusted-input model.

Omit the recipe once every computation part is consumed, even if stored snapshots remain unopened. A restore operation’s temporary in-memory recipe pointer may live until that operation is consumed; persistence must not retain it for future replay. Existing attached dependency edges remain owned until ordinary result collection. Deciding how to retain recipes after completion for remote fallback remains outside this change.

Decode and demand routing

A restore operation, with one group latch authority

Add ContainerRestoreLazy in core/container_persistence.go. It implements LazyContainerParts. It holds the optional original refined recipe and a reference to the container’s immutable map of stored part descriptors. The descriptors also live on Container independently of Lazy, so clearing the op cannot lose snapshot ownership or saved completion.

For a remaining refined recipe, the restore operation returns that recipe’s ContainerLazyState(). Initialize completed original groups under that state before publication. Use the same state for the extra open: groups. Do not wrap a recipe’s EvaluateContainerGroup in another call to EvaluateGroup on the same group: its body already takes that mutex. For a fully computed container, use a fresh state with metadata and no-I/O absence groups consumed. Leave lazyInitComplete false while any opening remains, or it would suppress those openings.

This operation exists only on decode. It is never recursively serialized as a new recipe. The encoder projects final part state and, when necessary, the original recipe JSON. A second restart creates one fresh restore operation, regardless of how often the row has crossed a restart.

Its interface methods are explicit: EncodePersisted(ctx, cache) forwards to the original recipe when that pointer exists, and returns nil, nil when it does not. AttachDependencies(ctx, attach) forwards to the original recipe’s attachment method, including its normal input rebinding and returned dependencies; without a recipe it returns nil, nil. Container’s existing attachment method still handles its plain resource references. The restore operation adds no serializable recipe kind.

The Container encoder decides whether to call EncodePersisted from remaining computation, rather than from op presence or pending openings. If any computation is pending, require an original recipe and nonempty encoded recipe JSON; otherwise omit the recipe field even if the restore op still holds its consumed original recipe. A missing recipe for pending work is an encode error. Forwarding alone is therefore not the form-selection rule.

Decode order

  1. Parse the new container payload. If metadata is pending, reject a nonempty parts map without consulting part-to-group mapping. Obtain the role-to-snapshot-ID links and build the plain metadata and correctly typed empty accessor records. Store all completed descriptors on the container before installing the typed payload.
  2. Decode resource references with their existing contracts. Reconstruct an original recipe only when computation remains. Refactor decodePersistedContainerLazy to construct and return the recipe without overwriting restored fields. In particular, stop the exec decoder from clearing restored MetaSnapshot or changing settled ImageRef. Pending metadata still runs its normal body later.
  3. If metadata was consumed, restore it as settled and seed the corresponding recipe group. Validate and seed every completed original group from part state and the settled mapping. Install explicit absence shapes without snapshot I/O. Keep nonempty completed snapshot accessors empty until their opening group runs.
  4. If metadata is pending, its validated parts map is empty. Publish the ordinary original op with fresh latches and empty snapshot accessors. The unrefined import follows its existing whole-group path. There is no stored snapshot to open in either case.
  5. If all computation and required local availability are already satisfied, omit the restore op immediately. For example, metadata plus absent fs/execMeta and no snapshot mounts needs no deferred work. Keep any descriptors on the Container, but publish Lazy=nil rather than waiting for a visit to clear it.
  6. Use the existing persisted-hit install, lease sync, and lazy registration. All unopened snapshot IDs must already be visible through PersistedSnapshotRefLinks at this point. Decode never calls Evaluate to discover metadata or groups.

The original recipe decoder may load parent Containers and standalone Directory/File sources by result ID. A parent Container receives the same treatment recursively. A standalone source still follows decodePersistedDirectoryWithSnapshotRole or its File counterpart, which opens its snapshot. Keep this cost visible in tests; do not describe the whole decode closure as free of opens.

ResolveLazyEvalGroups retains its metadata-first self-demand outside shared.lazyMu. The restore operation’s nil-part enumeration builds a union of per-part mappings, rather than returning the original group list unchanged. A completed joint writer becomes multiple stored-part opening groups only at decode. A pending joint writer never changes groups while it runs. This prevents a cache attempt from referring to a group that was renamed beneath it.

ContainerLazyParent returns the original recipe’s parent, or an empty result when no recipe remains. Pending copy groups retain their part-name keys and their usual sweep. Stored opening groups use a reserved open: prefix, so they never equal a snapshot part key. The current consumeFinalParentDelegations test therefore cannot mistake a stored open for a parent copy.

containerParentPartFinal continues to inspect the parent’s active group mapping and current object latch. On a restored parent with a closed snapshot, that means the unconsumed opening group, so an opportunistic child sweep does not open it. Once it is open, a child copy may run under the existing rule. Durable computation completion does not mean the parent has a ready accessor in this process.

Keep runLazyGroup ordering for every group: body, final-parent-copy sweep, then clearLazyWhenConsumed. A successful stored open may be followed by copies of already available parent parts. The sweep cannot select a stored sibling because of its reserved key, and cannot open a closed parent part because that parent’s opening group is unconsumed. Such copies may create additional handles; they do not expand which closed stored parts are demanded.

Direct narrow and whole evaluation visit runLazyGroup(metadata) even when its body was seeded consumed. Its no-op body can therefore be followed by the same sweep before the requested opening. In contrast, the cache reads a nil metadata callback and completes without calling runLazyGroup. Preserve both paths. No stored-open or stored-metadata exception to the sweep is needed.

Clear the outer op only when every currently mapped group, including every required opening, is consumed. Do not clear it merely because all computation was done before restart. The cache can still owe bookkeeping after this pointer clears; pendingLazyGroups must continue to route that work.

An open body prepares a complete detached value in a local variable, then publishes it once. Release any newly obtained ref if construction fails before publication. After publication, the container’s ordinary OnRelease owns that ref. Successful opens are protected by EvaluateGroup even on direct object-side entry paths. Descriptors contain no live ref and are never independently released.

Unset accessors, selectors, and schema children

For a stored nonempty part, a successful demand must publish the accessor before returning. ContainerRootFSLazy.Evaluate demands the parent’s fs before its Peek and scratch fallback. metaFileContents calls evaluatePartsDirect(execMeta) before its Peek and ErrNoCommand fallback. The restore operation’s Evaluate must call evaluateAllLazyGroups, and its direct narrow path must use the same opening bodies and latches. Neither path may mistake a closed stored descriptor for legitimate absence. Test both fallbacks with known nonempty stored snapshots and with actual absent values.

A restored parent with unopened snapshots still returns true from HasPendingLazyEvaluation. Thus cloneContainerForSchemaChild may clone empty accessor records, but its caller installs the existing lazy child operation instead of taking the eager mutation branch. For example, a new mounted-directory child keeps the parent result and later copies its demanded rootfs from that parent, which first opens the stored snapshot. A metadata-only child similarly keeps copy groups. No descriptor or descriptor mutex is cloned into the child. If the parent is no longer pending, all its snapshot accessors are available for the existing clone helpers. A concurrent completion after a true pending observation merely leaves an ordinary lazy copy to consume.

Keep the semantic pending predicate unchanged at schema construction sites. Changing those sites to the reporting predicate would create an eager child with missing rootfs or exec metadata. Add regression tests for a metadata child and a mount-mutating child made from a fully computed, decoded parent whose snapshots are all still closed.

Bookkeeping failure and a pointer that has already cleared

Suppose opening the last stored snapshot succeeds, publishes its ref, and clears the restore op. Then syncResultSnapshotLeases or operation-lease release fails. evaluateGroup records syncPending=true, leaves complete=false, and retires that attempt with an error. A later demand sees no object groups, so evaluateResolved uses pendingLazyGroups. prepareLazyGroupEvalLocked retries only bookkeeping. It must neither reopen the snapshot nor run any recipe.

A computed body can fail after its own consumption because a later sweep fails. Then syncPending need not be true: the enclosing callback did not succeed. Current code rereads the consumed group and can complete a no-body demand. Capture the successful object consumption at shutdown anyway. Do not infer it from syncPending, or expand this proposal into a redesign of the existing sweep-error path. The relevant original refs and ordinary retained input/output graph remain the source of snapshot links.

Direct metadata visit after the parent becomes ready

Decode X with a stored mount and pending fs/execMeta. Let another caller complete M’s pending outputs. A cache demand for X’s consumed metadata takes the no-body path and leaves its copies pending. A direct narrow or all-parts call instead visits runLazyGroup(metadata); its sweep may copy M’s now available fs/execMeta before opening the requested stored mount. The mount remains closed until its own demand reaches its opening body. Also exercise an opening callback whose post-body sweep consumes a remaining parent copy. Count these copy handles separately and assert that no undemanded stored sibling opens.

Flush unopened, then restart again

After the first restart, read only X’s metadata and close again. Its typed payload now exists, so the encoder must emit descriptors from the container, without calling standalone value encoders that require open refs. The next boot obtains the same completed mount, pending sibling groups, recipe, and snapshot link. Demanding the mount on this third engine opens its snapshot and performs no mutation. Also cover the envelope-only branch: a row never decoded on the middle engine is passed through by persistResultEnvelope with its owner links unchanged.

For a fully computed exec, all output snapshots may stay unopened through the middle engine. Opening only execMeta must leave fs and writable mounts closed. Their computation remains complete in both checkpoints. Nothing synthesizes a new joint exec recipe.

Collection before or after opening

Prune removes the ordinary persisted edge. If a session or dependent still owns the result, it stays alive. Once ownership reaches zero and active operations have drained, collection removes every result-role lease and invokes Container.OnRelease for the refs actually present in accessors. Before any open there are no such handles to release. After one open there is exactly that newly owned handle, plus any other normally materialized fields. Other results linking the same snapshot retain their own leases. No descriptor reserves content beyond this result’s existing ownership.

Locks, leases, and collection

Do not add a concurrent checkpoint protocol. Cache.Close already calls waitForQuiescence and checks release cleanup before persistCurrentState. snapshotPersistState captures the retained graph under egraphMu.RLock, then releases it before encoding typed values. Production encode occurs after admitted operations and cleanup have drained. Direct encoder unit tests must supply equally quiescent objects.

One desired-link view before and after an accessor opens

desiredSnapshotLinksForResult uses envelope links only while there is no decoded value. After decode it asks the typed object. Extend Container.PersistedSnapshotRefLinks to return the union of immutable descriptor links and its currently held accessor links. Deduplicate by role; duplicate role and ID is one link, and conflicting IDs are an internal error handled by the existing sync check. A stored completed part cannot be replaced by remaining computation.

Retaining descriptor links after opening avoids a handoff window in which concurrent lease sync could see neither representation. The steady-state cost is one small descriptor per imported completed part. After the op pointer clears, both ownership and the encoder can still discover the snapshot. Live pending pre-seeds may be reported by accessors for ordinary runtime ownership; the new encoder omits them as unfinished output.

An open ImmutableRef is a process handle, not a durable snapshot pin. Snapshot retention comes from containerd leases. Stored parts already have their imported result-role leases before opening; the usual attempt lease and result bookkeeping remain in place during access. Do not rely on a handle surviving to protect content after removing its owner link. This proposal does not repair unrelated pre-existing failure windows for freshly computed output whose lease sync failed.

Keep positional snapshot roles. Compute a role from the settled mount list and record the association with the target-keyed part. Metadata is immutable while its snapshot groups run. A child that removes or replaces a mount creates its own list and role mapping; it does not reuse its parent’s descriptors or positional roles. At decode, check target, source kind, and role against that row’s settled metadata. This is enough to handle mount deletion/reordering without a new lease naming scheme.

CacheUsageIdentities must return the deduplicated union of descriptor IDs and accessor IDs. CacheUsageSize may use an already open ref’s Size method; for a descriptor-only identity use the supplied CacheUsageSizeProvider.SnapshotSize. Never open a ref merely to measure it. The snapshot manager’s current SnapshotSize queries snapshot usage and known content directly. Usage and pruning should see the same local identities before decode, after decode, and after an open.

Cache reporting

Today core/telemetry.go suppresses the cached attribute and sets pending when HasPendingLazyEvaluation is true. That function includes callbacks, active attempts, and unfinished bookkeeping. A restore-only container would therefore appear to have computation left. Merely changing its op name would not fix that.

Keep HasPendingLazyEvaluation as the coordination predicate, including its use in cloneContainerForSchemaChild. Introduce a reporting predicate, HasPendingLazyComputation, and a small optional typed-value contract for remaining computation and per-group work purpose. Put the Container implementation on the Container value, not solely on its restore op. Its immutable descriptor map identifies every reserved opening key it issued; remaining original recipe groups report computation. Ordinary lazy values and unknown group keys default to computation. Plain local copy groups keep their current reporting behavior.

Group purpose must be a stable, non-evaluating query for the value’s lifetime, including after Lazy clears and through sync-only retries. Container can satisfy this from its immutable descriptors, so add no purpose field to lazyGroupState. DagQL asks the optional typed-value contract and never interprets Container’s key spelling. Under shared.lazyMu, the reporting predicate first classifies unsettled attempts, callbacks, and bookkeeping using their group keys, then consults the object’s still-unstarted computation. A successful computation body with failed bookkeeping remains pending; an unopened completed snapshot alone does not.

Use that same stable query when creating an attempt’s telemetry and when computing partial status at retirement. After the last stored open publishes its ref and clears the op, a failed sync still classifies as stored access on retry. The descriptor remains on Container, and the key has not changed. There is no need to reconstruct the recipe or retain a second copy of this classification in the cache.

State and actions to add

  • Add an opt-in ModelContainerPartPersistence scenario constant, false in existing configurations. New fields have one fixed inert value when it is false. Keep all existing action branches and the single-group state encoding unchanged in that mode.
  • Track actual computation consumption per part, separately from the current process’s group-body consumption. Fresh recipe body success sets it for every member of the group. Successful swept copies also set it. Opening a stored snapshot sets its opening group’s lazyConsumed but does not perform computation.
  • At Flush, write a per-part completed/value-kind record derived from actual live consumption. Capture an independent observation of the live consumed set for assertions. The encoder’s proposed bits and that observation must not be the same variable copied twice. In particular, a swept copy with lazyConsumed=TRUE, lazyComplete=FALSE, and lazySyncPending=FALSE must be captured as computed.
  • Add a per-result effective part-to-group mapping for the enabled scenario. Fresh/pending parts use PartGroupOf. On decode, completed nonmetadata parts use reserved opening groups, metadata is installed as consumed, and absent parts need no open. Mapping is fixed for that process once metadata settles. Original joint groups remain joint for computation.
  • Define routing helpers that reduce to existing PartGroupOf and GroupNeedClosure when the feature constant is false. Use the effective mapping in evaluator spawn, prerequisite resolution, delegation demands, parent finality, successful return checks, and group-order properties. Distinguish active groups from unused reserved opening groups so inactive groups do not create false pending work.
  • Initialize imported computation and opening state from the stored row when decode installs the typed value, including initially decoded rows. Make the enabled ImportedLazyArm path deterministic from that row and ensure no evaluator can take a no-work return before installation/registration. Keep optional generic lazy arming for existing disabled configurations.
  • Allow opening bodies to succeed or fail through the same attempt protocol, including cancellation, release, and sync-only retries. The opening body itself does not demand dependencies. After its success, allow the existing copy sweep and its internal parent demands before bookkeeping, just as after a recipe body. A stored open cannot be selected as a copy candidate. Lease and operation ownership stay under the existing bookkeeping/token abstraction.
  • Keep the two process epochs. Extend ImportRowChoices and ImportGraphState with legal stored part state for the enabled scenario, so an imported starting row can decode, flush unopened, and restart. Keep a separate fresh-computation and fresh-sweep path through Flush and Restart to prove that real completed work produces the stored state.

For direct metadata visits, account for the existing sweep effects under the calling operation’s lifetime: copied-group exclusion, final-parent observation, and the internal parent demand. A visit to already consumed metadata does not perform another metadata computation or create a metadata cache attempt. The model may abstract the direct entry plumbing to this sweep visit, but it must permit that sweep before the requested open and must not manufacture a cache completion or sync-pending flag for the directly copied group. The cache no-body branch remains a return without a sweep. Focused Go tests distinguish these entry paths and check their accessor/open behavior.

Legal imported starts use the existing retained dependency graph and ownership counts. Pending metadata has an empty parts map and a recipe. With settled metadata, every part has one pending, absent, or stored-value state; pending parts require a recipe, completed original joint groups have consistent member completion, absence is limited to valid container fs/execMeta, and stored nonempty values have local links. For modeled copy relations, a completed child copy requires the parent’s corresponding computation to be consumed, although the parent’s stored snapshot may be closed in this process. Initially decoded rows install their deterministic group state before evaluation is possible.

An imported start assumes a valid prior checkpoint; it does not prove that the engine produced it. Use it to check preservation through the next checkpoint. The separate fresh body/sweep → flush → restart witness proves capture from actual lazyConsumed state. Together they cover the two boundaries without altering epoch/refusal properties. Go tests still perform two actual restarts, including the middle engine’s typed and untouched-envelope cases.

The part-consumption field is semantic state, not a second completion mechanism for Go. In Go, initial completed descriptors plus current recipe group consumption supply it. The model needs the field because one old joint computation group becomes several opening groups at restart. lazyConsumed continues to mean the body of the currently mapped group was consumed.

Define the capture oracle directly from that source state: for a decoded part, LiveComputed(r,p) = InitiallyStored(r,p) OR res[r].lazyConsumed[GroupForPart(r,p)]. For an untouched envelope, use its prior saved computed state. Capture this observation before restart resets the process state. Check the semantic per-part field against this projection as well as checking encoded bits against it. Thus accidentally omitting a swept copy from both a new semantic field and the encoder still fails against the actual lazyConsumed record. Decode initialization must distinguish an uninstalled envelope from a completed body, as specified above.

Alternatives and decisions

AlternativeWhat it would simplifyReason for the chosen design
Persist only group done flags, reopen all snapshots on decodeMinimal routing change.It preserves computation but still eagerly opens every container snapshot. Durable per-part values also express a completed joint group whose stored members open independently.
Force every container at shutdownEvery row would be fully computed.It executes previously undemanded work and can surface errors during checkpoint. The current partial-evaluation benefit should survive shutdown.
Put deferred opening inside generic accessors or snapshot refsCould serve many types with one handle abstraction.Current accessors expose Peek, cloning, and direct snapshot use widely. Those paths do not supply group ownership or attempts. This local change can use the already existing container demand boundary.
Teach Container routing about a second live lazy fieldAvoids a restore operation implementing the recipe interface.It gives nil Lazy a new meaning across direct evaluation, parent finality, pointer clearing, and registration. One active op with explicit stored-open groups reuses those contracts with fewer branching sites.
Reuse part-name keys for stored opensShort group names.The current sweep interprets those keys as parent copies. The reserved open: prefix preserves the existing copy test and prevents undemanded opens.
Change all mount lease roles to targetsPart names and lease names would coincide.Settled metadata already supplies a stable target-to-position association per row. No material local scenario requires a wider role-format change.
Retain all recipes and rerun on local open failureCould resemble a future remote fallback.It changes local error behavior and pre-decides recipe availability after completion. Neither is needed to preserve completed local work.
Defer every Directory/File dependency decode tooCould support a broader no-open claim.The useful mounted-output preservation and completed-container opening behavior do not require it. Keep the measured dependency cost explicit and leave broader decoding to a separate decision.

There is no unresolved scope question blocking this draft. The substantive boundary is explicit: completed container-owned values are deferred; standalone dependency decoding remains as today. The mounted mutation, decode bookkeeping, and ownership arguments are source-based and await the stated implementation evidence.
