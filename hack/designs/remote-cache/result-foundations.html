Engine foundations · snapshot implementation

Reusable snapshot chains and recipe foundations

Make locally produced snapshot chains reusable through a supplied content provider, with ordinary ownership and persistence. Compare how a later execution consumer could recover a recipe, without making that decision or consumer a prerequisite for this PR.

Revision 4 · September 5, 2026 · inspected starting point 81bb9105de191489885a52af2546d53107eaeb2f

Implementation status. The approved snapshot scope is implemented. Focused Go checks and the bounded snapshot model pass. The implementation record describes the final ownership repairs and evidence limits. Recipe reconstruction remains a separate decision.

Concrete outcome and boundary

The implementation lets an engine export a build’s immutable snapshot chain, import it from an in-process content provider, and receive an ordinary local immutable ref. Existing snapshots win before any byte request; existing blobs win before a source read. A layer is applied when no reusable local snapshot exists under its resolved parent/diff key; rebuilding a lost ancestor can change descendant parent keys. Exported local builds participate in the same reuse indexes as imported image layers. The result survives through existing lease and local-persistence machinery.

This is a substantial snapshot-foundation change: common import mechanics, export-side reuse registration, empty-root normalization, transfer lifetime, persisted indexes, and real local evidence. It works below Container, Directory, and File. The recipe comparison can be discussed in parallel; snapshot implementation does not depend on a recipe ruling. The bounded snapshot scope was approved with that choice left open. Generic recipe execution code would have no production consumer in this unit and should wait.

Excluded: live foreign-result learning; result describe APIs or portable result wire formats; foreign numeric-ID remapping; Cloud channel, service, or policy; production pull-to-run orchestration; mixed-output publication semantics. No second cache, identity system, or client recipe-replay rules.

A local witness builds /out/report.txt, exports its snapshot ancestry, and imports that chain into a second local snapshot store through the supplied provider. A Directory or File constructed with the returned ref reads the same bytes. Repeating the import reuses the local snapshots; importing a longer chain reuses its prefix. This proves transfer and ownership, not that an uncomputed DagQL call becomes a cache hit.

All persistable values remain the goal

Eligibility follows existing persistability, including retained dependencies, scalars, lists, plain objects, module objects, and resource-bearing values under their existing session contracts. Snapshots are optional. A completed plain value needs no artificial executable recipe merely to return its saved payload. A cached File.contents string or module scalar can retain snapshot-bearing dependencies without requiring their bytes just to serve that value.

This PR supplies mechanics needed by immutable snapshots wherever they occur. It does not require a rewrite of every result type. Preserve parent results and semantic dependency edges when mutable backing contents are excluded. Mutable cache volumes, full filesync mirrors, and mutable git mirrors remain local; those exceptions do not exclude every object that references them. Frozen client-directory and git-source output edges still need an explicit ruling before future cross-engine exposure. This snapshot capability makes no eligibility ruling about those edges.

Recipe availability: proposed direction

A stored call describes provenance. A typed recipe describes executable inputs. A consumed live operation also contains synchronization and mutable execution state. These are different things. Current completed results retain producing calls; they do not universally retain executable recipes. Completed Container encoding omits recipe JSON, and existing typed recipe decoders consume separate JSON rather than reconstructing it from call arguments.

Recommendation for Erik’s review: use stored producing calls as the default basis for future execution-time reconstruction, with additional immutable declarative provenance where a concrete producer lacks sufficient inputs. The reason is proportionality: ordinary calls already survive completion and cover eager schema producers. Retention remains a valid alternative if the concrete execution comparison shows reconstruction loses frozen inputs or needs more machinery. The synthetic merge case is a required future coverage case, not a new exclusion. Neither approach may regenerate identity from today’s ambient defaults or replace established session contracts.

Implementing reconstruction now would require a cache execution seam without its actual consumer. ObjectResult.call enters GetOrInitCall and could rediscover the very result needing reconstruction. A nonce, deletion of the hit, or a second lookup system is not a solution. Delay that seam and producer-wide retention changes until the later execution design specifies ownership and output installation. Erik may settle the recipe direction in parallel using the named local producer traces; this is optional for the snapshot PR, which does not promise fallback for completed results. If Erik chooses eager retention instead, scope its capture boundaries before adding that code.

Snapshot mechanics

One chain representation and one apply path

Reuse ExportLayer and ExportChain: ordered OCI layer descriptors with compressed digest, uncompressed digest information, size/media type, and a content provider. Keep export request-driven; ensureExportBlob already generates or reuses blobs on demand. Do not hash normal build completion or invent a chain-identity registry.

SnapshotManager.ImportChain accepts a supplied in-process provider compatible with the existing reader contract. Each invocation imports one immutable snapshot chain. A caller may import separate output chains independently; this API has no DagQL result or part handle. Under the existing parent/diff exclusion, find and pin a reusable snapshot first, then check and pin local content, and request bytes only if absent. Copy into the ordinary content store through its writer contract, then reuse layer application. Source errors return to this caller; this layer does not run recipes.

Reuse snapshotPin actual resources before advancing or returning.
Reuse blobPin existing bytes; read the source only when absent.

Adopt normallyKeep the ref owned through adoption and release.

ImportImage at the inspected starting point assumed blobs were local and wrapped layer import with image metadata and progress. The implementation shares only the common reuse/apply mechanics and keeps image-specific manifest/config links and metadata in the wrapper. A new generic importer must not route through registry fetching of an entire image closure. Preserve existing image behavior while proving that both callers use the same layer reuse rules.

Reuse locally built snapshots too

The starting gap: successful export recorded snapshot/blob metadata, while import populated the parent/blob and parent/diff indexes. Exporting a local build did not register those reuse entries. Importing its description back into the same manager could therefore apply bytes even though the exact local snapshot existed.

Register each successfully exported layer using the descriptor export actually returned, including an encoding produced by an explicit compression request. Generate no extra compression forms for registration. The existing parent/diff index permits snapshot reuse across encodings. Reuse their current persistence. Keep publication under the existing manager synchronization, with no manager-wide lock across byte transfer. Index membership is a reuse hint, not ownership; retain missing-snapshot eviction and existing handling of other lookup errors.

Normalize keys for roots the exporter omits. ExportChain skips canonical scratch, and export can omit an empty root. The first emitted layer’s local parent may therefore differ from import’s empty-prefix key. Use the same empty-prefix representation for exactly those omitted roots; retain actual parents for snapshot operations. Do not equate arbitrary snapshots or ignore ancestry. A zero-layer generic chain returns the ordinary scratch ref; no-snapshot result payloads do not call this API at all. Keep image-specific empty-root metadata behavior separate.

Leases and cleanup are part of success

AttachLease pins the snapshot, every actual ancestor, and their recorded content. recordSnapshotContent also adds newly exported blobs to existing owner leases. Preserve both: an index or a returned provider interface alone does not keep content alive.

Reuse paths must attach resources too. GetBySnapshotID returns a handle; EnsureLease can supply a lease from an existing scope. Neither operation itself attaches the reused snapshot or blob. Require successful attachment to a live operation or caller-owner lease, not merely a ref handle or an ambient lease ID.

  • Producer: pin the export snapshot and its actual ancestry before using them. Pin every selected existing or generated blob before exposing its descriptor/provider, and retain that ownership through provider consumption. The existing-blob return path must satisfy this too. The former ExportChain fallback ended its lease at return, before provider consumption.
  • Consumer: attach each reused prefix snapshot, its ancestors, and required recorded content before advancing to the next layer or returning the tip. Pin reused local blobs before reading/applying them. Keep those pins until normal result snapshot-link ownership or another caller owner has successfully adopted the resources.

A consumer reuse candidate that disappears before successful pinning is a cache miss: discard the stale candidate and continue the ordinary local-blob/source path. Handle partial attachment cleanup without removing another owner’s resources. Other attachment errors remain errors. An unavailable producer export remains an ordinary unavailable-resource outcome, without recipe fallback. Hold no manager or ownership metadata lock across byte I/O; per-parent/diff import exclusion still covers apply.

On cancellation or failure, close unfinished content writes, unmount, release mutable and prefix handles, and remove only temporary ownership. Preserve reusable completed layers and unrelated owners. Track the last acquired prefix independently of an error return that returns nil. After successful adoption, ordinary usage, collection, and restart apply. A retained descendant pins its ancestors, so testing a pruned ancestor beneath a live leased child would prove an impossible lifecycle.

Why standalone deferred opening waits

No Directory/File opening change is proposed. Chain import operates below typed decode and returns a present local ref. Deferring standalone local opening would add another lifecycle without improving this unit’s concrete witness.

It also requires precise promises: GetOrEval invokes cache evaluation even when an accessor is set, and Directory/File have one whole group. An opener could avoid snapshot access during typed decode, re-encode, usage, and some wrapper metadata; it could not promise every path accessor remains closed without routing changes. A later proposal must preserve local missing-snapshot errors, snapshot identity and leases before opening, usage without opening, re-encode, ready-helper expectations, and release exactly once. Reuse existing saved-opening reporting through operation clearing. Do not add Container-style parts just for symmetry.

Approved implementation sequence and acceptance contract

The sequence below records the approved scope and validation requirements. The completed work and measured evidence follow it.

  1. Approve the bounded snapshot scope. Scope approval is required; ruling the recipe mechanism is not. The snapshot implementation can proceed while that choice remains open. If Erik wants a parallel recipe decision, use the named completed, eager, native, module, and synthetic cases with their exact frozen inputs. No generic recipe API or foreign-reference conversion is needed for this unit.
  2. Model snapshot lifetime before concurrency changes. Add a small snapshot component: two importers, a shared prefix and suffix, two owners, export registration, source failure, and prune/re-apply. Separate source fetch from apply, snapshot presence from index presence, and actual resource pins from ref handles. Assert at most one in-flight apply per parent/diff key, reuse while the indexed snapshot survives, retained ancestry, and cleanup. Prune or failure/retry may legitimately cause a later apply. The current runner hardcodes CacheLifecycle.tla and its config prefix; register the separate component with a narrow runner change preserving existing invocations and outcome expectations. Keep DagQL learning and mixed production out; unchanged cache lifecycle need not acquire new state.
  3. Unify layer reuse and implement supplied-source import. Extract the common helper, establish operation/provider lifetime, and implement zero-chain handling and missing-byte copy. Preserve the image wrapper. Use source-call, apply, and release counters at real boundaries.
  4. Register local exports and persist reuse state. Cover generated/reused descriptors and omitted-root normalization. Add a focused alternate requested-compression test only if changes to that handling justify it. Round-trip existing index/content rows and ordinary snapshot owner links. Avoid a new persistence format unless the implementation demonstrates an actual representation need.
  5. Prove bytes, reuse, and ownership locally. Use two real local snapshot/content stores with an in-process provider and ordinary engine/cache fixtures. Exercise returned refs through Container, Directory, and File use, plus retained local scalar/list/module-object regressions. No remote service fixture or claimed foreign cache hit.
  6. Run only relevant checks and reconcile the draft. Quick model checks, the new bounded component, and affected ownership/persistence configurations as justified by the delta; focused snapshot/image and changed cache/core tests, with race coverage for concurrency. Each individual TLC run has a 30-minute maximum. Reduce measured bounds before expensive exploration; record source/config hashes, positive reachability, and targeted deliberate breaks. No routine full suite.

Implementation and validation

SnapshotManager.ImportChain imports one chain through the existing content store and shared importLayer helper. Image import retains its image metadata wrapper. Import waits use the parent/diff key; export waits use the snapshot ID. Both observe caller cancellation. Each transfer owns its resources independently while waiting and doing work.

ExportChain registers each returned descriptor under the last emitted prefix. Actual snapshot parents remain unchanged. The returned chain owns its provider resources through Release. Image assembly retains the original chains and a separate lease for manifests, configuration, and timestamp-rewritten layers. Prepared images keep this ownership through the ordinary arbitrary-cache release callback.

Review found that a canceled arbitrary-cache waiter could lose a value that completed later. The consumer now publishes completion and transfers callback ownership under callsMu. Cleanup runs once outside that lock. An existing cache-operation token covers initialization and late cleanup, so shutdown waits for both. Session ownership and cache identity rules are unchanged.

A clean shutdown can retain typed results without releasing every Go ref. A physical check found their private transfer lease still present beside durable result owners. New transfer leases carry a dedicated marker. Startup removes only those marked leases after restoring durable owners and before admitting new work. Unrelated temporary leases remain intact. This preserves live transfer ownership without a fixed expiration time.
