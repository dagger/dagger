# Generated API clients

`engine-dev/` is a typed Go client for the `toolchains/engine-dev` module,
produced by `dagger api client` and regenerated by:

```console
dagger generate dagger-go-sdk:generate-all-client
```

It is registered in the workspace `dagger.toml`:

```toml
[[modules.dagger-go-sdk.as-sdk.clients]]
path = "sdk/go/e2e/internal/dagger/engine-dev"
module = "toolchains/engine-dev"
```

## Manual steps

The generator does not yet emit a client that compiles as-is. Two edits were
made by hand, and both have to be redone if the client is ever regenerated into
an empty directory.

**1. Rewrite the client's module path.** The generator names the module after
the bound module, so it writes `module engine-dev`. That is not a path: nothing
can resolve it, and Go's `internal/` rule stops applying, which would leave this
client importable from anywhere in the repo. `engine-dev/go.mod` was changed to:

```
module github.com/dagger/dagger/sdk/go/e2e/internal/dagger/engine-dev
```

**2. Wire it into the parent module.** The generator never touches
`sdk/go/e2e/go.mod`, so nothing can import the client until it is required and
replaced there by hand:

```
require github.com/dagger/dagger/sdk/go/e2e/internal/dagger/engine-dev v0.0.0-00010101000000-000000000000

replace github.com/dagger/dagger/sdk/go/e2e/internal/dagger/engine-dev => ./internal/dagger/engine-dev
```

`go mod tidy` cannot work this out on its own. It resolves an unknown import by
downloading the module it belongs to, and a nested module has nothing to
download, so tidy fails and editors drop the import as unresolvable.

## What regeneration does to these edits

Nothing — both survive, which is why the fixes are worth making by hand.

Regeneration reads the module name off the existing `go.mod` and keeps it,
refreshing only the `dagger.io/dagger` requirement. It then generates against
that name, so `dag/dag.gen.go` imports the rewritten path rather than
`engine-dev`. The parent `go.mod` is never touched at all.

## Known rough edges

- There is no `go.sum` here, so editors treat this directory as a broken module
  and may report errors on every file. The build is unaffected: the parent
  module's `go.sum` is what governs it. See dagger/go-sdk#20.
- Only one client is generated. A second one would need its own session, and
  object IDs do not cross session boundaries — which is why `harness_test.go`
  lifts the CLI out of the engine container instead of calling `cli-dev`
  directly. See dagger/go-sdk#18 and dagger/go-sdk#19.
