# Rust standalone-client generation

Rust standalone clients are ordinary Cargo libraries whose generated API is bound to
the complete Dagger Core schema and, optionally, exactly one selected module. They use
the public `dagger-sdk` lifecycle and transport; generated projects do not carry a
second Core client, session implementation, or repository-local runtime.

## Initialize and generate

From a Dagger workspace, initialize a client by naming the SDK, a workspace-relative
Cargo project, and the module to bind:

```console
dagger api client init rust clients/acme github.com/acme/daggerverse/acme@<full-revision>
```

Initialization adopts a compatible Cargo package or creates a minimal one, records the
client in the workspace, and initially generates only that client. Add `--no-generate`
to create the scaffold and workspace record without generating bindings. Subsequent
workspace generation selects managed clients at or below the current workspace
directory; it does not rewrite sibling clients.

A local module reference remains mutable with its workspace source. A remote reference
must resolve to the full revision stored in the client record. Moving refs and a
revision different from the stored pin fail before publication.

One client contains Core plus at most one bound module. A module dependency is not
merged into that surface: initialize an independently bound client for the dependency.
That rule keeps regeneration, naming, schema identity, and ownership isolated.

## Public API

Generation adds a public `dagger_client` module to the adopted library:

- `dagger_client::connect()` returns the public owned `dagger_sdk::Client`;
- `dagger_client::core` reuses public Core SDK types by identity;
- `dagger_client::<module>` contains only the selected module's reachable types;
- `dagger_client::<Module>Ext` adds the module-root method to the shared client; and
- `dagger_client::prelude::*` imports the extension trait and common generated roles.

The generated `examples/dagger-client-quickstart.rs` is compile-checked by the fixture
harness. Its lifecycle shape is:

```rust,no_run
use my_client::dagger_client;
use my_client::dagger_client::prelude::*;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = dagger_client::connect().await?;
    let module = client.acme();
    let _selection = module.selection();
    client.close().await?;
    Ok(())
}
```

The selected module determines the generated root method (`acme` above). Generated
handles remain lazy until a scalar is awaited. Call `close` when application work is
complete; all generated handles share that one lifecycle.

## Cargo and ownership policy

The reconciler preserves unrelated dependencies, features, targets, profiles, source,
README content, and `.gitattributes` entries. It adds the exact `dagger-sdk` package
dependency and Tokio features required by the generated quickstart. A conflicting
dependency, toolchain, module declaration, or generated-region claim is a diagnostic,
not an invitation to replace caller policy.

Application lockfiles remain user-owned. Generation neither creates nor deletes
`Cargo.lock`. Reproducible downstream applications should commit their lockfile under
their own policy.

The operation manifest is the sole authority for generated replacement and removal.
It binds target, selected module and pin, package, visible schema, binding catalog,
semantic amendments, and every generated file digest. Regeneration may replace an
authenticated owned file and remove an authenticated obsolete file; unknown files and
authored bytes survive unchanged. The manifest is published last, so a failed or
cancelled operation exposes no partial next generation.

Generated package READMEs contain one digest-authenticated Dagger region. Content
outside that region is authored and preserved.

## Troubleshooting

- A pin error means the resolved remote revision differs from the recorded full
  revision. Re-run initialization intentionally against the new immutable revision.
- A project conflict identifies the semantic Cargo, Rust-module, README, or attributes
  coordinate that cannot be adopted safely. Resolve that authored policy rather than
  deleting unrelated files.
- A schema-scope error means Core changed, the selected module root is ambiguous, or a
  non-Core coordinate is unreachable or belongs to another module.
- An ownership error means current generated bytes no longer match their manifest.
  Restore the generated file or make the desired change in authored source and
  regenerate; never edit generated implementation files directly.
- Diagnostics deliberately contain stable coordinates, not module refs, credentials,
  absolute paths, Cargo output, or generated source text.

## Contributor checkpoint

Standalone-client development is Rust-first and engine-free. From `sdk/rust`, run only
the affected typed slices and reuse current checked assets and the materialized fixture
baseline:

```console
cargo test -p dagger-codegen \
  --test client_compiler_properties \
  --test client_renderer --locked
cargo test -p dagger-sdk-engine \
  --test client_project_properties \
  --test client_usability_properties --locked
```

Investigate fixture sequencing and the owning input before broadening a failed slice.
Do not use an engine run as a local checkpoint substitute. The ordinary completed-engine
check runs one isolated external Rust consumer and leaves focused engine regressions to
their owning tests.
